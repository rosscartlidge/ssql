Status: **built 2026-10-27 (phases 1–4; see §8); release pending.** Ross, after v4.127.1: "now that we have datafusion under
control - I think we should revisit our earlier decision to not produce

## 1. Why revisit a decision that is six weeks old

DFC132 said no to a Rust backend for three reasons. Two of them fell on
2026-10-27; the third still stands and shapes what gets built.

1. **"A lane that cannot be gated."** There was no cargo on the machine
   or in CI, so a generated Rust program could never be run by a test,
   and "every generate format without a test is broken by the next
   refactor". Today the toolchain is installed (rustup stable 1.99.1,
   DataFusion crate 55.2.0 compiled once: 4m47s wall, 1.3 GB of target).
   A Rust lane can be an opt-in gate exactly as the Postgres and
   DataFusion lanes are — and v4.127.1 was the morning those two lanes
   came back after idling from v4.101 and found an integer SUM that
   wrapped. The lesson applies here with more force: a Rust output ships
   only with its lane.
2. **"A SQL string in main.rs is not what the asker means."** True, and
   DFC132 §4b named the alternative — a DataFrame-API lowering — and
   parked it as "buys no semantics, only appearance". Appearance is the
   ask. People want to read the Rust, and a program whose stages are
   `read_parquet → filter → aggregate → sort → limit` is readable and
   extendable where `ctx.sql("…")` is not.
3. **"A port of the typed runtime would own ssql's semantics twice."**
   Still true, and more so: since September the semantics grew checked
   int64 (DFC155 B), Int128 sums (C) and decimal scales (E). This DFC
   does not port anything. The Rust program builds a DataFusion logical
   plan, as `generate sql -dialect datafusion` does through text; the
   engine owns the semantics, and the DataFusion oracle lane — green over
   all 328 equivalence cases as of v4.127.1, decimals and int128 included
   — is what makes "inherits verified semantics" a fact rather than a
   hope.

What the measurement in §4 decides is the *pitch*: whether the Rust is
"faster" or "lives in your Rust program". Every Rust shape builds the
same logical plan as the SQL, so the numbers do not depend on how the
Rust is rendered; they were taken before the renderer existed.

## 2. Decisions (Ross, plan mode, 2026-10-27)

1. **Name: `ssql generate rust`.** The artifact is a Rust program; its
   header says it runs on Apache DataFusion.
2. **Expressions: hybrid.** Everything that comes from *flags* renders as
   DataFusion builders — `col("age").gt(lit(25))`, `avg(col("salary"))
   .alias("avg_salary")`, `col("x").sort(false, false)`, join keys,
   include/exclude/rename, the ranking window functions. Only the
   *expression-language* stages (`-if-expr`, `-set-expr`, `-expr`,
   `-stream-expr`) go through `df.parse_sql_expr(r#"…"#)` with the text
   the existing datafusion-dialect translator already emits. The trade
   that settled it: a builder rendering of the expression language would
   be a third expression translator (~100 functions, every dialect quirk
   — the NaN-is-absent rule, the domain guards, xor as `^`, decimal
   casts, int128 as `Decimal128(38,0)` literals — re-expressed as builder
   calls), the seventh place for every new function and the least
   exercised one; while `parse_sql_expr` takes the exact text the oracle
   lane verified. Rule: **builder when a renderer exists, text
   otherwise**, so coverage never shrinks for want of a builder form.
3. **Coverage equals `-dialect datafusion` from day one.** Common stages
   are DataFrame calls; the exotic layers (the rollup/cube emulation with
   its null-safe joins, keyed except/intersect, unpivot, sample, `from
   range`, `-empty zero`) run as one `ctx.sql(…)` step over the DataFrame
   so far — the **escape hatch**. Same refusals as the SQL dialect, so the
   Rust lane covers exactly the cases the datafusion lane covers; escape
   hatches get DataFrame forms later.
4. **Measure, but build regardless.** The numbers go into §4; no pause
   between phases.

## 3. Design

### 3.1 What the program looks like

The codelab pipeline

```
ssql from employees.csv | ssql where -if status eq active
  | ssql update -set-expr bonus 'salary * 0.1'
  | ssql group-by dept -avg salary avg_salary -sum bonus bonus
  | ssql sort -desc avg_salary | ssql limit 10 | ssql to table
```

renders as (the exact text is pinned by `TestGenerateRustProgram`):

```rust
// Generated by ssql generate rust — runs on Apache DataFusion 55
// Pipeline:
//   ssql from employees.csv
//   …

#![allow(unused_imports)]

use datafusion::arrow::datatypes::DataType;
use datafusion::error::Result;
use datafusion::functions_aggregate::expr_fn as agg;
use datafusion::functions_window::expr_fn as win;
use datafusion::prelude::*;

pub async fn pipeline(ctx: &SessionContext) -> Result<DataFrame> {
    let df = ctx.read_csv("employees.csv", CsvReadOptions::new().has_header(true)).await?;
    let df = df.filter(col("status").eq(lit("active")))?;
    let e1 = df.parse_sql_expr(r#"("salary" * CAST(0.1 AS DOUBLE))"#)?;
    let df = df.with_column("bonus", e1)?;
    let df = df.aggregate(vec![col("dept")], vec![cast(agg::avg(col("salary")), DataType::Float64).alias("avg_salary"), coalesce(vec![agg::sum(col("bonus")), lit(0i64)]).alias("bonus")])?;
    let df = df.sort(vec![col("avg_salary").sort(false, true)])?;
    let df = df.limit(0, Some(10))?;
    Ok(df)
}

#[tokio::main]
async fn main() -> Result<()> {
    let config = SessionConfig::new().set_str("datafusion.catalog.has_header", "true");
    let ctx = SessionContext::new_with_config(config).enable_url_table();
    let df = pipeline(&ctx).await?;
    df.show().await?;
    Ok(())
}
```

Three details of the rendering that the first compile taught: a
`parse_sql_expr` result is bound to a name before the call that consumes
the DataFrame (Rust evaluates the receiver first, so the inline form is
a use after move); the aggregate helpers and the window helpers both
export `first_value`, so they are imported as `agg::` and `win::`
modules rather than glob-imported; and `count_all` lives in the count
module, not `expr_fn`, so a count is `agg::count(lit(1i64))`. The avg
cast and the `coalesce(sum, 0)` are the datafusion dialect's own rules
(`sqlAggAvg`, `sqlSumOrZero`) rendered as builders; an integer column
sums as `cast(col, Decimal128(38, 0))` as the SQL does (`sqlSumArg`).

The sink decides `main`'s tail: `to table` → `show()`; `to csv` → the
arrow CSV writer on stdout; `to jsonl` and every other sink → JSONL on
stdout through `datafusion::arrow::json::LineDelimitedWriter` over
`execute_stream()` (the form the equivalence lane reads); `to parquet F`
→ `write_parquet(F, single-file)`. `-func NAME` emits only the function,
which is how the lane builds one binary from 328 pipelines (§5).

### 3.2 The assembler keeps the layer tree

`generate sql` builds one flat `sqlQuery` per SELECT layer and, when the
next stage would break SQL's fixed clause order, *renders* the layer into
text and makes it the next layer's `FROM (…)` (`wrapAsSubquery`,
`generate_sql.go`). The Rust renderer needs the chain as a tree. Phase 2
adds parallel structure the SQL path never reads — `inner *sqlQuery`
retained by the wrap, a `source` for leaves, structured `conds`, `aggs`,
`wins`, `sorts`, `assigns`, `join`, `setOp`, `star` beside the strings the
translators already produce, and `sqlOnly`/`fromTemplate` marking the
layers that run as SQL text — and leaves every rendered string exactly as
computed today. An opt-in snapshot test (`SSQL_SQL_SNAPSHOT=write|check`)
renders all 328 equivalence pipelines in all three dialects before and
after and diffs the bytes; the three SQL lanes stay the semantic gate.

This is not a second parse of command grammar (the DFC115 rule). The
structured records are produced by the same `translate*` functions that
produce the SQL text, from the same `lib.Op`; the Rust renderer consumes
the assembler's structures, as the SQL renderer does.

### 3.3 Rendering rules

Per layer, in SQL evaluation order: joins (`df.join(right, JoinType::…,
&["k"], &["k"], None)`; USING yields one key column in SQL and `join`
keeps both, so the right key is dropped; `-on` aliases `__l`/`__r`) →
where (builder for `-if FIELD OP VALUE` with int/float/string/bool
literals, text for `-if-expr` and for time/decimal/int128 literals) →
group-by (`aggregate(group, aggs)`; `count_all()` for `-count`; an
aggregate without a `rust` renderer in the registry and every `-expr`
term fall back to text; output order — group columns then aggregates in
flag order — matches the SELECT list) → projection (star layers map to
`drop_columns` / `with_column` / `with_column_renamed`; explicit lists to
`select`; window additions to `with_column(alias, …)` — `select` and
`with_column` plan the window node themselves) → distinct → sort
(`col(x).sort(asc, !asc)`, DataFusion's SQL NULLS default) → limit/offset.
Escape-hatch layer: `ctx.register_table("__qN", df.into_view())?` then
`ctx.sql(r#"<the layer's SQL with FROM __qN>"#)`; a leaf escape hatch
(`from range`, `-empty zero`) is `ctx.sql` alone. Aggregates used as
windows must be built as `Expr::WindowFunction(WindowFunction::new(
sum_udaf(), …))` — `sum(x).partition_by(..)` fails in DataFusion 55 — so
window flags with frames render as text in v1; the ranking and offset
functions by flag get builders.

### 3.4 Running it

`generate rust OUTPUT.rs` writes the source. `-run` and `-build PATH`
compile through a cache crate at `${XDG_CACHE_HOME:-~/.cache}/ssql/rust/`
(`Cargo.toml` pinned to `datafusion = "55"` and tokio, `src/main.rs`
rewritten per invocation, `CARGO_TARGET_DIR` inside it so the dependency
build persists). `cargo` is resolved from PATH, then
`$HOME/.cargo/bin/cargo`, or `SSQL_CARGO`. The first build compiles
DataFusion — several minutes and ~1.3 GB, announced on stderr — and later
builds are the incremental link, tens of seconds. The binary is ~170 MB;
documented, not hidden. `-time` prints compile and run wall as `generate
go` does.

## 4. Measured: DataFusion against typed Go (2026-10-27)

Machine A (24 cores, 62 GB), warm page cache, three runs each, best shown.
DataFusion runs the `generate sql -dialect datafusion` output through the
DFC132 §4b harness extended with CSV/JSONL output modes (`dfrun`, release
build); typed Go is `generate go -build`; DuckDB 1.5.0 runs the duckdb
dialect. All write their output to `/dev/null`; wall is the whole process.

| Pipeline (14.6 M rows unless noted) | DataFusion | typed Go | DuckDB |
|---|---:|---:|---:|
| `group-by a_kind relationship z_kind -count -cube` (the README cube) | **0.19 s** | 0.32 s | 0.36 s |
| `group-by relationship -count`, Parquet | **0.03 s** | 0.15 s | 0.03 s |
| `group-by relationship -count`, the same rows as 1.2 GB CSV | **0.24 s** | 1.63 s | 0.71 s |
| `where -if relationship eq 7 \| include a_kind a_name z_name \| to csv` (2.7 M rows out) | 0.70 s | 1.51 s | **0.41 s** |
| 10 M rows, `where age gt 30`, three chained `join -using`, `count` | **0.26 s** | 0.89 s | 0.29 s |
| `cast -type relationship decimal:2 \| group-by a_kind -sum` | **0.04 s** | 1.29 s | 0.06 s |
| `window -partition a_kind -order a_name -sum relationship` then `group-by a_kind -max` | **5.7 s** | 35 s (fixed; was > 1800 s) | 14.0 s |

Peak RSS, for the record: the cube 185 MB / 940 MB / 437 MB; the CSV
group-by 88 MB / 1.5 GB / 760 MB; the filtered write 1.9 GB / 8.1 GB /
1.4 GB (typed Go's parallel CSV sink buffers every shard's output before
the dump, the documented trade); the window 1.7 GB / 3.8 GB / 3.0 GB.

What the table says:

1. **DataFusion is faster than typed Go on every workload**, by 1.7× on
   the cube and 2–7× elsewhere, and matches DuckDB within noise on the
   scan-and-aggregate shapes. The DFC132 framing ("Rust would not change
   the algorithm or the memory model") was right about a port and wrong
   about the engine: a vectorised, morsel-parallel executor over Arrow
   batches beats a row-at-a-time streaming program with struct types,
   including on CSV, where DataFusion's reader is 7× faster than
   `ReadCSVParallel`. The pitch for `generate rust` can be speed as well
   as ecosystem.
2. **The one shape DataFusion does not win is the streaming write**, where
   DuckDB is faster and typed Go is within 2×: a filter and a projection
   with 2.7 M rows of output is bounded by formatting, not by the plan.
3. **The typed Go window is pathological.** One core at 100 %, 3.8 GB,
   still running at the 30-minute cap (an earlier run was killed at twelve) on a running sum over 26 partitions of
   about 560 k rows; DataFusion's 5.7 s and DuckDB's 14 s are themselves
   a global sort of 14.6 M rows by a string column. Something in the
   typed window path is super-linear in the partition size, and the scale
   gate (DFC113) has no window case, which is exactly the gap the
   "fixture that fits in a pipe buffer" rule names. Fixed the same
   evening (window_running.go, typed/window_running.go: the running
   frame carried in one pass, the whole frame once; 50 k rows 53 s →
   0.15 s in exec, 9 s → 0.02 s typed; the 14.6 M-row pipeline 35 s
   typed, 219 s exec); the scale gate has its first window cases.

Method: `scratchpad/bench/run.sh` and `run2.sh` (this session), three
runs each, best wall; DataFusion's "plan" time (SQL → logical plan) was
2–9 ms in every case, so the whole-process wall is the engine's time
plus the ~20 ms start of a 174 MB binary.

## 5. The gate

- **`rust` lane** in `TestPipelineEquivalence`, opt-in on
  `SSQL_RUST_LANE=1` and cargo found; inherits the datafusion lane's
  skips. One binary, not 328: on first use the lane walks `equivCases`,
  runs `generate rust -func case_<n>` for each (a refusal records the
  skip), writes one crate (`src/cases/<name>.rs`, a `main.rs` dispatching
  on `argv[1]`), builds once under a persistent `CARGO_TARGET_DIR`
  (`SSQL_RUST_TARGET`, default `~/.cache/ssql/rust-lane`), then each
  subtest runs `bin case_<n>` and hands its JSONL to the standard
  normalisation. The rust lane must equal exec, and — same engine — the
  datafusion lane; a difference between those two is a lowering bug.
- **Watch it fail** before trusting it: flip one `sort(asc, …)`.
- `make lanes` gains the rust lane; the pre-tag checklist names it.
- Snapshot test for the Phase 2 refactor (§3.2).
- Pinned-text unit tests for ~12 rendered programs; a cargo-gated test
  that compiles and runs the codelab pipeline.

## 7. Built (2026-10-27)

Phases 1–4 and the docs landed the same day, on the `generate-rust`
branch.

- **Assembler tree** (`generate_sql.go`): `sqlQuery` gained `inner`,
  `source`, `sqlOnly`/`fromTemplate`, `star`, `includeCols`,
  `groupFields`/`aggs`, `conds`, `wins`, `assigns`, `joinNodes`, `setOp`
  and `sink`, filled by the same translators that render the text;
  `wrapAsSubquery` keeps the layer it folds, `wrapAsSQLOnly` builds a
  rebuilding translator's text twice (over the source and over the
  placeholder), `buildJoinQuery` returns a side's layer,
  `assembleQuery` is `assembleSQL` without the render. `TestSQLSnapshot`
  (972 files: 324 cases × 3 dialects) was byte-identical after every
  step.
- **`generate rust`** (`generate_rust.go`, ~800 lines): the renderer
  of §3.3, `-run`/`-build` through the cache crate, `-func`, the
  optimiser re-exec shared with `generate sql` (`optimiseThenRegen`).
  Pinned by `TestGenerateRustProgram` (the whole codelab program),
  `TestGenerateRustLayers` (one case per layer kind), `TestGenerateRustUnion`,
  `TestGenerateRustFunc`, and the cargo-gated `TestGenerateRustRuns`
  (`SSQL_RUST_LANE=1`), which compiles and runs a program and checks
  its JSONL.
- **The `rust` lane** (`equivalence_rust_test.go`): of the 324 cases,
  172 render, 132 are refused by the datafusion dialect by design, and
  20 fail to generate for reasons the case already skips every SQL lane
  for (`-expr` aggregates, seeded samples, folds, conditional new
  columns); one crate, one 190 MB binary, built in about 25 s once the
  dependency build exists. Green on the first full run but for one
  case: `path_literal_dot_wins` — `col("a.b")` is table `a`'s column `b`
  to DataFusion, so a name with a dot or a quote now goes through
  `Column::from_name`. The lane equals exec and the datafusion lane on
  every other case at once, which is the claim of §1: a second lowering
  onto an engine whose first lowering is verified inherits the
  verification. Watched to fail: one flipped sort direction failed
  `groupby_no_aggs_distinct`.
- **Compile lessons** (§3.1): bind `parse_sql_expr` results before the
  consuming call; `agg::`/`win::` module aliases instead of two globs
  that both export `first_value`; `count(lit(1))` for `count_all`.
- **Numbers**: the first `cargo build` of the cache crate compiled
  DataFusion in 4m47s wall (60 CPU-minutes, 1.1–1.3 GB); the relink of a
  new program is 3–10 s; the binary is 174 MB.
