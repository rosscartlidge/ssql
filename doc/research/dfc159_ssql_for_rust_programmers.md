# ssql for Rust Programmers: Pipelines as DataFusion Programs

Reference: DFC159
Created: 2026-10-30
Last modified: 2026-10-30

[Back to Index](./README.md)

Audience: a Rust programmer who knows (or is willing to meet) Apache
DataFusion and wants to know what ssql gives them. It explains what
`ssql generate rust` produces, how to build it, embed it, and trust it,
and where its edges are. For the design and its history, see
[DFC157](./dfc157_generate_rust.md); for why ssql did not port its
runtime to Rust, see [DFC132](./dfc132_rust_target_datafusion.md).

## 1. The pitch in one paragraph

ssql is a Unix-pipeline data tool: `ssql from f.csv | ssql where … |
ssql group-by …`, with Tab completion of field names and values at every
step. You explore the data in the shell until the answer is right. Then
`ssql generate rust` turns that pipeline into an ordinary Rust function
on DataFusion's DataFrame API, one statement per stage, with no ssql
runtime, crate or FFI involved. The result is code you would have written
by hand, that you can read, edit, commit and call from your own service.
On the workloads measured (§6), it is also the fastest way to run the
pipeline, faster than ssql's own generated Go and level with DuckDB.

## 2. What you get

```bash
ssql generate rust -pipeline 'ssql from employees.csv
  | ssql where -if status eq active
  | ssql update -set-expr bonus "salary * 0.1"
  | ssql group-by dept -avg salary avg_salary -sum bonus bonus
  | ssql sort -desc avg_salary | ssql limit 10 | ssql to table' pipeline.rs
```

```rust
// Generated by ssql generate rust — runs on Apache DataFusion 55
// Pipeline:
//   ssql from employees.csv
//   ssql where -if status eq active
//   …
// Rules applied:
//   sort-limit-to-top: ssql sort -desc avg_salary | ssql limit 10 → ssql top 10 -field avg_salary

#![allow(unused_imports)]

use datafusion::arrow::datatypes::{DataType, Field, Schema};
use datafusion::error::Result;
use datafusion::functions_aggregate::expr_fn as agg;
use datafusion::functions_window::expr_fn as win;
use datafusion::logical_expr::Operator;
use datafusion::prelude::*;

pub async fn pipeline(ctx: &SessionContext) -> Result<DataFrame> {
    let df = ctx.read_csv("employees.csv", CsvReadOptions::new().has_header(true)).await?;
    let df = df.filter(col("status").eq(lit("active")))?;
    let e1 = df.parse_sql_expr(r#"("salary" * CAST(0.1 AS DOUBLE))"#)?;
    let df = df.with_column("bonus", e1)?;
    let df = df.aggregate(vec![col("dept")], vec![cast(agg::avg(col("salary")), DataType::Float64).alias("avg_salary"), coalesce(vec![agg::sum(col("bonus")), lit(0i64)]).alias("bonus")])?;
    let df = df.sort(vec![col("avg_salary").sort(false, true)])?;
    let df = df.limit(0, Some(10))?;
    Ok(df)
}

#[tokio::main]
async fn main() -> Result<()> {
    let config = SessionConfig::new().set_str("datafusion.catalog.has_header", "true");
    let ctx = SessionContext::new_with_config(config).enable_url_table();
    let df = pipeline(&ctx).await?;
    df.show().await?;
    Ok(())
}
```

How to read it:

- **One `let df = …` per stage, shadowing.** Every stage takes the
  DataFrame and returns a new one. Nothing executes until `main` asks for
  rows (`show`, `execute_stream`, `write_parquet`), so DataFusion's
  optimiser sees the whole plan.
- **Flags become builders.** `-if status eq active` is
  `col("status").eq(lit("active"))`, and a group-by is `aggregate` over
  the `agg::` helpers. Window flags such as `-rank` and `-lag` use the
  `win::` helpers with `.partition_by(…).order_by(…).build()?`. Joins are
  `join` / `join_on`, and set operations are `union` / `except` /
  `intersect`. A rollup is one `aggregate` per grouping set joined on its
  keys, a keyed `except` an anti join, `unpivot` a `union` of branches.
- **Expressions become text that DataFusion parses.** An ssql expression
  (`-set-expr`, `-if-expr`, `group-by -expr`) is handed to
  `df.parse_sql_expr(r#"…"#)`, DataFusion's own SQL expression parser,
  in the text ssql's DataFusion SQL dialect renders. That keeps the
  expression to one translation, the one the test lanes check (§5). It
  is bound to `e1`, `e2`… before the statement that consumes `df`,
  because Rust evaluates the receiver first and the inline form would be
  a use after move. Some aggregates without a builder in the generator,
  such as `median`, come through the same way.
- **The semantics are spelled out in the code**, so nothing is hidden in
  a runtime. `avg` is cast to `Float64`, since ssql's average is always a
  float. An empty `sum` is `coalesce(…, 0)`, since ssql's empty sum is 0.
  An integer column sums through `cast(…, Decimal128(38, 0))` so it
  cannot wrap past `i64::MAX`.
- **The header is the provenance.** It lists the pipeline as written,
  and the optimiser's rewrites when it applied any (`+O` turns them off).
  It also lists any stage that still runs as SQL text (§7), and in the
  current test suite there are none.

## 3. Building it

You need a Rust toolchain (rustup's stable is what is tested) and
nothing else from ssql.

**Let ssql build it.** `-run` compiles and runs it, and `-build PATH`
compiles it to a binary:

```bash
ssql generate rust -run -pipeline '…'           # compile, run, print
ssql generate rust -build ./report -pipeline '…' # keep the binary
ssql generate rust -run -time -pipeline '…'      # plus compile and run wall
```

ssql keeps one cache crate under `${XDG_CACHE_HOME:-~/.cache}/ssql/rust/`
with its own `CARGO_TARGET_DIR`. The **first build compiles DataFusion:
several minutes and about 1.3 GB of target directory**, which it
announces on stderr. After that a new pipeline is an incremental build
and relink, tens of seconds. cargo is found on `PATH`, then at
`~/.cargo/bin/cargo`, or wherever `SSQL_CARGO` points. The release
binary is about 170 MB, because DataFusion is statically linked.

**Or use your own crate.** The program needs three dependencies:

```toml
[dependencies]
datafusion = "55"
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
futures = "0.3"   # only the CSV/JSONL stdout sinks use it
```

The generated code targets DataFusion 55, the version the test lane
pins. A later major version may move an API (DataFusion breaks its API
between majors). Pin it, and regenerate when you move.

## 4. Embedding: `-func`

`-func NAME` emits only the function, with no `main` and no imports:

```bash
ssql generate rust -func top_paid -pipeline 'ssql from employees.csv
  | ssql window -partition dept -order salary -desc -rank r
  | ssql where -if r le 2 | ssql include dept name salary' >> src/queries.rs
```

```rust
pub async fn top_paid(ctx: &SessionContext) -> Result<DataFrame> {
    let df = ctx.read_csv("employees.csv", CsvReadOptions::new().has_header(true)).await?;
    let df = df.select_columns(&["dept", "name", "salary"])?;
    let df = df.with_column("r", win::rank().partition_by(vec![col("dept")]).order_by(vec![col("salary").sort(false, true)]).build()?)?;
    let df = df.sort(vec![col("dept").sort(true, false), col("salary").sort(false, true)])?;
    let df = df.filter(col("r").lt_eq(lit(2i64)))?;
    let df = df.select_columns(&["dept", "name", "salary"])?;
    Ok(df)
}
```

(The `select_columns` before the window is ssql's optimiser pruning the
read to the columns the pipeline uses.)

Put the import block from §2 at the top of the module once, and as many
`-func` functions under it as you like. ssql's own test lane builds
about 200 pipelines into one crate this way. The function takes your
`SessionContext`, so the caller owns:

- **the session**: memory pool, spill directory, target partitions,
  object stores. To read `s3://` paths, register the store on the
  context; the generated `read_csv` takes whatever path you generated it
  with. The context needs `datafusion.catalog.has_header = true` only if
  you also run SQL against it.
- **the output.** The function returns a lazy `DataFrame`, so you can
  `collect()` it into `RecordBatch`es, stream it with
  `execute_stream()`, `write_parquet`, register it as a view
  (`ctx.register_table("t", df.into_view())`), or keep building on it
  with more DataFrame calls.
- **the paths.** The file names are literals, exactly as you typed them
  in the pipeline, so a relative path is relative to the process's
  working directory. To make the function take its input as a
  parameter, edit the one `read_csv` line. The code is yours.

## 5. Why you can trust it

The same ssql pipeline runs six ways: ssql's interpreter, three
generated Go forms, generated SQL on DuckDB, Postgres and DataFusion,
and this generated Rust. `TestPipelineEquivalence` runs about 330
pipelines through every way and asserts that the outputs are
byte-identical after normalisation, on shuffled fixtures chosen so that
a wrong answer actually diverges. The `rust` lane (opt-in:
`SSQL_RUST_LANE=1`, part of `make lanes` before every release) builds
every case's `-func` into one crate and runs it. The lane has paid for
itself already. On the day TSV, JSONL and declared types were lifted,
it found that DataFusion's CSV reader **truncates** a decimal cell with
too many digits (12.345 → 12.34) where ssql rounds (12.35), so the
generator now reads a declared decimal as text and casts it. It also
found `trunc`/`sign` of a decimal failing on the infinity guard.

The rust lane must also agree with the DataFusion SQL lane. It is the
same engine, so any difference is a bug in the generator, not a
semantic choice.

Semantics a Rust programmer should know:

| ssql | In the generated program |
|---|---|
| an absent value | Arrow null |
| a NaN or ±Inf result | null (ssql treats non-finite numbers as absent; expressions that can produce one are wrapped in a guard) |
| `int` / `float` / `bool` / `string` | `Int64` / `Float64` / `Boolean` / `Utf8` |
| `int128` (a cast, a literal past int64, an integer sum) | `Decimal128(38, 0)`: DataFusion has no 128-bit integer type |
| `decimal:S` (declared only, never inferred) | `Decimal128(38, S)`, rounded half away from zero |
| a time column | read as `Utf8`: ssql's zone rules are not DataFusion's timestamp parser |
| `x / y` | always a float division, null when `y` is 0 |
| row order with no `sort` | **not guaranteed**. ssql keeps input order and DataFusion's parallel executor does not; add a `sort` stage if order matters |

## 6. Performance

Machine A (24 cores), 14.6 M rows, whole-process wall, best of three
(`doc/performance.md` §1a, `scripts/bench-engines.sh`):

| Pipeline | generated Rust (DataFusion) | ssql typed Go | DuckDB 1.5 |
|---|---:|---:|---:|
| three-key cube | **0.19 s** | 0.32 s | 0.36 s |
| `group-by -count`, Parquet | **0.03 s** | 0.15 s | 0.03 s |
| the same, 1.2 GB CSV | **0.24 s** | 0.39 s | 0.71 s |
| filter + project + write CSV (2.7 M rows) | **0.70 s** | 1.51 s | 2.9 s |
| 10 M rows, three chained joins, count | **0.26 s** | 0.89 s | 0.29 s |
| decimal cast + sum | **0.04 s** | 0.23 s | 0.06 s |
| windowed running sum over 26 partitions | **5.7 s** | 9.2 s | 14.0 s |

A vectorised, morsel-parallel engine over Arrow batches beats a
row-at-a-time program on every row here, CSV reading included. The
binary starts in about 20 ms despite its size.

## 7. Edges

**What refuses.** `generate rust` refuses what ssql's DataFusion SQL
dialect refuses, with the same message ("… has no datafusion
translation: reason"), apart from the sources the DataFrame readers
can take and the SQL file table cannot (`.tsv`, `.jsonl`, `-type`, a
schema sidecar, integers past int64). The main groups:

- **sources**: `from lines`, `from -last`, `from catalog`, a URL source,
  a single-array `.json` file (DataFusion reads JSON one object per
  line), several Parquet files by pattern;
- **DuckDB-only constructs**: `join -asof`, `resample`, `describe`,
  `extract`, `explode`, list functions and member access on nested
  values, the `-stream-expr` folds;
- **functions DataFusion lacks**: `date_diff`, `sha1`, `mode`, an exact
  percentile over a window frame, `string_agg` over a bounded frame,
  time functions in a zone other than UTC (run the pipeline with
  `-tz UTC`);
- **seeded sampling**: `sample -seed` cannot reproduce ssql's generator
  on another engine. An unseeded `sample` works, and is statistically
  equivalent rather than identical.

When a pipeline refuses, `generate go` produces a Go program for it,
and `generate sql` may produce DuckDB SQL for it.

**What is still text.** Expressions go through `parse_sql_expr` by
design (§2). Window aggregates over a frame (`-sum … -preceding 3`)
are also text: in DataFusion 55 an aggregate used as a window has to be
built through `WindowFunction::new(sum_udaf(), …)`, and the generator
does not do that yet. Neither choice costs speed, because the parsed
expression is the same logical `Expr` the builder would make. `from
range`'s source is one `ctx.sql("SELECT value AS n FROM
generate_series(…)")` line, because the DataFrame-side route to
`generate_series` is deprecated in 55 and fails at run time. The stages
after it are builder calls.

**Coming back to ssql.** The program's output is ssql's input: `to
jsonl` and `to csv` stream to stdout (`./report | ssql from jsonl - |
…`), and `to parquet F` writes a file ssql reads. A dedicated
interchange test for Parquet written by the Rust program is a TODO
(DFC157 follow-up 4). JSONL and CSV are covered by the lane itself.

## 8. Workflow, end to end

1. Explore in the shell with Tab completion: `ssql from data.parquet |
   ssql where -if <Tab>…`, looking at the answer after every stage.
2. When it is right, put `generate rust -run` in front of the same
   pipeline, check that it prints the same answer, and see how long it
   takes.
3. `-func my_query` and paste it into your crate, or `-build` a binary
   for cron.
4. When the question changes, change the pipeline and regenerate rather
   than editing the Rust, unless the edit is the point (a parameterised
   path, your own sink).
