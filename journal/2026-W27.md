## 2026-06-30 (Tue) — v4.54.0: top type-aware ranking, kill _row_number, Alt-r timing

Three things, all from the user comparing CLI output to generated typed code.

**`top` ranked strings wrong.** `top -field a_name` (a string field) returned
arbitrary rows: the execution path keyed via `extractNumeric`, which returned 0
for every non-number, so all strings tied at 0. The typed codegen always
compared by the field's native Go type (string → lexicographic), so it was
right and the CLI was silently wrong. Fixed by ranking with `ssql.CompareAny`
(the comparator `sort` uses). Added comparator-based `ssql.TopByFunc`/
`BottomByFunc` (bounded heap, O(N·log K)) to back it; deleted the now-dead
`extractNumeric`. Execution now matches codegen — locked with a `top_string_asc`
corpus case across record/typed/parallel.

**Killed `_row_number`.** `ssql.ReadCSV`/`ReadCSVFromReader`/`from xlsx` had
attached a hidden `_row_number` column at read time since the very first commit.
It leaked into to-table/to-csv/to-json and diverged from typed mode (which never
had it) — the user "never liked it", so: removed from both io.go readers and
xlsx.go, dropped the now-dead consumer guards (helpers.go fieldNames filter,
join.go right-field skips). Kept arrow.go's general `_`-prefix skip (defensive)
and repointed its test to a neutral `_internal` example so the term appears
nowhere in code. Record and typed output now match. Tradeoff noted in CHANGELOG:
`window -row-number` is the way to get row numbers now.

**Alt-r timing.** Alt-r regenerates typed Go from READLINE_LINE and runs it, so a
shell `time` never wrapped the real work. Added `generate go -time`: runGoSource
already compiles then runs as two steps, so it now reports both to stderr —
`[ssql: compiled in 1.4s, ran in 7ms]` — compile separate from run so the run
figure is the compiled pipeline's true speed. Alt-r passes `-time` and echoes it
inline on success (errors still go to the popup).

Gates: full corpus (record/typed/parallel) green, cmd/ssql -short green (260s),
root/commands/wasm/typed green, -race clean, doc-check 36/36. Also shipped

## 2026-06-30 (Tue) — N-way differential equivalence harness + record/SQL top fixes

**The bug that motivated it.** User's `top -field a_name` (string) gave different
results in record-mode Go codegen vs typed. Root cause was the SAME string-vs-
numeric bug from v4.54.0, but in two paths I'd missed: (1) the **record-mode Go
codegen** template still emitted `ssql.BottomBy(..., float64 GetOr(f,0.0))`
(coerces strings to 0) — fixed to `ssql.BottomByFunc + ssql.CompareAny`, matching
execution + typed; (2) **`generate sql`** `translateTop` was worse — it looked
for the long-removed `-by` flag (so NO `ORDER BY` was ever emitted) and treated
`args[0]` as N (so `-asc` became `LIMIT -asc`). Rewrote it → `ORDER BY FIELD
DESC|ASC LIMIT N`; DuckDB-verified. All four paths now agree.

**Why it kept happening → build a real gate.** `top` had 4 result-producing
paths and the smoke corpus (Contains/Excludes) couldn't tell them apart —
`top_string_asc` expected Alice/Bob and the *buggy* output also contained
Alice/Bob (employees are alphabetical, so "first-N" == "sorted-N"). So I built
`cmd/ssql/equivalence_test.go` (`TestPipelineEquivalence`): one pipeline → every
lane (exec / go-record / go-typed / go-parallel / generate-ssql) → canonical
JSONL via `to jsonl` → normalise the *legitimate* differences (column order:
record alphabetical vs typed struct order; int/float via json→float64) →
assert **byte-identical**, ordered-list when the pipeline defines order else
multiset. Fixtures are **shuffled** with distinct values (new `corpusShuffledCSV`)
so wrong selection diverges; `Golden` gives an impl-independent oracle (catches
"all lanes agree but all wrong" — how the exec bug originally hid).

**Proved it has teeth**: temporarily reverted the record-codegen fix → the
harness failed with the exact diff (`exec: Tokyo,Quito,Paris` vs `go-record:
Cairo,Lima,Mumbai`), pointing at the lane. Restored; all 8 cases × 5 lanes green.

Tests: strengthened TestTopGeneration/Asc (assert TopByFunc+CompareAny, reject
float64 key); new TestTranslateTopSQL; new corpus `top_string_desc`

gate for any change to a command's results. Uncommitted, on top of the

## 2026-07-03 (Fri) — DuckDB equivalence lane + real expr→SQL translation

Picked the top item from the v4.55.0 TODO triage: make DuckDB the sixth
equivalence lane, then let it drive the remaining `generate sql` fixes.

**The lane** (`equivalence_test.go`): `generate sql` output executed by
`duckdb -json`, rows re-emitted as JSONL into the same normalise-and-compare
path as the Go lanes. Discovered via PATH or `~/.local/bin`; the lane is simply
absent (with a t.Log) when no binary — so CI without duckdb still runs the
other five. One legitimate representation difference needed normalising:
DuckDB's SUM over BIGINT returns HUGEINT, which `duckdb -json` serialises as a
JSON *string* (`"150000"`); canonical integer strings are converted back to
numbers (defensible because ssql's own CSV reader parses digit strings as
numbers anyway).

**What honest watch-it-fail looked like.** The TODO's headline quirk — WHERE
values always quoted (`n > '15'`) — turns out to be MASKED by DuckDB itself:
probed `SELECT 20 > '15.5'` → DuckDB coerces by the non-string side, so
well-typed columns never observably diverge. Quoting is still fixed (bare
numerics/booleans via `sqlLiteral`) but its guard is unit tests
(`TestSQLLiteral`, `TestTranslateConditionLiterals`), not the lane. The lane's
real teeth came from the OTHER quirk: `-if-expr` passthrough. `&&` is a SQL
parse error, and `"double quotes"` are SQL *identifiers* — so
`where -if-expr 'pop > 15 && city != "Oslo"'` (idiomatic, straight from the
help examples) generated SQL DuckDB rejected. Reintroduced both bugs
temporarily: `where_expr` failed loudly (parser error) and `update_set_expr`
failed silently-wrong (multiset diff: exec had `TOKYO`, duckdb had `Tokyo`) —
the exact two failure modes the harness exists for.

**The translator** (`generate_sql_expr.go`, `exprToSQL`): parse with the
expr-lang parser (already a dependency), walk the AST, render the SQL-safe
subset — `and`/`&&`→AND, `or`/`||`→OR (SQL `||` is concat!), `==`→`=`,
string literals re-quoted `'…'`, `??`→COALESCE, `?:`→CASE WHEN, `in [..]`→IN,
contains/startsWith/endsWith/matches operators, upper/lower/trim/abs/round/
floor/ceil/len→length/hasPrefix→starts_with/hasSuffix→ends_with/min→least/
max→greatest, int/float/string→CAST, has(f)→f IS NOT NULL, getOr→COALESCE.
Anything else fails loudly naming the construct (member access, closures,
split, …). This de-risks the future expr→Go transpiler too: the AST-walk shape
is now proven on the most alien backend.

**Silent drops found by reading the translator with fresh eyes** (all fixed,
all previously produced wrong-but-running SQL): `update -set-expr`/`-if-expr`
ignored entirely; `+if`/`+if-expr` negation ignored (extra rows!); `group-by
-expr/-stream-expr/-rollup/-cube` dropped (now loud errors; ROLLUP/CUBE have
direct SQL forms if ever wanted, but exec's subtotal-row shape must be matched
first — TODO'd).

## 2026-07-03 (Fri) — user-reported: SQL assembler ignored pipeline stage order

Minutes after pushing the DuckDB-lane work, the user ran
`update -set x 3 | limit 10 | group-by relationship -count count | join …`
through `generate sql -run` and got a parser error (`CASE ELSE '3' END`).
The parse error was the SHALLOW bug; the deep one: the assembler folds every
stage into ONE SELECT, whose fixed clause order applies LIMIT after
GROUP BY/JOIN — the OPPOSITE of the pipeline. Even de-parsered, that SQL
computes a different thing (group all rows, keep 10 groups).

**Fix — subquery wrapping** (`needsWrap` + `wrapAsSubquery` in
generate_sql.go): before translating each stage, check whether its SQL slot
is already occupied or an earlier-running clause is already set (limit before
group-by, a second projection, join/where after group-by, sort after limit,
offset after limit, re-sort, top after sort…); if so, fold the accumulated
query into `FROM (subquery)` and continue. In-order pipelines still render
flat (asserted). The user's pipeline now nests three-deep and returns
byte-identical results to exec. Related fixes in the same pass: unconditional
`-set` emits the plain value (CASE needs ≥1 WHEN); `distinct` renders
`SELECT DISTINCT` (was a fake select column — `SELECT DISTINCT, col` and bare
`SELECT DISTINCT`, both invalid SQL); a later `sort` PREPENDS its keys
(stable re-sort semantics: new key primary, old order tie-break).

**The harness immediately earned its keep.** Adding an `include dept |
distinct` equivalence case surfaced a bug nobody reported: record-mode
generated code didn't dedup at all (7 rows vs 3). Root cause is nasty and
general: both `distinct` and `union` keyed records by `fmt.Sprintf("%v", r)`
— Record is `{schema *Schema, values []any}` with no Stringer, so the key
embeds the schema POINTER. Equal-valued records from different schema
instances never match. Exec `distinct` only worked by luck (one shared
schema from the reader); exec `union` — whose whole point is records from
DIFFERENT sources — never deduped (verified: self-union returned 24 rows).
The kicker: `ssql.RecordKey` (value-based, exactly right) already existed
and union's GENERATED code already called it — only the CLI exec paths never
adopted it. That's the CLAUDE.md "refactor CLI when exporting package
functions" rule failing in the wild. All three call sites now use RecordKey.

**Do we need extra tests to find these?** (the user's question). The harness
design is sound — what was missing is CASES: every v4.56 stage-order bug was
a 2-stage ORDERING (limit|group-by, update|group-by, projection|projection)
no hand-written case exercised, and distinct/union had no cases at all.
Added: TestSubqueryWrapping (7 shapes incl. flat-stays-flat),
TestUpdateUnconditionalSet, TestDistinctSQL, TestResortPrepends unit tests;
equivalence cases limit_then_group, update_unconditional_then_group,
include_distinct, union_dedup (duckdb lane skipped — union has no SQL
translation yet, TODO'd). Watch-it-fail: disabled needsWrap → binder error +
golden diffs, as expected. The systematic answer is TODO'd: a PERMUTATION
generator enumerating 2–3-stage orderings of a small command set through the
existing lanes would find this whole class mechanically.

Also TODO'd: `update -set NEWCOL` translates to `* REPLACE`, which needs the
column to exist (exec creates it) — right fix is schema-aware translation
via the SSQL_MODE=schema walk.

Gates: equivalence 13 cases × 6 lanes green, corpus green, commands green,
doc-check 36/36.

## 2026-07-03 (Fri) — typed update was serialising entire pipelines

## 2026-07-03 (Fri) — expr→Go transpiler: deep dive + implementation plan (doc only)

User named the transpiler (expr-codegen-transpilation.md) as the next big
thing and asked for a detailed implementation plan — no code yet. Wrote
doc/research/expr-transpiler-implementation-plan.md (indexed in README).

**Method:** two parallel tracks. (1) Empirical probes of expr-lang v1.17.6
semantics (three scratchpad programs, typed AND dynamic envs — the dynamic
one matters because ssql compiles with map[string]any, so cross-type == is
silently false at runtime, not a compile error). (2) An Explore agent
produced a verbatim inventory of every VM emission site, Tier-3 bail-out,
runtime helper, and the aggregation patcher.

**Probe results that would have bitten us** (now §2 tables in the plan):
`/` is ALWAYS float division (7/2 = 3.5 — emitting Go integer division is
the #1 regression trap); `**`/`^` always float64; `abs`/`min`/`max` are
type-PRESERVING; `len()` counts RUNES not bytes; `round()` is
half-away-from-zero (== math.Round, luckily); int arithmetic wraps like Go;
missing fields are nil and comparisons with them are per-row runtime
errors; `1 < 2 < 3` chained comparisons are legal expr-lang.

**Plan shape:** exprToGo next to exprToSQL (same package, proven walk);
a tiny generic exprfn runtime package; a three-tier fallback ladder —
native → VM-with-STATIC-env (new: keeps the stage typed so one exotic expr
no longer drags the whole downstream pipeline through toRecord into Record
mode) → whole-stage Record fallback (today's floor). Five shippable phases
(typed where/update first; -stream-expr as an explicit fold before -expr
via the aggregation patcher's normal form; record mode fourth). Divergence
policy: the VM's silent behaviours (cross-type == false, non-bool predicate
→ all rows dropped, toFloat64 → 0) become LOUD codegen errors. Test gates:
emitted-source unit tests, a differential VM-vs-native harness (corpus
build-and-run pattern), unskipping the update_set_expr typed lanes as the
Phase-1 acceptance test, a permutation-stage addition, 0-alloc benches, and
a watch-it-fail (emit integer division once; the harness must catch 7/2).

**Three latent bugs found on the way** (§9, fix with/before Phase 1):
+if-expr negation silently DROPPED in record-mode codegen (only exec
honours _negated — live multi-backend divergence, v4.55 class; needs an
equivalence case + fix NOW, independent of the transpiler); update
-set-expr eval errors silently set the field to ""; toFloat64 defaults
non-numerics to 0 in -expr aggregations.

## 2026-07-04 (Sat) — negation + expr bug sweep (the §9 fixes, pre-transpiler)

Fixed everything §9 of the transpiler plan found, plus what fell out while
fixing. The negation bug was far wider than the dig's headline:

**The matrix.** `+if`/`+if-expr` negation was honoured ONLY by where's exec
path and by generate sql (v4.56). Everywhere else, silently wrong: record
codegen applied `+if` conditions UN-negated (where AND update), typed
codegen same (where AND update), `+if-expr` entries (map form with
_negated) were dropped entirely by record codegen — and by update's EXEC
path too (string-only type assert). Root cause is one shape: autocli
delivers negated single-arg flags as maps, plain ones as strings, and five
different readers each type-asserted only the string. Fix: one shared
`parseExprConds` helper (helpers.go) + `_negated` reads and `!(…)` wrapping
at every emission site.
