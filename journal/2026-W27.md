# Journal — 2026-W27

## 2026-06-29 (Mon) — v4.52.0: ssql conventions + subcommand-help fix

Two discoverability wins, both from "thinking aloud" turns.

**`ssql conventions`** (commands/conventions.go) — the third leg alongside
`ssql functions` (expr language) and `-help`/Alt-h (per-command): an in-binary
reference for cross-cutting semantics that span commands and surprise people.
Kept tightly scoped (evaluation / data / pipeline / codegen). Single-source
`ConventionsReference` + per-category consts, mirroring FunctionsReference.
Registered in BOTH mains (the drift test enforces parity). Entry #1 is the
`update` snapshot semantics we'd just nailed down by experiment: every
-set/-set-expr/-if in one update sees the ORIGINAL row (SQL SET semantics);
pipe to sequence. So a subtle, undocumented behaviour now has a discoverable
home — and the pattern scales (next surprising rule → one more entry).

**Subcommand help lists subcommands** (autocli v4.11.0) — `ssql to -help` (and
from/generate/…) never listed `to table`, `to csv`, … Fixed Subcommand.Generate
Help / GenerateManPage to add a COMMANDS section (in -help and -man), show
`<COMMAND>` in USAGE, and drop the misleading "does not support clauses" for
dispatchers. Also fixed the parser walk to pass the full parent path so
`ssql to table -help` reads "ssql to table", not "ssql table" (it was passing
the root name, dropping the intermediate). General fix — helps every dispatcher
command across any autocli CLI.

The update-semantics question that kicked this off: confirmed empirically that
update assignments all read a once-frozen snapshot (no left-to-right; same-field
literal-vs-expr → expr wins regardless of order; pipe to sequence), and that
execution and codegen AGREE. It's SQL UPDATE SET parity, not a bug.

Released autocli v4.11.0 then ssql v4.52.0 (full flow + deploys).
