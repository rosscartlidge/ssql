### CLI pipeline added as third row in codegen comparison (commit c109c0a)

The `TestCodegenBench` was missing the most user-visible baseline:
the multi-process CLI pipeline that users actually run interactively
*before* discovering code generation. Added it. Findings:

```
CLI pipeline    3.08s   33 MB     (interactive, JSONL on inter-process pipes)
Record codegen  2.69s   910 MB    (SSQLGO=1)
typed codegen   0.77s   8.7 MB    (SSQLGO=typed)
```

- typed vs CLI:    **4.0× faster**
- typed vs Record: **3.5× faster, 104× less memory**

Surprising-but-correct: each row wins on a different dimension *until*
typed. CLI pipeline keeps RSS tiny by streaming via JSONL pipes (no

serialization. Record codegen collapses to one process (faster wall
time) but `map[string]any` blows up RSS to 900 MB. Typed codegen wins
both at once.

Numbers updated in three docs (README, typed-reference, codegen
proposal §11a) so users see the three-way comparison wherever they
land.

### Tier 3b codegen — Sprint 1 + Sprint 2 (commit 370eee1)

Did items #1-5 from the roadmap in one focused session. Five new
commands moved from "deferred" to "shipped":

- `top N -field F` → desugared to `typed.SortByDesc(...)` followed by
  `typed.Limit[T](N)` (or `typed.SortBy` when `-asc`)
- Multi-field `sort` → new `typed.SortByFunc` runtime helper, plus a
  comparator generator that handles per-field asc/desc by swapping
  `a` and `b` for descending fields. Single-field path keeps the
  simpler `typed.SortBy`/`typed.SortByDesc`.
- `cast -type FIELD TYPE` → `typed.Select` with a derived
  `<Input>Cast` struct where the cast field's Go type changes.
  Conversion expressions cover string ↔ int ↔ float ↔ bool: numeric
  casts use direct conversion, string casts go via `strconv`,
  bool↔numeric uses inline closures.
- `update -set FIELD LITERAL` → `typed.Select` that copies all
  fields and overrides the named ones. Emits a derived
  `<Input>Updated` struct *only when the update introduces a new
  field*; otherwise reuses the input type for zero added struct cost.
  Inferred Go type for new fields: bool > int64 > float64 > string
  from the literal value.
- `update -if F OP V -set ... + ... + ...` → first-match-wins
  rendered as an if/else-if Go block. Reuses `typedWhereCondition`
  for predicates so all literal operators work.

`-if-expr` and `-set-expr` get clear "Tier 3" error fragments
naming the offending operator.

### Per-shard CSV output buffer — closes the parallel-mode write-everything regression

The earlier parallel-mode codegen had a known regression on the
filter `age > 30` workload: 9.07 s vs 6.59 s for typed-serial (0.73×,
parallel slower). Root cause was the `Stream.Serial()` fan-in
channel before `WriteCSV` — about ~100 ns/row of scheduling cost,
which on a 7.25 M-row output adds up to ~700 ms of pure overhead
that exceeds the parallel-filter savings on transform-and-write
workloads.

Fix: added `Stream.WriteCSV` and `Stream.WriteCSVToWriter` on the
Stream type itself. Each shard formats its rows into its own
`*bytes.Buffer` in parallel; the final stage writes the buffers to
the output sequentially in shard order. No per-row coordination on
the hot path. Updated `to csv` codegen for `SSQLGO=parallel` to emit
`inputVar.WriteCSVToWriter(os.Stdout)` instead of
`typed.WriteCSVToWriter(inputVar.Serial(), os.Stdout)`.

Re-ran the same benchmark on the same machine (32-core, 10M-row CSV
input, ~7.25M-row output):

| Config | Wall time | vs typed-serial | vs DuckDB |
|---|---:|---:|---:|
| typed-serial | 5.7 s | 1.0× | 8.1× slower |
| **typed-parallel (per-shard buffer)** | **1.3 s** | **4.4× faster** | 1.86× slower |
| DuckDB | 0.7 s | 8.1× faster | 1.0× |

Trade-offs documented in `claude/concurrency.md` §12: peak memory
~2× output size (each shard buffers its slice in RAM); within-shard
order preserved, across-shard is shard-concatenation order (same as
`Serial()` already emits, no regression). For outputs that don't fit
in RAM, fall back to `SSQLGO=typed`.

Output verified identical to typed-serial after sort: 7,250,028 rows
match exactly across both modes.

### GroupByParallel — Sink/Combine/Finalize lands

Following the per-shard buffer fix, the next big-win item was
parallel group-by. Same morsel-driven idea DuckDB uses: each shard
owns its own `map[K]ParallelAggregator[T, S]`; once the input is
drained, a sequential Combine phase merges shards' partials into a
single global result; Finalize yields rows lazily.

Design captured in
`doc/research/typed-groupby-parallel-proposal.md` before
implementation (per the user's request to keep design separate
from code).

Aggregator interface decision: opt-in extension rather than
breaking change. `typed.ParallelAggregator[T, R]` extends
`typed.Aggregator[T, R]` with `Merge(other Aggregator[T, R])`.
`typed.ParallelAggFunc[T, R]` is the constructor type.
`typed.GroupBy` is unchanged; `typed.GroupByParallel` is the new
entry point. Counter/Summer/Averager all got a Merge method (their
state is trivially associative) and `New*` constructors that
return `ParallelAggFunc`.

Runtime in `typed/stream.go`:

```go
func GroupByParallel[T, S, O any, K comparable](
    in     Stream[T],
    keyFn  func(T) K,
    newAgg ParallelAggFunc[T, S],
    build  func(K, S) O,
) iter.Seq[O]
```

Implementation: `len(in.shards)` goroutines each build their own
partial map; `wg.Wait()` joins them; sequential Combine walks
partials in shard order; the returned `iter.Seq[O]` walks the
final map's `[]K` in insertion order and yields `build(k, agg.Result())`.
No shared mutable state during Sink. No channels. Race-clean
under `-race`.

Codegen wiring: `cmd/ssql/commands/typed_groupby.go` got a
`parallel bool` parameter. When true, the synthesized
`<Input>Aggregator` struct picks up a generated `Merge` method
(per-spec rules: count and sum are `a += b`; avg merges sum + n;
min/max honour the "have value" flag). The call site flips from
`typed.GroupBy(...)` + `typed.Aggregator` to `typed.GroupByParallel(...)`
+ `typed.ParallelAggregator`. The output fragment carries
`IsStream=false` because `GroupByParallel` returns `iter.Seq[O]`
not `Stream[O]`.

That last point exposed an existing bug in the parallel-mode
sinks: `to_csv` and `to_table` were keying off
`parallelMode()` (the global env-var-derived flag) rather than
the previous fragment's `IsStream`. After parallel group-by
that's a category error — global mode is "parallel" but the
specific fragment carries `iter.Seq[T]`. Fixed both sinks to read
`fragments[len-1].IsStream`. The per-shard CSV buffer path is
now correctly only taken when the immediate upstream is a Stream.

`-presorted` group-by is rejected in parallel mode at codegen
(shards split contiguous runs); error suggests `SSQLGO=typed` for
that pipeline.

Headline result on the same 10M-row corpus, group-by `dept_id`
(1 000 distinct values) with `count + sum(salary) + avg(salary) +
min(age) + max(age)`, 32-core machine:

| Config | Wall time | vs typed-serial | vs DuckDB |
|---|---:|---:|---:|
| typed-serial group-by | 3.80 s | 1.0× | 9.7× slower |
| **typed-parallel group-by** | **0.95 s** | **4.0× faster** | 2.4× slower |
| DuckDB equivalent | 0.39 s | 9.7× faster | 1.0× |

All 1 000 groups produce identical count/min/max across serial,
parallel, and DuckDB; sum and avg agree to within float64
precision (parallel reorders the addition, which is non-
associative in `float64` — the divergence is in the last few
ULPs, irrelevant for analytics). Tests in `typed/agg_test.go`
include a parity check across shard counts {1, 2, 4, 7, 16}.

### What's next

User flagged TSV (no-quoting split-on-tab) and Parquet as
upcoming I/O work. Both made it into the typed-codegen-proposal
future-work list:

- **TSV (clean, no escaping):** ~1 hour of work. Should be ~2×
  faster than `encoding/csv` because there's no quote-handling
  state machine and no `bufio.Reader` per-byte cost.
- **Parquet:** likely the biggest single I/O win on read-bound
  workloads. Columnar + compressed + typed; row groups map
  naturally to shards. Would need a dependency on `parquet-go`
  and tag-mapping work; ~1–2 days of effort. Could plausibly
  close the remaining 2.4× gap to DuckDB on the group-by
  workload.

Additional Phase-3 items still on the list: stream-aware
`Limit`/`Offset`/`Distinct`, hash-partitioned Stream source for
the `#groups ≈ #rows` case, and `SerialOrdered()` fan-in.
