### Per-shard CSV output buffer — closes the parallel-mode write-everything regression

The earlier parallel-mode codegen had a known regression on the
filter `age > 30` workload: 9.07 s vs 6.59 s for typed-serial (0.73×,
parallel slower). Root cause was the `Stream.Serial()` fan-in
channel before `WriteCSV` — about ~100 ns/row of scheduling cost,
which on a 7.25 M-row output adds up to ~700 ms of pure overhead
that exceeds the parallel-filter savings on transform-and-write
workloads.

Fix: added `Stream.WriteCSV` and `Stream.WriteCSVToWriter` on the
Stream type itself. Each shard formats its rows into its own
`*bytes.Buffer` in parallel; the final stage writes the buffers to
the output sequentially in shard order. No per-row coordination on
the hot path. Updated `to csv` codegen for `SSQLGO=parallel` to emit
`inputVar.WriteCSVToWriter(os.Stdout)` instead of
`typed.WriteCSVToWriter(inputVar.Serial(), os.Stdout)`.

Re-ran the same benchmark on the same machine (32-core, 10M-row CSV
input, ~7.25M-row output):

| Config | Wall time | vs typed-serial | vs DuckDB |
|---|---:|---:|---:|
| typed-serial | 5.7 s | 1.0× | 8.1× slower |
| **typed-parallel (per-shard buffer)** | **1.3 s** | **4.4× faster** | 1.86× slower |
| DuckDB | 0.7 s | 8.1× faster | 1.0× |

Trade-offs documented in `claude/concurrency.md` §12: peak memory
~2× output size (each shard buffers its slice in RAM); within-shard
order preserved, across-shard is shard-concatenation order (same as
`Serial()` already emits, no regression). For outputs that don't fit
in RAM, fall back to `SSQLGO=typed`.

Output verified identical to typed-serial after sort: 7,250,028 rows
match exactly across both modes.

### GroupByParallel — Sink/Combine/Finalize lands

Following the per-shard buffer fix, the next big-win item was
parallel group-by. Same morsel-driven idea DuckDB uses: each shard
owns its own `map[K]ParallelAggregator[T, S]`; once the input is
drained, a sequential Combine phase merges shards' partials into a
single global result; Finalize yields rows lazily.

Design captured in
`doc/research/typed-groupby-parallel-proposal.md` before
implementation (per the user's request to keep design separate
from code).

Aggregator interface decision: opt-in extension rather than
breaking change. `typed.ParallelAggregator[T, R]` extends
`typed.Aggregator[T, R]` with `Merge(other Aggregator[T, R])`.
`typed.ParallelAggFunc[T, R]` is the constructor type.
`typed.GroupBy` is unchanged; `typed.GroupByParallel` is the new
entry point. Counter/Summer/Averager all got a Merge method (their
state is trivially associative) and `New*` constructors that
return `ParallelAggFunc`.

Runtime in `typed/stream.go`:

```go
func GroupByParallel[T, S, O any, K comparable](
    in     Stream[T],
    keyFn  func(T) K,
    newAgg ParallelAggFunc[T, S],
    build  func(K, S) O,
) iter.Seq[O]
```

Implementation: `len(in.shards)` goroutines each build their own
partial map; `wg.Wait()` joins them; sequential Combine walks
partials in shard order; the returned `iter.Seq[O]` walks the
final map's `[]K` in insertion order and yields `build(k, agg.Result())`.
No shared mutable state during Sink. No channels. Race-clean
under `-race`.

Codegen wiring: `cmd/ssql/commands/typed_groupby.go` got a
`parallel bool` parameter. When true, the synthesized
`<Input>Aggregator` struct picks up a generated `Merge` method
(per-spec rules: count and sum are `a += b`; avg merges sum + n;
min/max honour the "have value" flag). The call site flips from
`typed.GroupBy(...)` + `typed.Aggregator` to `typed.GroupByParallel(...)`
+ `typed.ParallelAggregator`. The output fragment carries
`IsStream=false` because `GroupByParallel` returns `iter.Seq[O]`
not `Stream[O]`.

That last point exposed an existing bug in the parallel-mode
sinks: `to_csv` and `to_table` were keying off
`parallelMode()` (the global env-var-derived flag) rather than
the previous fragment's `IsStream`. After parallel group-by
that's a category error — global mode is "parallel" but the
specific fragment carries `iter.Seq[T]`. Fixed both sinks to read
`fragments[len-1].IsStream`. The per-shard CSV buffer path is
now correctly only taken when the immediate upstream is a Stream.

`-presorted` group-by is rejected in parallel mode at codegen
(shards split contiguous runs); error suggests `SSQLGO=typed` for
that pipeline.

Headline result on the same 10M-row corpus, group-by `dept_id`
(1 000 distinct values) with `count + sum(salary) + avg(salary) +
min(age) + max(age)`, 32-core machine:

| Config | Wall time | vs typed-serial | vs DuckDB |
|---|---:|---:|---:|
| typed-serial group-by | 3.80 s | 1.0× | 9.7× slower |
| **typed-parallel group-by** | **0.95 s** | **4.0× faster** | 2.4× slower |
| DuckDB equivalent | 0.39 s | 9.7× faster | 1.0× |

All 1 000 groups produce identical count/min/max across serial,
parallel, and DuckDB; sum and avg agree to within float64
precision (parallel reorders the addition, which is non-
associative in `float64` — the divergence is in the last few
ULPs, irrelevant for analytics). Tests in `typed/agg_test.go`

```

$ time ./parallel       # SSQLGO=parallel | group-by | to table
real  0m1.809s
user  0m10.184s

```

Parallelism: `user/wall = 10.18 / 1.81 = 5.62×` on what is
effectively a 6-core box — close to perfect scaling for
embarrassingly parallel `read + group + count`.

I ran DuckDB against the same file on the same machine:

| Tool | Wall time (mean of 3) | vs other |
|---|---:|---:|
| ssql `SSQLGO=parallel` | 1.81 s | 1.0× |
| **DuckDB** | **0.78 s** | **2.32× faster than ssql** |

Output content matches: same 14 relationships, same row counts.
The 2.32× gap is consistent with the 2.4× we measured on the
synthetic 10 M-row corpus — real-world data corroborates the
synthetic benchmark, so the model is sound.

What this gap actually is, on a back-of-envelope:
- DuckDB's wall time (~0.78 s) is approximately the time to
  read 1.23 GB off disk at typical SSD bandwidth (1.5–2 GB/s) —
  i.e. **DuckDB is essentially at the I/O ceiling.**
- We are paying for `encoding/csv`'s quote-handling state
  machine and per-row allocation churn. The Go pipeline is no
  longer algorithm-bound; it's parser-bound.

Two levers ranked by likely effect:

1. **Clean-TSV reader (split-on-delim, no quoting/escaping)** —
   ~2× faster than `encoding/csv` on clean data because there's
   no state machine and no `bufio.Reader` per-byte cost. Cost:
   ~1 hour of implementation. Won't help users with quoted
   fields.
2. **Parquet input** — 5–10× less bytes off disk, no string
   parsing at all (types are native), row groups map naturally
   to shards. Cost: a `parquet-go` dependency and ~1–2 days of
   tag-mapping work. Could plausibly close the remaining 2.32×
   gap to DuckDB without changing the algorithm.

Both go into the next sprint. Decision and design coming up
next.

## 2026-04-28 (Tuesday)

### TSV reader landed — but was a smaller win than projected

Implemented `typed.ReadDelim` / `ReadDelimParallel` /
`WriteDelim` mirroring the CSV API surface. Default delimiter
`'\t'`; configurable via `typed.WithDelim(byte)`. Same struct-tag
decoder. NOT safe for embedded quotes / delimiters / newlines —
explicitly out of scope.

Two micro-optimisations targeted at the per-row hot path:

1. **Zero-copy field strings via `unsafe.String`.** The parallel
   reader holds the entire file in memory (one `os.ReadFile`,
   sliced into per-shard chunks); each row's `[]byte` is a stable
   slice into that buffer. We can therefore make the row's
   `[]string` alias into the file bytes — no allocation, no
   copy. Safe because the strings (and any struct-string fields
   decoded from them) live only as long as the iter.Seq, which
   holds the file buffer.
2. **SIMD-accelerated split via `bytes.IndexByte`** instead of
   a manual byte-by-byte scan.

The serial `ReadDelim` (using `bufio.Scanner`) does NOT use
zero-copy because Scanner reuses its internal buffer between
calls — aliased strings would be silently invalidated.

Headline on the user-corpus 14.6 M-row group-by-with-count:

| Tool | Wall (mean) |
|---|---:|
| ssql parallel CSV (existing) | 1.85 s |
| ssql parallel TSV (split, copy strings) | 1.73 s |
| **ssql parallel TSV (zero-copy + SIMD)** | **1.51 s** |
| DuckDB on TSV | 0.74 s |

The originally projected "2× faster than CSV" did not
materialise. The bottleneck wasn't `encoding/csv`'s
quote-handling state machine (~7 % of CPU), it was per-field
string allocation (~30 % of CPU went into
`runtime.slicebytetostring`). After zero-copy + SIMD we hit the
memory-bandwidth ceiling of `bytes.IndexByte` at ~600 MB/s. The
remaining 2× to DuckDB is the cost of two full passes through
the file (newline pre-scan + per-shard parse) vs DuckDB's fused
single pass.

Lesson: pre-implementation guesses about where time goes can be
off by 4×. Profile, don't model.

### Parquet reader landed

Implemented `typed.ReadParquet` / `ReadParquetSafe` /
`ReadParquetParallel` / `WriteParquet` / `Stream.WriteParquet`.
Reuses the Apache Arrow Go dependency that ssql already imports
for Record-mode Parquet — no new third-party dependency.

Architecture:

- Read path opens via `parquet/file` + `pqarrow.FileReader`.
  Schema mapping uses the same struct-tag rules as CSV (`ssql:`
  preferred, `csv:` fallback). Per-column decoders are built
  once at file-open time and write directly into struct field
  offsets via `unsafe.Add(p, off)` — no boxing through `any`.
- String fields alias into the Arrow column's contiguous bytes
  buffer (same zero-copy trick as the TSV reader).
- Parallel read uses one shard per row group, capped at `n`.
  Each shard owns its own `pqarrow.FileReader` (the library's
  reader isn't safe for concurrent use across goroutines).
  Round-robin partition so a long row group at the end doesn't
  leave a worker idle.
- `Stream.WriteParquet` collects per-shard `arrow.Record`s into
  a single multi-row-group table; one `pqarrow.WriteTable` call
  writes the whole thing. Each shard builds its arrow column
  builders concurrently (no per-row fan-in).
- `ParquetStrict()` and `ParquetColumns(names...)` options
  match the CSV / Delim convention.

Headline on the same 14.6 M-row corpus (DuckDB-converted to
Parquet with row_group_size = 1 M → 15 row groups):

| Tool | Wall (mean) | vs DuckDB-Parquet |
|---|---:|---:|
| ssql parallel CSV (existing) | 1.85 s | 62× slower |
| ssql parallel TSV (zero-copy + SIMD) | 1.51 s | 50× slower |
| ssql parallel Parquet (all 7 cols) | 1.51 s | 50× slower |
| **ssql parallel Parquet, `ParquetColumns("relationship")`** | **0.15 s** | **5× slower** |
| DuckDB on CSV | 0.74 s | 25× slower |
| DuckDB on Parquet | 0.03 s | 1× |

**Column projection is the primary lever, not the columnar
layout itself.** Without specifying `ParquetColumns(...)` we
read all 7 columns, decompress them all, and end up at TSV
speed. With projection we read 1 of 7 columns and the wall
time drops 10×.

DuckDB's 0.03 s on Parquet is presumably using metadata stats
+ dictionary encoding for `COUNT(*) GROUP BY single_col`; that's
a query-aware optimisation we don't yet do. Even without it, ssql
with column projection lands within 5× of DuckDB on this query.

12 unit tests covering round-trip, column projection, strict
mode, parallel parity, time.Time fields, empty input, Stream
writer round-trip. All race-clean.

### Hitting the I/O ceiling — what remains

Trajectory recap:

- CSV (encoding/csv): 1.85 s — bottleneck was per-field string
  allocation, not the parser
- TSV (zero-copy + SIMD): 1.51 s — memory-bandwidth-bound on
  IndexByte
- Parquet, all cols: 1.51 s — memory-bandwidth-bound on
  decompression stream
- Parquet, projected col: 0.15 s — finally below the
  whole-file read ceiling

The runtime can keep getting faster only by reducing how much
data flows through CPU caches. We've exhausted "do the same
work faster"; remaining wins are "do less work": predicate
pushdown, dictionary stats, codegen-time column projection.
Those are query-planner features, not parser/runtime features.

### What's next

The biggest remaining lever is making the **typed-mode codegen
emit `ParquetColumns(...)` automatically** based on which struct
fields are referenced downstream. With that, a pipeline like
`from large.parquet | where -if x gt 5 | group-by y -count n`
would read only `x` and `y` columns even if the file has 50 —
which is the difference between "fast" and "DuckDB-fast" on
real wide-table workloads.

User shared timings from their dual-socket Xeon Gold 6154 (72
logical cores, 3.0 GHz, slower per-core than the original
benchmark machine but many more cores). Same 1.23 GB /
14.6 M-row corpus, same `from … | group-by relationship -count
number | to table` pipeline, five execution modes:

| Mode | Wall | User | User/Wall | vs CLI |
|---|---:|---:|---:|---:|
| Interactive CLI (3 processes, JSONL pipes) | 68.7 s | 148.9 s | 2.17× | 1.0× |
| `SSQLGO=1` Record codegen | 15.5 s | 45.6 s | 2.93× | 4.4× faster |
| `SSQLGO=typed` codegen | 22.0 s | 26.1 s | 1.19× | 3.1× faster |
| `SSQLGO=parallel` CSV codegen | 1.23 s | 17.4 s | 14.1× | **56× faster** |
| `SSQLGO=parallel` Parquet (column projection) | 0.76 s | 0.74 s | 0.97× | **90× faster** |

**The ~90× chain from CLI to typed-parallel-Parquet** is the
product of three roughly independent wins — easier to see when
laid out:

| Step | Speedup | Cause |
|---|---:|---|
| CLI → Record codegen | 4.4× | Collapse 3 processes → 1; no JSONL serialise/parse round-trips between stages |
| Record → typed codegen | 0.7× (slower!) | Single-threaded compute on slow-clock Xeon; loses GC parallelism |
| typed-serial → typed-parallel CSV | 17.8× | Sharded scan + Sink/Combine/Finalize group-by |
| typed-parallel CSV → Parquet (proj) | 1.6× | Less I/O (column projection skips 6 of 7 cols); also capped at 1 shard because the test file has only 1 row group |
| **Total CLI → parallel Parquet** | **90×** | |

**The "typed-serial slower than untyped" surprise.** On the slow-
core workstation, typed-serial took 22 s while Record-mode took
15.5 s — counter-intuitive given typed wins on the original
benchmark machine. Diagnosis: `SSQLGO=typed` is single-threaded
by design (composing `iter.Seq[T]` is sequential), so it bottle-
necks on per-core clock. `SSQLGO=1` Record-mode looks parallel
(user/wall = 2.93×) but most of that's *concurrent GC across
many cores* cleaning up the millions of `map[string]any` allocations
— not useful work. On a CPU with abundant cores and slower
per-core throughput, the GC parallelism scales out enough to
beat single-threaded typed compute. With `SSQLGO=parallel`, the
real data parallelism unlocks (14.1× user/wall) and beats both.

**The "iter.Seq coroutines = parallelism?" question.** User
asked whether Go 1.23+ `runtime.coro` (the coroutine primitive
that range-over-func uses) might be contributing to Record-mode's
2.93× user/wall. Looked into the runtime source:

- `runtime/coro.go` line 12-13: "A coro represents extra
  concurrency **without extra parallelism**, as would be needed
  for a coroutine implementation." Verbatim.
- `coroswitch_m` lines 222-223: `setMNoWB(&gnext.m, mp)` — the
  goroutine being switched to inherits the same M (OS thread)
  the calling goroutine was on. No M migration, no scheduler
  involvement.
- Plain `for v := range seq` doesn't even invoke `newcoro` /
  `coroswitch` — the compiler transforms it into a direct
  callback. Coros only show up in `iter.Pull` / `Pull2`
  (`src/iter/iter.go` lines 271, 387).
- `grep -rn iter.Pull typed/` returns nothing — the typed
  package doesn't use Pull anywhere.

So coroutines explain nothing about parallelism here. The 2.93×
in Record-mode really is GC parallelism (verified earlier by
`GOGC=off` — user time collapsed from 20.8 s to 7.6 s with
unchanged wall on the original machine).

**Architectural divergence between Record and typed group-by.**
Record-mode emits `Chain(GroupByFields, Aggregate)` — two
separate filters where `GroupByFields` materialises
`map[any][]Record` (storing all 14.6M rows) and `Aggregate`
then iterates each group's `[]Record` to count. O(#rows)
memory, ~100M allocations from boxed `any` and per-row map
entries. Typed-mode emits `typed.GroupBy(records, keyFn,
newAgg, build)` — one call, where the synthesised aggregator's
`Add()` does `c.N++` per row. O(#groups) memory, ~zero allocations.

The architectural difference is the deeper reason for the GC
gap, not just "typed has fewer types."

**Real-corpus numbers added to README.** The existing
synthetic-benchmark table (1M-row, 1-join) showed typed beating
Record by 3.5×; the new real-corpus table (14.6M-row, group-by)
shows the full 90× chain from interactive CLI to typed-parallel-
Parquet. Captures the real user pain point (waiting 68 s for
`ssql ... | ssql ... | ssql ...`) vs the optimised endpoint
(0.76 s).

### v4.37.3 — `ssql to parquet` row-group-size + compression flags

Self-inflicted ceiling spotted yesterday: `ssql.WriteParquet` and
`typed.WriteParquet` both passed total row count as the chunkSize
to `pqarrow.WriteTable`, producing a single row group regardless
of input size. Files written by ssql couldn't be read efficiently
by ssql's own `ReadParquetParallel` (caps at 1 shard).

Three additive fixes in v4.37.3:

1. Library options on Record-mode and typed `WriteParquet`:
   `WithRowGroupSize(n)` and `WithCompression(name)`. Default
   row-group size changed from "all rows in one group" to
   1 000 000 rows per group.
2. CLI flags on `ssql to parquet`: `-row-group-size N` and
   `-compression {snappy,gzip,zstd,none}`.
3. Typed-mode codegen for `to parquet` — was previously a silent
   type-mismatch (the codegen always emitted `ssql.WriteParquet`
   with an `iter.Seq[T]` argument, which doesn't compile).
   Now dispatches: serial typed → `typed.WriteParquet`,
   parallel typed → `Stream[T].WriteParquet` (one row group per
   shard, naturally parallel).

Round-trip verified on a 4-row test file with `-row-group-size 2`:
output has 2 row groups, DuckDB reads it back correctly. Slim
build stub updated so callers compile in `slim` mode.

pipeline to emit parallel fragments. We captured it in the
proposal doc as the interim workaround.

Then we shipped the actual flag:

  `-optimise` / `-O` — apply optimiser rewrites first, then
    re-execute the rewritten pipeline through plain
    `generate go`. SSQLGO target mode inferred from incoming
    fragment metadata (any IsStream=true → "parallel"; else any
    OutputTypedSchema set → "typed"; else "1"). Recursion guard
    is structural (inner generate-go is invoked without
    `-optimise`). Composes cleanly with `-run`, `-build`, and
    `OUTPUT`.
  `-build PATH` — compile to a named binary and exit. Mutually
    exclusive with `-run` and `OUTPUT`. Useful for shipping the
    compiled pipeline (no Go toolchain on the production host)
    or for repeat invocations that should skip the compile step.
  `-explain` / `-e` — with `-optimise`: print applied rules to
    stderr, mirroring `generate ssql -explain`.

End-to-end shortcut: the four-step manual chain
(`generate ssql | bash | SSQLGO=parallel | generate go | go run`)
collapses to:

```bash
ssql ... | ssql generate go -optimise -run
```

The 215× speedup chain accessible via one flag combo. Auto-injects
`ParquetColumns(...)` projection, plus all the other
generate-ssql rewrites (predicate pushdown, sort+limit→top, etc.).

Implementation in `cmd/ssql/commands/generate_go.go`. Reuses
`optimizePipeline` from `generate_ssql.go` directly. Tests
covering all five mode combinations

### v4.38.1 — `group-by` with no fields = single group

User wanted to count rows: `ssql group-by -count count` errored
with "no group-by fields specified." Empty-fields case now means
"single group spanning all rows" (SQL `GROUP BY ()` semantics).
Composes with all aggregations (`-count`, `-sum`, `-avg`, `-min`,
`-max`):

```bash
$ ssql from parquet shuffled.parquet | ssql group-by -count count | ssql to table
count
--------
14628366
```

Plumbed through all four code paths:

- Record-mode execution: `ssql.GroupByFields("_group")` with
  zero fields was already routing to `groupByMultipleFields`
  which collects everything under a single zero-key. Just
  removed the pre-flight error.
- Record-mode codegen: same — emits `ssql.GroupByFields("_group")`
  with no field args.
- Typed/parallel codegen (`typed_groupby.go`): `buildGroupKeyType`
  returns `struct{}` / `struct{}{}` for the empty-fields case.
  The synthesised result struct contains only aggregation fields
  (no group-key fields). Works under both `typed.GroupBy` and
  `typed.GroupByParallel`.
- `generate sql`: q.groupBy stays empty → `renderSQL` omits the
  `GROUP BY` clause. Pure SQL semantics:
  `SELECT COUNT(*) FROM t`.

Rollup/cube still require at least one field — the grouping-set
logic doesn't make sense without one.

Considered (and rejected) adding a `group-as-one` pseudo-command
synonym. The empty-fields case is a clean generalisation, not a
new feature; a separate command would just duplicate codegen and
help text. The complementary `ssql count` sink (deferred) is the
better discoverable shortcut for the most common case.

### v4.38.2 — `to table` column order matches CLI in Record-mode codegen

User noticed the same pipeline producing different column order
between the CLI and the Record-mode codegen binary:

```
$ ssql from csv shuffled.csv | ssql group-by relationship -count number | ssql to table
relationship   number      <- CLI: natural order from JSONL _schema

$ ./untyped                 <- Record-mode codegen
number    relationship      <- alphabetical (different!)
```

Root cause: the CLI pipeline carries a `lib.Schema` through
JSONL `_schema` headers (insertion-order `Fields []string`
slice), and `to table` reads it. The codegen path doesn't have
JSONL transit — fragments pass `iter.Seq[ssql.Record]` directly.
The Records' schemas come from `MutableRecord.Freeze()` which
goes through `NewRecord(map)` and sorts keys alphabetically (Go
map iteration is unordered). So `ssql.DisplayTable(records, 50)`
saw an alphabetical schema and emitted alphabetical columns.

Two-part fix:

1. **Fragment-level field-order tracking.** New
   `OutputRecordFields []string` on `lib.CodeFragment`,
   populated by Record-mode group-by (group-fields ++ each
   aggspec.result in declaration order). `to table` codegen
   reads it and emits
   `ssql.DisplayTableWithFields(records, 50, fields, false)`
   when set; falls back to plain `DisplayTable` (alphabetical)
   otherwise. Natural extension is to populate it from
   from-csv, include, exclude, rename codegens too, but this
   patch handles only the user's reported case.
2. **Runtime: DisplayTable picks up `Record.Schema()` field
   order when no explicit order is given.** Helper
   `naturalColumnOrder` in `io.go` consults the first record's
   schema for natural column order; falls back to alphabetical
   for fields not in the schema. Backwards compatible because
   records that come from `MutableRecord.Freeze()` already have
   alphabetical schemas, so they stay alphabetical (no
   surprise). Records built with explicit
   `NewRecordFromSchema(order, values)` would render in their
   natural order.

Both code paths now produce identical output:

```
relationship   number
---------------------
           1   4849187
           ...
```
