### Addendum: from parquet FILE showed no rows/s (found by Ross)

His three-step test (csv exec 642k rows/s → typed 9.0M rows/s →
parquet typed) found the gap: headInputRows recognized bare
`from X.parquet` by extension but not the `from parquet FILE`
subcommand form — "parquet" was taken as the file, the real file as a
second positional → multi-file → omitted. Format list gains parquet;
the ext-only branch folded into one spelling-agnostic check; unit
case for the subcommand form. Verified live: inputRows 14628366 on
his exact pipeline.

### Addendum 2: the rows/s display finds its first bug same-day

Ross's three-step demo (csv exec 642k/s → csv typed 9.0M/s → parquet
typed) read 2.2M rows/s on `group-by relationship` — "worked but got
a LOT SLOWER". Not a regression: agg-less group-by (DISTINCT
semantics) emitted include+typed.Distinct as SerialOnly — 14.6M rows
through one core (6.7s) — while -count ran GroupByParallel (1.5s).
The throughput display exposed a path difference that had always
existed. Fix: typed.DistinctParallel (per-shard parallel dedupe —
the expensive hashing — then a serial merge over ≤ shards×distinct
rows; race-tested), dual-templated into BOTH the agg-less group-by
and the distinct command (same SerialOnly gap). Verified on his
exact pipeline via a locally-built generated program: 6.7s → 1.5s,
14 groups. Equivalence case groupby_no_aggs_distinct (ordered, all
lanes); corpus green. Note: served ⚡ typed heads compile against the
PUBLISHED module, so they keep the serial form until the next
release — the version-pin behavior, now twice observed.

### Addendum 3: -columns values read as files (found by Ross)

Third find of the morning, same scanner: `-columns relationship`'s
value was taken as a second file → multi-file → rows/s omitted —
right on the showcase pipeline (column-pruned parquet: 14.6M rows in
0.18s ≈ 81M rows/s once displayed). The scanner now consumes an
Accumulate flag's whole value run. The lesson accumulating across
these three: headInputRows re-parses from-args with its own little
grammar, which drifts from the real flag definitions — if it grows
again, derive the file/flag split from ONE shared table with
splitServePipeline/translateFrom instead of three hand-copies.

## 2026-08-25 (Tue) — from -records: the count lives with the format

Ross, after the three scanner-drift bugs: "like completion and help
it should be built into the from command... the from command knows
all about the file so is best placed to know how to calculate the
number of lines in the most efficient way." Exactly the drift lesson,
solved structurally: `from … -records` prints ONE integer — the
records that invocation would produce — cheapest per format (parquet
footer; newline scan −header for csv/tsv; jsonl minus a _schema line;
-sample min(N,rows) parsed by from's OWN grammar; multi-file sums;
stdin/JSON-array loud refusals). serve's headInputRows collapsed from
a hand-rolled arg grammar to "exec stage0 + [-records]" — the entire
drifting-copy class is dead. Caching stayed serve-side per doctrine
(nothing caches across CLI invocations): keyed by opaque stage-0
argv, invalidated by a readdir fingerprint of the served dir's data
files (name:size:mtime) — verified live: first csv head +0.15s,
second 0.03s; limit cap still applies stage-side; pruned-parquet and
sampled paths correct. Tests: TestFromRecords CLI matrix (8 cases
incl. multi-file sum and both refusals), TestHeadInputRowsShape +
TestDirDataFingerprint replacing the deleted grammar table. Bonus
standalone feature: `ssql from big.parquet -records` answers
instantly where `| ssql count` reads everything.
