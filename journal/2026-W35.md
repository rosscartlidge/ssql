## 2026-08-26 (Wed) — the autocli round: completion asks the tool

The queued "sampler registry" plan came out more general: autocli
v4.14.0 grew two host hooks — FieldSource and FieldValueSource,
consulted BEFORE its built-in extractors, error → fallback — and ssql
installs them (commands/completion_sources.go). FieldSource is pure
DFC115: exec self under SSQL_MODE=schema `from FILE` and parse the
_schema header — the exact protocol Ctrl-O and serve already use, so
parquet, URLs, and any FUTURE format `from` learns to route all
complete with zero grammar duplication (no per-extension registry to
drift). FieldValueSource covers only what autocli can't: parquet
columns in-process via ReadParquetColumns (over http it fetches just
that column's byte ranges — value completion against a remote 1.2GB
parquet is instant), URL line formats streamed. `.arrow` honestly
stays at the hint until from arrow grows schema mode (TODO).

The find of the day: while testing the hook, the CONTROL case failed
— `from catalog kind.csv -if <Tab>` gave the hint too. Same-command
field completion (the doc's own debug example!) had silently died:
analyzeCompletionContext parses the words before the cursor, that
prefix necessarily ends mid-flag ("FILE -if"), strict Parse errors,
and the error discarded the already-parsed FILE positional. Nobody
noticed because the degraded mode LOOKS intentional — it's the same
hint the legitimate cross-pipe case shows. autocli v4.14.1: keep the
longest parseable prefix. Gates on both sides, both sabotage-verified
(TestFieldCompletionDanglingFlag in autocli, TestFieldCompletionSources
driving the real binary here). Lesson for the pile: a graceful
fallback can mask a total failure of the primary path — if a feature
degrades to something that looks acceptable, the GOOD path needs its
own test, not just the fallback. This is the W34 field/value
completion lesson again, one layer deeper.

autocli v4.14.0 (hooks) + v4.14.1 (prefix fix) tagged and pushed;
