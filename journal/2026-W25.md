### gh-pages `git add -A` footgun — fixed

Root cause: `gh-pages` shares one working tree with `main`. `git
checkout gh-pages` removes main's *tracked* files but leaves main's
*ignored* artifacts (`typed.test`, `typed/typed.test`, `dist/`, a
generated `dashboard.html` — ~91MB) as untracked, because gh-pages had
**no `.gitignore` of its own**. The documented `git add -A` deploy
would have swept them into the branch.

Fix (gh-pages `28c68cc`): removed the stray artifacts, then added a
gh-pages `.gitignore` mirroring main's patterns. `git add -A` is now
safe — `git status` on gh-pages is clean, and tracked deploy assets
still stage normally (ignore rules never apply to tracked files;
verified by staging a real `playground.html` content change under the
`/*.html` rule). Documented the gotcha in `claude/playground.md`.

### `SSQLGO=schema` de-risk spike — done, doc corrected

Ran the two-front spike (two parallel agents, one per repo) before
committing to implementation. Both load-bearing assumptions had real
cracks; architecture survives but the doc was wrong in
implementation-breaking ways. Findings folded into a new §0 of
`doc/research/schema-aware-completion.md` (authoritative; the stale
inline sketches now carry ⚠ pointers to it).

**Separability (§4.3): HOLDS with caveats.** Every schema-mutating
command builds an explicit `*lib.Schema` before/independent of
iteration (pivot is the sole data-dependent case, correctly
`ok=false`). Big de-risk: `Command.Parse(args)` is reusable, so
SchemaOps don't hand-parse argv. But "5–15 lines" is optimistic for
**group-by** (4 sub-shapes + rollup/cube) and **join** (~20–40 lines;
*not* pure — does I/O on the right file's `_schema`, bails on process
substitution). Doc errors caught: `rename` is `-as old new` not
positional; `window` has no `-into` (17 result flags + real type
inference); `cast` emits no runtime schema so it can't be
shadow-tested. Pre-req: factor group-by's ~140-line ×2 agg-flag parse
into a shared `parseAggSpecs(ctx)` first.

**autocli surface (§7): sound strategy, every API name fictional.**
`Completer` is a clean one-method interface and `UpstreamFieldsCompleter`
+ `ChainCompleter` fallback drop in cleanly — but `CompleteWithContext`,
`ctx.UpstreamFields`, `ctx.State` all don't exist; real entry is
`Command.Complete(args, pos)` with no injectable context; completion
has no `State` analog; `tabComplete` currently discards everything
before the last `|`. Two misses: **layering** (shell is ssql-agnostic,
can't resolve ssql SchemaOps — needs a generic `SchemaWalk` callback
hook, ssql supplies the walker) and **release order** (needs autocli
**core** v4.7.0 first → shell v0.4.0 → ssql; not "shell-only").

**Decisions taken:** env var = **`SSQL_MODE=schema`** (umbrella; SSQLGO
becomes a deprecated alias, existing modes migrate to SSQL_MODE=*);
scope = **bundle Phase 1+2** (serve + bash, ≈5–6 days, SchemaOps shared
so marginal bash cost is just the plumbing).

### Slice 4: shell — pipeline-aware completion plumbing (shell/v0.4.0) — done

Second cross-repo slice (autocli/shell). The framework half of the
shell integration: on TAB, `tabComplete` now splits the line into
pipeline stages and — when a host-supplied `SchemaWalk` hook is set —
calls it with the upstream stages + session State to get the field
names flowing into the stage under the cursor, seeding them into
`CompleteWithContext`'s `UpstreamFields`. So the framework can now
surface `from-loaded | group-by <TAB>` → loaded schema columns; ssql
supplies the actual walker in slice 5.

- `Options.SchemaWalk SchemaWalkFunc` — `func(state any, upstream
  [][]string) (fields []string, ok bool)`. Shell stays
  **schema-agnostic**: forwards stages + state, seeds whatever names
  come back (resolves the §0 layering risk — shell can't know ssql's
  SchemaOps).
- `tabComplete` rewrite: replaced the old "discard everything before
  the last `|`" scan with `splitStagesForCompletion` (a lenient
  splitter that tolerates empty/trailing stages mid-typing, unlike the
  execution `splitOnPipe`); always seeds `State`; seeds `UpstreamFields`
  when the hook returns ok; calls `CompleteWithContext` not `Complete`.
- Bumped autocli-core dep v4.6.1 → **v4.7.0**.

A nil `SchemaWalk` leaves completion exactly as before (bash/CLI path)
— verified by test. `schema_complete_test.go` covers the end-to-end
seed (insert the hook's field, hook gets `[["from-loaded"]]` + state),
ok=false, nil-hook-unchanged, first-stage-skips-hook, and splitter
cases; existing trailing-space test still green. `shell.go`/`pipeline.go`
were gofmt-clean and stayed clean (no manual-alignment gotcha here).
Shipped **shell/v0.4.0** (annotated `05294ce`), proxy-verified.

### Slice 5: ssql SchemaOps + serve wiring — done; pipeline-aware completion LIVE

The payoff. `from-loaded | group-by <TAB>` now offers the loaded schema,
and a mutating upstream is honoured: `from-loaded | rename name person |
group-by <TAB>` → `person`, not stale `name`.

**Two design forks resolved during the slice:**
1. *Completer wiring.* Rather than registering `UpstreamFieldsCompleter`
   on ~30 field flags (the §7 plan), changed autocli's **`FieldsFromFlag`
   to chain it automatically** (`ChainCompleter{UpstreamFieldsCompleter,
   FieldCompleter}`). Every ssql field flag becomes pipeline-aware for
   free; bash unaffected (empty when unseeded → file fallback). Cost: an
   autocli **v4.8.0** release. (User chose this over the per-flag churn.)
2. *Argv decoding.* The slice-2 plan assumed the group-by SchemaOp would
   reuse `parseGroupBySpecs(ctx)`. But autocli's `Command.Parse` parses a
   *leaf* command's flags and **does not descend into subcommands**, so a
   SchemaOp can't cheaply get a group-by `Context` from raw stage args.
   The ops hand-decode argv via a shared `walkStage(args, arityMap)` with
   per-command arity maps (`cmd/ssql/commands/schema_ops.go`). Slice 2
   still stands — `parseGroupBySpecs` dedups the handler+codegen paths;
   the SchemaOp is just a third, argv-shaped decoder.

**ssql side (`schema_ops.go`):** `schemaOp` registry + `serveSchemaWalk`
(walks upstream stages left-to-right; any `ok=false` poisons the
result). Ops for every serve command where identity would be *wrong*:
`from-loaded` (source → `serveState.schema`), `rename`, `include`,
`exclude`, `update`, `group-by` (keys + agg result names; -rollup/-cube
→ undeterminable), `window` (appends result-flag names), `pivot` (→
undeterminable). `cast`/`where`/`sort`/`limit`/… use the identity
default. `serve` passes `serveSchemaWalk` via `ssh.Options.SchemaWalk`.

**Tested:** each op's decode; multi-stage walk incl. mutating-upstream +
pivot-poison; full composition through the **real serve CLI**
(`buildServeCLI` + walk + `CompleteWithContext`). The autocli
`FieldsFromFlag` change touches all ssql field completion — ssql
completion tests + commands pkg + full corpus (40s) + vet all green,
bash unaffected.

**Released (multi-module, dependency order):** autocli **v4.8.0**
(`6eb62a7`), ssh **v0.1.13** (`3cdf6a1`); both proxy-verified. ssql
pinned to autocli v4.8.0 / shell v0.4.0 / ssh v0.1.13 (dev `replace`s
dropped). Known minor gaps: `count`'s op left identity (near-terminal,
rare upstream); the design §9 schema-shadow corpus test is still future.

### Phase 2: bash subprocess completion — done

Pipeline-aware completion now works at the bash prompt too, reusing the
slice-5 `schemaOp`s (one rule per command across both runtimes).

`SSQL_MODE=schema` (`schema_mode.go`): each command, run under this
mode, reads a schema header from stdin (sources read only the file
header — near-zero cost), applies its rule, writes the output header.
`runSchemaModeTransform` drives the slice-5 ops via `ctx.RawArgs`
(stripping a leading command name if the framework includes it — the
serve path hand-decodes raw stage tokens, the bash path feeds RawArgs;
same op either way). `ssql generate schema` (`generate_schema.go`) is
the terminal that prints the field list.

Sources wired: `from csv` (+ bare `from FILE`), `from tsv`, `from
json[l]` — schema branch lives in the shared `executeFromCSV/TSV/JSON`
so bare-from and the subcommand both get it (caught a bug where bare
`from FILE` fell through to the full read and tacked on `_row_number`).
Transforms wired: rename/group-by/include/exclude/update/window/pivot
(pivot would otherwise crash indexing `results[0]` on empty input).
Identity transforms (where/sort/limit/…) currently pass through via
their normal exec on the empty-record header — correct, just not yet
explicitly short-circuited.

Bash shim (`schema_completion.go`): `ssql -completion-script` now
appends `_ssql_schema_complete` after autocli's `_autocli_complete`
(intercepted in `main()`, like `-shell-helpers`). On TAB at a value
position inside a pipeline it runs `(export SSQL_MODE=schema; <upstream>)
| ssql generate schema` and feeds the fields to compgen; flags and the
single-command case fall through to autocli (which since v4.8.0 already
completes from a referenced file). Verified live via a COMP_WORDS
simulation and a binary-subprocess integration test.

Build-tag note: the registry + transform ops + schema-mode mechanism
are untagged (compile into slim); only the serveState-dependent bits
(`serveSchemaWalk`, `from-loaded` op) are `!slim` in `serve_schema.go`.
Both builds + vet clean; corpus (40s) + commands pkg + new unit and
integration tests green.
