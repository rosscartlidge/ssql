# Week 19, 2026

v4.43.0 ships catalog remote-Go execution — the third and final
codegen-symmetric mode (after v4.42 single-host ssh and the v4.41
`-script` plumbing it sits on). Stock ssh + a deployed ssql per
shard host is now enough to run typed-parallel pipelines distributed
across N shards, with one self-contained Go binary doing the
orchestration.

## 2026-05-07 (Wednesday)

### v4.43.0 — catalog remote-Go execution (commit 5ffd3c0c)

Extends the v4.42 codegen-symmetric pattern across catalog shards.
Whatever mode the local pipeline runs in, each shard runs the same:

```
ssql from catalog SHARDS.csv -- STAGES                                      → CLI chain on each shard (v4.27 baseline)
(SSQLGO=record; ssql from catalog SHARDS.csv -- STAGES) | generate go -run  → record-mode Go on each shard
(SSQLGO=typed;  ssql from catalog SHARDS.csv -- STAGES) | generate go -run  → typed-parallel Go on each shard
```

The local generated Go embeds the per-shard pipeline stages as a
`[][]string` slice, reads the catalog at runtime, prunes, and calls
`ssql.ProcessCatalogShardsRemoteGo`. The function builds the per-
shard `.ssql` script (`# require:` header + `ssql from PATH` +
pushdown stages joined with `| ssql ...`), ships+runs it on each
host (concurrently by default), and returns `iter.Seq[Record]` of
the merged output. Downstream local stages compose on top.

End-to-end verified against a 3-shard catalog pointing at
ssql-node1: CLI baseline, SSQLGO=record codegen, and SSQLGO=typed
codegen all produce byte-identical cross-shard `n=3` aggregation.

### Four design decisions for the orchestrator (proposal rev 2)

The user reviewed the rev 1 proposal and pushed back on the
default-cap-of-8 concurrency: shards run on different hosts, the
local orchestrator is just multiplexing ssh subprocesses with
negligible CPU cost, fork-bombing concerns start at hundreds of
shards. So:

1. **Uncapped concurrency by default.** `-shard-concurrency N` opt-in
   for pathological catalogs.
2. **Completion-order output by default.** Cheaper (no buffering, ~1
   record peak memory). `-shard-order catalog` opt-in for callers
   that need deterministic ordering — buffers per shard, flushes in
   catalog order at the end.
3. **Fail-fast by default.** First shard error cancels remaining
   shards. `-keep-going` opt-out lets all shards finish, returns
   the first error.
4. **Auto-emitted `# require: vX.Y.Z` directive.** The local codegen
   path prepends `# require: v$localVersion` to every shipped .ssql
   script. The remote `ssql generate go -script` preprocessor
   parses this and refuses scripts that name a higher version than
   the running ssql. Single clear error on stale shards instead of
   the cascade of symptoms a v4.40 shard gives when handed a
   v4.42-feature script.

### Two v4.42 bugs surfaced and fixed

End-to-end testing surfaced two real bugs in v4.42:

**Typed JSONL fallback emitted broken Go.** Pipelines without an
explicit `to X` sink fall back to schema-aware JSONL via
`buildInlineToRecordExpr`, which contained:

```go
for v := range %s {  // %s = inputVar
```

That's correct for `iter.Seq[T]` (a function type with Go 1.23+
range-func semantics) but invalid for `typed.Stream[T]` (a struct
that has no Range method — `.Serial()` is required to drain it).
The fix: when the last fragment's `Capabilities.Produces ==
ShapeStream`, render the input variable as `outVar.Serial()`
inside the converter expression. ShapeSeqTyped/ShapeSeqRecord
ranges directly as before.

This affects every typed pipeline that ships JSONL — including
the new catalog remote-Go path, where each shard runs `ssql
generate go -script -mode typed -run` against a sinkless script.
First catalog test failed with `cannot range over filtered
(variable of struct type typed.Stream[ServicesRow])` until this
was fixed.

**Bare `ssql` invocation on remote.** The orchestrator's ssh
command was:

```
trap 'rm -f /tmp/ssql-remote-N-T.ssql' EXIT;
cat > /tmp/...ssql && ssql generate go -script ...
```

`ssql` resolved via PATH to whatever was first on the remote.
Per CLAUDE.md security rules, remote commands should use absolute
paths to prevent PATH manipulation. Worse, on hosts with multiple
ssql installs (a v4.42.1 in `/usr/local/bin`, a newer in
`/usr/bin`), the orchestrator hit the older binary even after
deploy. Fix: `/usr/bin/ssql` everywhere on the remote (both
catalog and from-ssh paths).

### Sequence of incidents debugging the typed-mode catalog path

For the journal-as-context-for-future-Claude file:

1. First catalog typed test against ssql-node1 produced
   `n=1` per shard instead of `n=3` aggregate. Initially
   suspected a bug in my orchestrator — turned out the
   `-optimise` rewriter was pushing `group-by origin -count n`
   into the catalog's `--` pushdown, and `origin` doesn't exist
   on the remote (it's added LOCALLY by enrichCatalogRecord).
   Pre-existing optimiser bug, not introduced by v4.43. Documented
   in TODO. (For v4.43, removing `-optimise` confirms the orchestrator
   itself is correct.)

2. Removing `-optimise` then surfaced the `for v := range stream`
   bug above (the typed-mode codegen for sinkless pipelines).
   Fixed in `buildInlineToRecordExpr`.

3. Fix worked locally, but the catalog test still failed. Manual
   `ssh ssql-node1 ssql generate go -script -mode typed` (no -run)
   showed the new code with `.Serial()`. With -run, still broken.
   Difference: `which ssql` on ssql-node1 returned
   `/usr/local/bin/ssql` (old binary, build e938edb7), but I'd
   only deployed the new binary to `/usr/bin/ssql`. Bare `ssql`
   in the orchestrator's ssh command resolved via PATH to the
   stale `/usr/local/bin/ssql`. Fix: absolute path in the remote
   command + sudo cp the new binary to both locations on the host.

4. Once both fixes landed, every variant produced the expected
   `{"n":3,"origin":"ssql-node1:/data/services.csv"}` aggregate
   row, identical to the CLI baseline.
