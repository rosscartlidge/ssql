## 2026-09-03 (Thu) — DFC123: the pipeline IR charter

Wrote DFC123 (dfc123_pipeline_ir.md) from a three-turn design
discussion with Ross: the IR is the next arc — optimisation,
verification, generation to multiple languages. Framing: "finish the

Op-vs-Code drift checks, rules certified against operator
properties), protocol facts on fragments (retiring fixErrorHandling
textual surgery — this week's typed-sink bug as evidence), and a
fully worked dead-order-elimination example (sort|sort, Ross's
workspace pain; valid because slices.SortFunc is documented-unstable,
now a pinned decision). Sequencing: bindings → Op → SQL translator
consumes Op → protocol facts → order properties → verification.
No code yet by design. Ref: DFC123, DFC099, DFC115, DFC105.

## 2026-09-03 (Thu) — dead-sort elimination (DFC123 §7)

Ross's workspace pain (grid clicks stack sort stages over user text
the workspace may not edit) is now the optimiser's job:
ruleSortElimination grown from the adjacent sort-before-group-by
rule into a forward scan — a sort is dead iff its order reaches an
orderReset stage (sort/top/group-by/resample) across only
orderTransparent stages (where/include/exclude/rename/cast/update);
everything unclassified conservatively consumes order and keeps the
sort. Faithful because ssql sort is documented-unstable (pinned in
the table's comment + DFC123 §7). Surfaces automatically in
Ctrl-T/tail-optimize.

The build's best moment was a sabotage that PASSED when it should
have failed: adding limit to orderReset sailed past the
`sort -desc pop | limit 3 | sort id` equivalence pin because
ruleSortLimitToTop rewrites desc-sort+limit to top BEFORE the
dead-sort rule runs — that case pins rule COMPOSITION, not the
limit-consumes-order classification. Added the ascending variant
(which no other rule rewrites) and the sabotage failed properly in
the ssql-opt lane. Lesson for the DFC: when rules interact, a gate
must pin each rule's own decision, not just the pipeline's end
state. Gates: 11-row unit table, dead_sort_across_where +
live_sort_limit_sort_desc + live_sort_limit_sort_asc equivalence
cases, both-direction sabotage. Ref: DFC123.

## 2026-09-03 (Thu) — `limit -last N` (DFC122 Tier 1, first unit)

Ross's call over the DFC's original `tail` verb: ssql's data verbs
are SQL-flavored and `limit` IS head — a `tail` command would beg
"where's head?", a `head` alias would need every Kind-keyed table to
know two names (the DFC115 drift machine), and head/tail already
name the workspace's pipeline halves. So: `limit -last N`. Rationale
recorded in DFC122 §1 so it isn't re-litigated.

Prime directive honoured on day one: `ssql.TakeLast` + `typed.TakeLast`
(ring buffer, O(N), barriers — `Last` was taken by the group-by
aggregate, hence the name), exec/record/typed/parallel through the
existing limit fragment (one `fn` switch), `generate sql` takes N
under the REVERSED ORDER BY then restores the original outside — and
refuses loudly with no preceding sort (SQL has no arrival order; the
sample -seed precedent). The optimiser's parseLimitCmd hides N when
-last is set so sort-limit-to-top can't fire (`sort -desc x | limit
-last 3` is the three SMALLEST in descending order — not top). Gates:
unit tables in both packages, TestTranslateLimitLast, an optimiser
unit, a corpus case, and three equivalence pins (unsorted with the
duckdb Skip recording the refusal contract; sorted; desc-is-not-top).
Sabotage: an off-by-one in the ring failed the unit table AND the
duckdb lane — the independent oracle mattered here because every Go
lane shares the one TakeLast. Note for the dev loop: `generate go
-run` compiles against the RELEASED module, so a brand-new library
function shows "undefined" there until release; the corpus harness
(replace directive) is the right check. Ref: DFC122.

## 2026-09-03 (Thu) — `ssql describe` (DFC122 Tier 1, second unit)

`ssql.DescribeRecords` (root describe.go): per-field type/count/
missing/distinct + numeric min/max/mean/median, exact everywhere so
the DuckDB translation can match (median = quantile_cont semantics:
middle or mean of two middles). Record-shaped in all lanes BY DESIGN —
rows are heterogeneous (numeric stats absent on string fields) and a
typed struct would have to lie; typed pipelines re-enter record mode
at the stage via the planner boundary, exactly like pivot. SQL:
one UNION ALL branch per column with DuckDB `typeof(min(x))` mapped
to ssql's int/float/string/bool, `count(DISTINCT) FILTER`, `median(
TRY_CAST(x AS DOUBLE))`, ORDER BY the field position; refuses loudly
when q.columns is unknown. Also fixed: bare `from x.csv` never seeded
the translator's column list (only `from csv x.csv` did).

The duckdb equivalence lane earned its keep TWICE before shipping:
(1) exec ordered rows by CSV header, generated record code by
alphabetical key order — first-seen order is lane-dependent, so the
contract became "explicit FIELDS order, else sorted by name" (also
fine UX for wide files); (2) `describe pop city` in exec described
ALL fields — the variadic FIELDS value arrives as []any, my []string
assertion silently failed, and the go-record lane AGREED because it
had the same empty config. Only the independent SQL oracle saw it.
Now handled like include (both shapes) with a loud error on any
other type. Sabotage: mapping ints to 'float' in the SQL type CASE
fails describe_all. The equivalence harness gained one normalization:
null-valued keys are dropped on every lane (ssql's record model does
not distinguish absent from null; SQL can only say NULL). Gates: root
golden test, SQL unit, completion config, corpus (typed→record
boundary), two equivalence cases incl. duckdb. Ref: DFC122.
