## 2026-09-02 (Wed) — typed record-sink fix + `-pipeline` flag

Ross hit a v4.81.0 codegen bug within a day of release: `generate go
-mode typed` on a pipeline ending in `to chart` failed to compile
("too many return values" at the chart sink). Root cause: `to chart`
has no typed template, so the planner shims typed→Record and injects
the RECORD final fragment — whose `return fmt.Errorf(...)` is legal
under the record assembler (which rewrites it via fixErrorHandling)
but the typed assembler emitted finals VERBATIM into `func main()`
(no error return). Fix in `cmd/ssql/lib/codefragment_typed.go`: init
and final fragments now go through fixErrorHandling too, with "os"
imported on demand; fixErrorHandling itself now loops over every
occurrence instead of only the first. Coverage gap closed with
corpus case `record_sink_in_typed_pipeline_chart` (chart sink in all
three modes; sabotage-verified — reverting the fix fails typed with
Ross's exact error). Lesson: the corpus had no record-only-sink ×
typed-mode case, so a whole fragment CLASS (record finals in typed
main) was untested.

Same session, Ross's call: the `ssqlgen` shell helper isn't earning
its keep — replaced by `-pipeline '...'` on all three generate
commands. `runPipelineForFragments` factored out of the -script path
(same preprocessing: comments, leading-| continuations), `generate
go` honors -mode (default typed, exclusive with -script), sql/ssql
fix record mode. Six tests in `cmd/ssql/pipeline_flag_test.go`;
codelab §Shortcut rewritten from ssqlgen to -pipeline. Ross then
called the removal ("they are no help :-)"): -shell-helpers flag,
ShellIntegrations table row, ShellHelpersScript const, and its tests
are gone; -shell-init no longer emits ssqlgen; keybinding

## 2026-09-03 (Thu) — DFC123: the pipeline IR charter

Wrote DFC123 (dfc123_pipeline_ir.md) from a three-turn design
discussion with Ross: the IR is the next arc — optimisation,
verification, generation to multiple languages. Framing: "finish the
IR we already have" (the fragment stream), building on DFC099's
additive plan, not superseding it. The load-bearing new piece is the
AUTHORITY INVARIANT, born from Ross's worry that a central IR
assembler would lose "the command knows how it itself works": the
command owns Op (what I mean) + Code (its own Go lowering calling its
own runtime); backends own composition in their target; Op never
replaces Code for imperative targets — with an explicit erosion guard
against future "generate Go from Op.Kind" simplifications. Also new
vs DFC099: the verification axis (schema flow pre-generation,
Op-vs-Code drift checks, rules certified against operator
properties), protocol facts on fragments (retiring fixErrorHandling
textual surgery — this week's typed-sink bug as evidence), and a
fully worked dead-order-elimination example (sort|sort, Ross's
workspace pain; valid because slices.SortFunc is documented-unstable,
now a pinned decision). Sequencing: bindings → Op → SQL translator
consumes Op → protocol facts → order properties → verification.
No code yet by design. Ref: DFC123, DFC099, DFC115, DFC105.

## 2026-09-03 (Thu) — DFC123 slice 1 shipped: assembler-owned bindings

Same-day follow-through on the charter: `lib.ResolveBindings`
(cmd/ssql/lib/bindings.go) runs at the single assembler entry point
(AssembleCodeFragments, before record/typed dispatch and before the
planner) and assigns guaranteed-unique variable names across the
fragment chain. Mechanics that mattered: (1) references resolve to
the MOST RECENT binding via an env walk; (2) renames are Go-token-
aware (go/scanner — string literals, comments, and selector fields
x.name are never touched); (3) the Var==Input shared-name shape
(`included := Project(included)`) splits on first-occurrence-is-the-
definition — my first draft blindly renamed whole snippets and the
unit test caught the capture immediately; (4) the general case
renames definition→placeholder→final so an input's final name
equalling the fragment's emitted Var can't capture; (5) AltCodeIfSeq
gets identical treatment because the planner swaps it in AFTER the
pass. Contract documented on fragment Code: Var is declared at its
first occurrence (the universal `out := F(in)` shape).

`uniqueVarName` and its 28 per-command call sites are DELETED —
commands now emit bare base names ("filtered", "included") and
collisions are structurally impossible at assembly, which is the
slice's whole point: 28 manual disciplines → one guarantee. Gates:
binder unit tests (collision chain, alt-code, token-aware rename
table), new collision corpus cases include_then_include +
where_then_where_collision alongside the v4.50.1
include_then_groupby, and sabotage — commenting out the
ResolveBindings call reproduces the exact v4.50.1 error ("no new
variables on left side of :=") in typed+parallel. Full battery +
doc-check green. Ref: DFC123.

## 2026-09-03 (Thu) — DFC123 slice 2: Op on the fragment

`lib.Op{Kind, Argv, Fields, Args}` added to CodeFragment, stamped
centrally in the four stage constructors from the emitting process's
own os.Args (one place covers every command — no 28-file sweep this
time). Continuation fragments (empty command) stay Op-less; func
fragments defer to their body fragments' own Ops. The optimiser's new
`pipelineCmdFor` view prefers Op over re-tokenizing the shell-quoted
Command string, with Command parsing kept as the fallback so
older-ssql fragments arriving across an SSH boundary degrade to old
behavior rather than a wrong parse. parsePipelineCmd's per-kind
switch factored into parseCmdFields, shared by both paths.

The slice found a LIVE bug, not a theoretical one: parseCommandArgs
can't represent an embedded single quote, so `generate ssql` on
`where -if name eq O'Brien` produced `-if name eq '"OBrien"'` — a
silently different pipeline (demonstrated by stripping .op with jq).
The Op path renders `'O'\''Brien'` correctly. Pinned three ways:
optimiser-view unit tests (preference proof via garbage Command +
valid Op; fallback; continuation), constructor stamping units, and
an end-to-end regression through the built binary — sabotage-forcing
the fallback reproduces the exact mangling. Fields/Args stay empty
until slice 3 (SQL translator) grows consumers. Ref: DFC123.
