# 2026-W39

## 2026-09-22 (Tue) — DFC134: `-arg` and `-param` decided (design only)

Ross read DFC134 and settled its two grammar questions; nothing built.

**Positionals get a flag form, `-arg VALUE`, in autocli** (Ross's idea; he
first wrote `-argv`, then preferred `-arg`). It appends one positional to
the current clause by arity, so §3.1's proven safety covers positionals
too: `include -arg name -arg -generate`. This replaces my first-draft
proposal to honour `--`, which was wrong three ways: it is a mode switch
(one forgotten `--` reopens the hole), it cannot coexist with `-`/`+`
clause separators, and, found while writing this up, autocli ALREADY
parses `--`: it stops and fills `ctx.RemainingArgs`, which `from ssh` and
`from catalog` use for the push-down pipeline. So DFC134's original "`--`
is not honoured" was imprecise; it is taken. `-arg` is exact-match, so
group-by's `-arg-max`/`-arg-min` are unaffected. The command path stays
bare (closed vocabulary, checked by lookup).

**Expression parameters: `-param NAME TYPE VALUE`**, bound as real expr
env variables (never substituted; my `$rate` spelling is withdrawn),
clause scope (Ross: several exprs can share one clause; matches
`.Local()`), declared type (inferring from spelling would be the `02134`
bug again), name collision with a field is an error, unused param is an
error. In generated Go the parameter becomes a flag of the binary: a true
prepared statement.

Build order recorded in DFC134 §5 and TODO: 5.2 (autocli, then hostile
column names in the equivalence gate and the random tester), 5.3, then
the shell-free runner 5.1. Ref: DFC134.

## 2026-09-22 (Tue) — DFC134 §5.2 built: `-arg` in autocli v4.18.0, and what the ssql half found

autocli v4.18.0 (`ec80307`) adds `-arg VALUE` to every command (see that
repo's journal for the mechanism). ssql's interpreter needed nothing: it
reads parsed positionals. The work here was the other four lanes, and the
method was DFC133's: write a discriminating fixture (`hostile.csv`, columns
`-generate`, `-desc`, `+x`, `-`; shuffled, name order != `-desc` order),

  fused an ascending two-key sort + limit into `top`. The optimiser runs
  ahead of `generate go`, so go-record/typed/parallel AND ssql-opt were

  to understand `-arg` and to fuse only one key / one clause / descending;
  multi-key `sort -desc a b | limit` is no longer fused (top has no
  tie-break).
- `generate sql` silently dropped `-arg` positionals (SELECT name, no ORDER
  BY). `collapseArgFlag` at the single `stageArgs` choke point: benign
  values collapse to the bare form, hostile ones are refused loudly. I did
  NOT teach a dozen translators about `-arg`; the real fix is parsed

  as the value of `-arg`, leaving a dangling `-arg` that failed downstream

  The flag-ARGUMENT case (`-if name eq -generate`) is still dropped: TODO,
  needs arities, ideally autocli hands back a classified argv.

## 2026-09-22 (Tue) — DFC134 §5.3 built: `-param NAME TYPE VALUE`

Expression parameters on `where` and `update`, every lane. The design was
already decided (§5.3); the interesting part was the lowering and what the
equivalence cases dragged out.

**Lowering.** `runtime.Params` is a THUNK (`func() map[string]any`), not a
map: generated programs lift each parameter into a `-param-NAME` flag of
the binary (the `CodeParam` machinery `where -if` and `limit` already
use; extended with `float` and `bool` kinds, time travels as a string and
is parsed at first use), and package-level `var exprFilter1 = …` runs
before `flag.Parse`, so the values must be read lazily. One `paramBinding`
(resolve once; on the first record check no parameter is also a field →
`*ParamCollisionError`, which where/update exec treat as fatal, not
per-row) sits behind `CompileExprParams`, the `…Env…` Tier-V forms, and
the interpreter. The native transpiler gets `params` resolved BEFORE
fields: a collision is `exprLoudError`, a time parameter refuses quietly
so the expression takes the VM tier. `generate sql` renders a literal by
declared type via a package var set for one `exprToSQLParams` call
(same convention as `sqlDialectCur`); the argv-walking translators
pre-scan `-param` triples per clause with `sqlClauseParams`. Result: a
compiled `./report -param-since 2026-06-01` re-runs with new values, a
prepared statement in the full sense.

**Five pre-existing defects found, none about parameters** (DFC134
§5.3a): (1) a malformed CSV row (bare `"`, ragged row) ended
`ReadCSVFromReader` silently with exit 0, found because my injection
fixture had a bare quote and "nothing matched"; (2) `generate sql` update
lost first-match-wins for a field set only in a later clause (`- -set y
9` applied to every row) — CASE per field now carries NOT(earlier) only
where an earlier clause did not set the field, so simple if/else SQL is
unchanged; (3)(4)(5) three copies of one table: record codegen's
`capitalizeFieldType` lacked `time` (→ FieldTypeAuto), the SQL `from`
translator's flag-arity table said `-type` takes one argument (→ `time`
read as a file), typed's CSV `decodeTime` accepted RFC 3339 only. All
three surfaced from ONE equivalence case, `from csv -type date time |
where -if-expr 'date >= since' -param since time …`. DFC115 restated as
a bug class: every copy of a command's grammar drifts on its own.

Also noticed, not fixed: exec and record infer an RFC 3339 CSV column as
STRING while typed infers `time.Time` (typed's own inference), so `ts >
since` with a time parameter matches in typed and errors per row in exec
unless `-type ts time` is given. Pre-existing lane divergence; TODO.

Tests: `runtime/params_test.go`, `commands/expr_param_test.go`,
equivalence `param_float_int_where`, `param_string_attack_is_data`
(§3.3's attack string as a value, through DuckDB too),
`param_clause_scope_update`, `param_time_where`,
`from_csv_type_time_all_lanes`; `TestReadCSVFromReaderMalformedRowIsLoud`,
`TestUpdateFirstMatchWinsGuards`. Sabotage: removing the SQL param
rendering fails all four param cases in the duckdb lane. Docs:
EXPRESSIONS "Parameters" section, codelab, troubleshooting Issue 12,
CHANGELOG. Not done: group-by's aggregation expressions (own compile
path; TODO). Ref: DFC134.

## 2026-09-22 (Tue) — DFC134 §5.1 built: `ssql run`, the shell-free runner

The last of the three units, and the one that turns §2's observation into
a guarantee: a program writes the pipeline as argv (a JSON list of
stages, each a list of strings) and `ssql run` execs the stages directly,
wired with pipes. No shell, so no grammar between the value and the
command's argument list.

Two design choices worth remembering. (1) Validation asks the parser:
autocli v4.19.0 grew `Command.Check(args)`, Execute's walk and validation
with no handler, and the runner checks every stage (nested ones included)
before starting any, naming the failing stage. The runner holds no table
of commands or flags. (2) Execution reuses serve's chain: `startStageChain`
is now a thin wrapper over a shared `startChain` (the os.Pipe discipline
and shell wait semantics that TestServeExecuteEarlyExit pins); nested
pipelines are their own chain writing into a pipe whose read end the
stage gets as `/dev/fd/3+k` through `ExtraFiles`. Process substitution,
no shell. A list of strings where a nested pipeline goes is the one-stage
shorthand (my own first fixture made that mistake, so it is allowed);
numbers are refused with a hint (typing by JSON kind would be a second
type system). `serve -readonly` refuses `run` since it cannot see inside
the file.

Oracle for TestRunDocument: the document's own `run -print` rendering,
run by bash, must produce byte-identical output; on a hostile fixture with
a nested join and a `-param` attack string it does. Also pinned: -check
refuses before a sink runs, failing stage named, early exit not a failure,
SSQL_MODE passes through.

Verification note for future me: `GOFLAGS=-modfile=…` is NOT a way to test
ssql against a local autocli; it leaks into every scratch module the tests
build (generated programs, Go codelabs) and they all fail to resolve
modules. A temporary `replace` in go.mod, reverted before commit, is the
only clean way until the tag exists. Codelab §9 "Pipelines from programs"
added (its first join example self-joined employees.csv and hit the
field-collision error; orders⋈customers now). Ref: DFC134.

## 2026-09-22 (Tue) — `generate json`: text → document, and a gate-run lesson

Ross, mid-release: "do we have a `ssql generate json` so we can create a
json file to use with ssql run?" We did not; it was the §5.5 gap. Built
before tagging: `generate json` reads the fragments and emits one stage
per line from each fragment's `Op.Argv` (the stage's own argv; never
parsed shell text). A func fragment (process substitution) becomes the
nested pipeline in the `/dev/fd` argument it fed; a func fragment with NO
`/dev/fd` in the argv is how `join customers.csv` reads a direct file, so
the argv wins and the file name stays (the codelab caught this: my first
rule errored on it). A fragment without an `Op` (older ssql over SSH) is
refused. Round trip document → `run -print` → shell → `generate json` is
byte-identical on the hostile fixture with a nested join and a `-param`
attack string; pinned in TestRunDocument.

Lesson, logged so I do not repeat it: I bumped `version.txt` and rebuilt
`~/go/bin/ssql` WHILE the pre-tag gates were running. Every test that
compiles generated code "against the released module at this binary's
version" then asked the proxy for v4.104.0, which did not exist, and
seven tests failed for that one reason. The checklist order (gates, THEN
bump) exists for exactly this; and the tree must be left alone during a
gate run. Reverted, re-running clean.

## 2026-09-22 (Tue) — the injection fuzz: "can we create safe SQL from our json?"

Ross asked whether a document plus `generate sql` gives safe SQL. The
honest answer was "the property rests on three quoting functions and
DFC134 §6 asked for a fuzz of them", so: built the fuzz. The random
tester (DFC133 instrument 3) now draws `randHostile` (apostrophes,
`'; DROP TABLE t; --`, `x' OR '1'='1`, comment markers, `;`, `%`, `_`,
`\`, `"`, `a,b`, `$1`, `NULL`) as cell values and in every literal slot
(`-if`, `-set`, and a new `-if-expr … -param who string V` form), and
`randHostileNames` (`select`, `from`, `x-y`, `a.b`, `1st`, `ünï`) for
the string column; the table writer uses encoding/csv so hostile cells
are quoted. Plus one equivalence case, `sql_injection_strings_are_data`,
in every lane.

Four defects on the first run, all "a value or name mis-rendered", none
"a value became a statement":
1. `quoteIdent` quoted only ` -./` and reserved words: `1st` went bare
   and `SELECT 1st` is the literal 1 aliased `st`. Now: quote anything
   not `^[A-Za-z_][A-Za-z0-9_]*$`.
2. `FROM 'file.csv'` lets DuckDB sniff the dialect, and it picked `'` as
   the quote character when a cell contained one, merging two rows into
   one. Now `read_csv(f, header=true, quote='"', escape='"', delim=…)`
   (`duckReadCSV`), single file, multi-file and `-last` alike; types are
   still inferred.
3. `escapeLike` backslash-escaped `%`/`_` but no `ESCAPE` clause was
   emitted, and DuckDB has no default escape character, so `contains '%'`
   matched a literal backslash. Now `ESCAPE '\'`, and a backslash in the
   value is escaped first.
4. From the equivalence case, not the fuzz: the generated Go program's
   header repeats the pipeline in a `/* … */` comment; a `-set` value
   `fine */` ended it and the rest compiled as code. `commentSafe` splits
   the sequence (header and optimiser HeaderNote).

Two generator artefacts fixed along the way (a string column whose only
value is `12` is an int column to both engines; whitespace-only cells
are trimmed by ssql and not by DuckDB, a pre-existing reader difference,
now in TODO). After the fixes: 6,500 pipelines over four seeds, zero
disagreements. The claim in DFC134 §6 is now: yes, and the property
rests on `escapeSQL`, `quoteIdent`, `quoteFile` and `escapeLike`, which
the fuzz exercises at volume. Ref: DFC134.

## 2026-09-22 (Tue) — DFC135 built: `-if-field`, `-set-field`, `-param-field`

Ross asked what we decided about `-if x eq y` with both sides fields.
DFC101 (June) had picked an `@field` sigil; today's DFC134 rule ("a
slot's kind is fixed by the flag, never by the value's spelling") makes
the sigil an injection: `-if token eq "$INPUT"` with INPUT=`@token` is
always true. DFC135 replaces it with a flag per slot; Ross asked whether
the win is just completion (for `-if-field`/`-set-field`, honestly yes;
`-param-field` is the one expressions cannot replace), reviewed the doc,
and said build all three.

Shape: `ssql.FieldOp` / `ssql.CopyField` in the root package serve exec
and record codegen (one semantics, readable generated code); typed
compares struct fields natively via `fieldCondTypedGo`, falling back to
record when the pairing has no native form; SQL renders the columns with
portable string-operator forms (`strpos`, `left`/`right`+`length`) and
the dialect's regex. `-param-field` extends `-param`: one namespace,
`runtime.FieldParams` bound per row and cast strictly, typed mode binds
the struct field (or a `MustCast`), record mode leaves it to the VM tier
because absence is a runtime property, SQL renders the column with a
`CAST` when the declared type differs from `sqlColumnKinds`. Field params
do not lift to a flag of the binary (they are the program's shape).

Four pre-existing defects fell out (DFC135 §9): exec `update` zero-filling
a new field on unmatched rows (record left it absent, SQL refused);
`generate sql` ignoring an `-if-expr` written after its `-set`;
`generate ssql`'s where rewrites dropping any flag their structured view
does not model (the canonicaliser rewrote `-if-expr 'k >= "b"'
-param-field k string 1st` to `-if k ge b`; `whereHasNegationFlags` now
means "anything but -if/-if-expr/+"); and, from the random tester, an
absent `-param-field` column comparing as nil (`l != r` true vs SQL's
NULL false), fixed with `runtime.ErrAbsent` = "no value": condition
false, set nothing, quietly.

Gates: nine equivalence cases (`pairs.csv`, `pairs_absent.csv`),
sabotage-checked; `@name`/`@@name` literal in the injection test; random
tester draws `-if-field` and `-param-field`, 6,000 pipelines agree.
Ref: DFC135.

Addendum: the crash sweep then found that exec `update` never validated
the fields its conditions READ (`-if nosuchfield eq 1` matched nothing,
exit 0; pre-existing), and that `where` skipped a clause holding only
`-param-field` before parsing it. Both loud now; the sweep's
create-a-field exemption became per argument (`-set-field`'s target may
be new, its source must exist).

## 2026-09-23 (Wed) — mixed-kind `-if` comparisons: loud in every lane

Ross asked for the existing situation and options. Measured before
answering (the probe had to be redone: piping stderr into the fragment
stream garbled two lanes): `where -if age gt abc` on a numeric age was
silently false in exec, silently WRONG in record codegen (`ParseFloat64
("abc")` = 0, so it filtered `age > 0` and returned every row), loud in
typed codegen and DuckDB. Three behaviours, and the equivalence gate had
never had a case. Options: loud everywhere; silent-false made consistent;
text fallback (the `top`-by-string class). Ross: option 1.

Built as one rule, stated once: the operand's kind is the field's kind,
a literal not of that kind is a `*ssql.CompareError`, not a coercion.
`ssql.LiteralOp` (literal RHS) and `FieldOp` (field RHS, now loud on
mixed kinds too) serve exec and generated record code; the commands'
compareEqual/Greater/Less/Contains/Pattern family is gone. Record codegen
validates the literal at generation even when it lifts to a flag, guards
the flag at runtime with `MustNumber`/`MustBool` (so `./prog -age-gt abc`
is loud), and with no advisory type emits `ssql.CompareLiteral` instead of
guessing the kind from the literal's spelling. Kept: a fractional literal
on an int column is a number comparison; a numeric-looking literal on a
text column is text; an empty literal against a non-text field is false
(`-if n eq ''` stays expressible). `TestMixedKindComparisonsAreLoud`
covers exec/record/typed for eight loud shapes and four valid ones;
sabotaging LiteralOp to silent-false fails four of them.

Found on the way, fixed: a generated record program with `to csv` failed
on ANY empty result ("failed to read CSV headers: file already closed"):
`WriteCSVToWriter` materialised the source for the header and, with zero
records, fell back to iterating the original sequence again, whose file
was closed. Every empty-result generated CSV pipeline had this.

## 2026-09-23 (Wed) — column order: one rule, every lane, gate-checked

Ross: "why the field order change?" (a typed-mode run of the codelab
pipeline printed `delta temp ts` where exec printed `ts temp delta`).
The typed lane had fallen back to record mode at `update` (a nullable
*float64 from `window -lag`), and the record lane's output was ALWAYS
alphabetical: three separate sorts hid behind exec's `_schema` header.
`readRows` sorted the CSV header into its schema; `MutableRecord` was a
plain map so `Freeze` (= `NewRecord(map)`) sorted keys on every
mutation; `WriteCSVToWriter` sorted the union of names. The equivalence
gate normalised column order away, so none of it was ever a failure.

Fixed at the root: `MutableRecord` carries an insertion-order list shared
like its map (`put` is the ONE write; `Delete`/`Rename` keep it);
`Freeze` builds the schema in that order; `ToMutable` seeds it from the
record's schema; the CSV reader keeps header order; the writers merge
orders positionally (`columnOrder`: a field first seen on a later row
goes after its predecessor there, so `window -lag`'s column on row 2
lands where the stage put it); `ssql.Project(r, fields...)` is the one
`include` primitive for exec and record codegen, in argument order, and
typed's projection now names fields in argument order too; joins put
left's columns then right's new ones; `ssql.AggregateOrdered` /
`NamedAgg` / `RollupConfig.Ordered` carry group-by result order and the
map forms emit sorted. The gate gained a column-order comparison
(`equivColumnOrder`, positional union of JSONL key order, over the
columns both lanes have) and the DuckDB lane stopped re-marshalling
through Go maps (which sorted its keys: a harness artefact).

The gate then found a real split: exec/record/typed ordered group-by
results by the aggregate REGISTRY (`-count` first whatever you typed),
SQL by the command line. Command-line order wins: `resultOrder` recovers
the typed interleaving from argv with the subcommand's declared arities
(autocli keeps per-flag order, not cross-flag), and parseGroupBySpecs
sorts each bucket by it (built-ins as typed, then -expr, then
-stream-expr; SQL refuses -expr so the buckets never interleave there).
Whole gate green with order checked; sabotaging Freeze back to sorted
keys fails it. Pre-existing `OutputRecordFields` (a group-by-only patch
feeding `to table`) is subsumed and left in place.

Addendum: the full suite found one defect the change introduced. Both
JSON-array readers (`ssql.ReadJSON` and `lib.ReadJSON`) iterate a decoded
Go map into the record; with insertion order now kept, the map's random
order showed through (`TestNullInFirstRecordSurvives` flaked 3 in 20).
Both sort keys now, as the old sorted Freeze had it in effect; the
source-order TODO for JSON input stays open. `window`'s result assembly
walked a map too and now follows spec order. Rule for future me: any
`for k, v := range someMap { m.put(k, v) }` is now a nondeterministic
column order; iterate a declared order or sort.

## 2026-09-26 (Fri) — DFC137 §3 built: `except` and `intersect`

Shape: `ssql from a.csv | ssql except -file b.csv` (whole row, SQL

1. **`RecordKey` had been order-dependent since v4.107.0.** Its comment
   said "schema fields are sorted"; the column-order work made schemas

   ordered headers keyed apart, and `union`/`distinct` stopped

   fixture had a reordered header. The `setops_right.csv` fixture

2. **`generate sql` matched `union` columns by position** (SQL's rule),

## 2026-09-27 (Sat) — DFC137 §2 built: ASOF join

"lets do ASOF". A mode on `join`, as agreed: `-asof FIELD` /
`-asof-on L R`, `-after`, `-strict`, `-tolerance` (duration or
number), `-type inner|left`, the equality part optional. Library
`ssql.AsofJoin(right, AsofConfig)`: index the right side per key
sorted by time, binary-search per left row — so the left streams in
INPUT order (output in left order, like every other join) and the DFC's
merge walk with its sort of both sides was not needed. Time axis is
int64 nanoseconds (exact) or float64; ties take the last in input
order in both directions. typed: `AsofJoin` / `AsofJoinParallel` (index
built once, shards probe; the key accessors reuse `typedSetOpKeys`,
the merged struct `mergeJoinSchemas`). SQL: DuckDB `ASOF [LEFT] JOIN`
with `__r.* EXCLUDE (same-named key, time)` and tolerance as a WHERE on
the matched distance; other dialects refuse. Six equivalence cases
(backward, left, forward+strict through a `<(… | where)>`, numeric
tolerance, no key with `-asof-on`, a time axis with a duration
tolerance), hand goldens, DuckDB agreeing; watched five of them fail
with the backward search sabotaged. Codelab §5: `alarms.csv` against
`sensor.csv` (new fixture, embedded).

## 2026-09-29 (Mon) — `run -check` checks fields (DFC138 §4a)

Ross: "lets build the field check now — part of -check". Built by
asking the commands rather than tabulating field slots: the source
runs under `SSQL_MODE=schema` for its typed header, every later stage
runs in exec mode on that header ALONE, so the command's own
validation refuses a field it reads that is not there and its output
header (with the fields it creates) feeds the next stage. No
per-command knowledge; `update -set new 1` is legal because update
says so — a `FieldsFromFlag` table would have flagged it. Nested
pipelines first; stop at sinks/tee and where a header is not known.

Two things fell out. `where` and `update` validated field names against
the FIRST RECORD, so on a header alone a typo sailed through; both now
check the header up front (and fail before reading a row). And `from
csv -type amountt float` was accepted silently by exec itself (the
override never applied); `from csv`/`from tsv` now refuse a `-type`
column the header lacks. `TestRunCheckFields` pins nine documents plus
"writes no sink file" and "ignores an inherited SSQL_MODE".
