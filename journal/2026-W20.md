# Week 20, 2026

The autocli-shell stack landed end-to-end this week. Three new
modules shipped — autocli v4.5.0, autocli/shell v0.1.1, autocli/ssh
v0.1.0 — and then `ssql serve` (v4.44.0) lit them up against a
real-world consumer: load a CSV once, ssh in, run commands against
the live in-memory dataset with no per-query startup cost.

## 2026-05-12 (Tuesday)

### Phase A — autocli engine split (commit 6b80e64, autocli v4.5.0)

Surfaced two new public APIs in autocli core:

- `Command.Complete(args, pos) ([]string, error)` — pure completion
  engine, side-effect free, safe to call concurrently. The bash
  `-complete N` flow becomes a thin wrapper.
- `Command.ExecuteWith(args, base *Context) error` — dispatch with
  caller-supplied IO/State/Ctx. `Execute(args)` keeps working as a
  wrapper that uses os.* defaults.
- `Context.Stdin/Stdout/Stderr/Ctx` accessors + matching
  `Set*` setters + a `State any` pass-through field.

Zero-value Context still returns os.* — bash CLI path unchanged.
Foundation for shell/ssh embedding.

### Phase B — autocli/shell readline driver (commit dcfd19a, autocli/shell v0.1.1)

Sub-module (own go.mod) so autocli core stays stdlib-only. Drives an
autocli Command from a chzyer/readline loop — TAB calls Complete,
Enter parses+runs ExecuteWith. Built-in `:` commands (`:help`,
`:exit`, `:set vi`/`:set emacs`). Shell-style tokeniser with
single/double quotes + backslash escapes.

**Path resolution snag**: Go's module resolution for sub-modules
under a `/vN` parent expects the filesystem layout to mirror the
module path (so `.../v4/shell` requires `v4/shell/` on disk).
Since our sub-module lives at `shell/`, dropped `/v4` from its
path. Sub-module is `github.com/rosscartlidge/autocli/shell` (v0);
parent stays `github.com/rosscartlidge/autocli/v4`.

**Library race**: `chzyer/readline.SetVimMode` races with its own
input goroutine (library bug, not ours). Worked around by deferring
runtime `:set` mode changes until the next session; bookkeeping
updates immediately so per-user prefs persistence still works.

### Phase C — autocli/ssh server (commit 392a63f, autocli/ssh v0.1.0)

Wraps `golang.org/x/crypto/ssh` around autocli/shell. Service
authors add ~20 lines of glue and get the router-style SSH-CLI
deployment pattern.

- `Serve(ctx, cli, opts)` + `ServeListener(ctx, ln, cli, opts)`
- ed25519 host-key load-or-generate (0600, sshd-shape)
- OpenSSH `authorized_keys` parsing
- `AuthCallback` override for key↔username binding / LDAP / etc.
- Refuse-to-start safety: empty/missing auth config errors before binding
- `ConnMeta` with claimed username + pubkey fingerprint for audit
- Graceful shutdown via ctx + configurable GraceTimeout

5 in-process integration tests using crypto/ssh client side.
Race-detector clean across 10 consecutive runs (one occasional
flake matches the chzyer/readline race documented in shell/).

## 2026-05-13 (Wednesday)

### Phase D — `ssql serve` (commit b07ef38, ssql v4.44.0)

The first real consumer of the autocli-shell stack. Loads a dataset
(CSV/TSV/JSON/JSONL) once at startup into a `[]ssql.Record`, exposes
small command tree to SSH sessions:

- `status` — uptime, dataset path, row count
- `schema` — field/type list
- `count` — row count
- `head [-n N] [-t]` — first N rows as JSONL or table

Each session's handlers read from `ctx.State.(*serveState)` and
write to `ctx.Stdout()` (the SSH channel). No per-query startup
cost — the dataset stays mmap'd in process memory across all
sessions and all queries.

Build-tag gated: `serve.go` has `!slim`, `serve_slim.go` registers
a stub that errors clearly when invoked in a slim build. WASM /
WebVM playgrounds keep working unchanged.

**Smoke test against 5-row CSV on loopback**: ssh in with normal
key, run `status` / `schema` / `count` / `head` / `head -t -n 2`,
all return expected output. Multi-command sessions work
(commands flow through stdin sequentially). Welcome banner displays
correctly.

**Sneaky bug**: autocli `Int()` flag values come back as `int`, but
my Default was `int64(10)` to satisfy the builder signature. Type
assertion `.(int64)` failed on the parsed value (which arrived as
`int`), so `-n 3` silently fell through to the default cap-to-all
branch. Fixed with a type-switch handling both.

### Open follow-ups (post-v4.44.0)

- **chzyer/readline race**: send upstream PR (1-2 hours) or
  fork. Currently worked around by deferring runtime mode switch.
- **Window-size propagation**: autocli/ssh doesn't yet pass
  ssh window-change events through to readline's `SetSize`. Lines
  wrap at 80 cols regardless of operator's terminal width.
- **`ssql serve` pipelines**: Position 2 (`io.Pipe` between stages)
  is the natural next step for autocli/shell, which unlocks
  `from-loaded | where | to table` in serve sessions. See the
  pipes/composition section of `autocli-shell-proposal.md`.
- **Per-user history**: `Options.HistoryDir` plumbing exists in
  autocli/ssh; just needs ssql serve to expose a CLI flag.
- **Schema-aware completion**: TAB on `head -if <TAB>` should
  complete loaded field names. Requires the same FieldCompleter
  ssql commands use today against files, pointed at the in-memory
  dataset instead. Small fragment-completer registration.

## 2026-05-14 (Thursday)

User started kicking the tyres on `ssql serve`. Five real-world
issues surfaced in rapid succession, each fixable in <30 minutes,
shipped together as v4.44.1 + autocli stack bump.

### Polish wave triggered by hands-on testing

1. **CRLF for SSH-PTY sessions** (autocli/ssh v0.1.2 → 0948bf1).
   SSH-PTY puts the client's terminal in raw mode; bare `\n` from
   our handlers walked the cursor down without returning to column
   0, producing staircase output (`:help` showed each line one
   indent further to the right). Fix: wrap the SSH channel in a
   `crlfWriter` that translates `\n` → `\r\n` while preserving any
   pre-existing `\r\n`. 7 unit tests; existing readline-managed
   prompt output unaffected.

2. **gpu binary drifted from ssql** (ssql 775bcef +
   `make install-local`). User noticed `ssql_gpu version` reported
   v4.32.0 while `ssql version` reported v4.44.0 — gpu was ~6
   releases behind. Root cause: `make build-gpu` builds to
   `./ssql_gpu` in the repo root, not into `$GOPATH/bin` where the
   developer's shell looks. Every release I'd ticked "make
   build-gpu and test" thinking I'd updated the install, but
   actually only the local repo copy. New `make install-local`
   target builds both ssql + ssql_gpu and copies BOTH into
   `$GOPATH/bin`, printing both `version` outputs at the end so
   mismatches are visible at release time. CLAUDE.md Post-Release
   Checklist updated to replace `make build-gpu` with this.

3. **autocli v4.6.0 — fix-loudly + embedded help** (ba95b34).
   Typing `junk` at the serve prompt dumped a full bash-flavoured
   help screen with `eval $(serve -completion-script)` references
   that mean nothing inside an SSH session. Two changes:
   `Command.GenerateHelpEmbedded()` strips the SHELL COMPLETION +
   `-man` footers from the help text; `ErrUnknownCommand` is now
   returned from `ExecuteWith` instead of silently falling through
   to a help dump. The bash CLI path keeps working (existing
   callers either get exit-1 with a clear message — improvement —
   or catch the error explicitly).

4. **shell v0.1.2 — intercept -help, friendly unknown msg**
   (4c45fb3). Layers on the autocli v4.6.0 changes: intercepts
   `-help` / `--help` / `-h` / `help` / `?` at the shell loop to
   emit `GenerateHelpEmbedded()` directly; catches
   `ErrUnknownCommand` to print "unknown command: 'X' (try -help
   or :help)" instead of leaking autocli's bash-flavoured help.
   `:help` built-in now scoped honestly to shell built-ins and
   points operators at `-help` / `<command> -help` / TAB for the
   service command tree. Two new tests prove both paths.

5. **Force-close active sessions on ctx-cancel** (autocli/ssh
   v0.1.4 → 16a9c8b). User reported Ctrl-C didn't kill `ssql
   serve` when an SSH session was open. Chain: SIGINT → cancel()
   fires → Accept unblocks → but `serveListener` then waits up to
   `GraceTimeout` (5s default) for in-flight sessions; each
   session is blocked in `readline.Readline()` which only checks
   ctx between lines. Net effect: 5-second Ctrl-C delay.

   Fix: `connTracker` — every accepted `*gossh.ServerConn` is
   registered; on ctx.Done(), the watcher goroutine force-closes
   them all. Readline sees EOF, shell.Serve's loop breaks, the
   session goroutine returns, `wg.Wait()` falls through in
   milliseconds. New `TestServe_ShutdownForceClosesActiveSession`
   measures <1s shutdown with default 5s GraceTimeout — a
   regression to the wait-for-sessions behaviour would fail it.
   Race-detector clean. Sessions disconnect immediately, which
   for an interactive operator console is what users want;
   callers that need the old graceful-grace-period behaviour
   (database admin shells with mid-tx cleanup) can later opt-in
   via a `ForceCloseOnShutdown=false` option.

6. **`to table` subcommand on `ssql serve`** (part of v4.44.1).
   User pointed out the obvious gap — sink-symmetric with the
   regular ssql CLI's `to table`. Renders the loaded dataset as a
   fixed-width text table. Default prints all rows; `-n N` caps.
   Sits alongside the pre-existing `head -t` (which previews the
   first N as a table). Same `renderTableTo` helper, different
   subcommand wrapper.

### Thursday evening — completion bugs + persistence (v4.44.2)

The user kept testing after v4.44.1 shipped and three more rough
edges showed up. All small, all from the same hands-on-testing
feedback loop.

**Completion bugs** (autocli v4.6.1, shell/v0.1.3, ssql go.mod
bump — no ssql tag, dep-only).

1. `-h<TAB>` at the prompt didn't complete to `-help`. The leaf-
   level completer (used after a subcommand name has been typed)
   already included `-help / --help / -h / -man / -completion-
   script`, but the ROOT-level completer (`completeRootGlobalFlags`)
   only walked user-declared globals. Asymmetric. Fixed by adding
   the same built-in set at the root.

2. `to <TAB>` echoed `to` instead of suggesting child subcommand
   `table`. Cause was in autocli/shell's `autocliCompleter.Do`:
   when the prefix ends in whitespace the user is starting a new
   word, and bash's COMP_WORDS protocol adds an empty entry at
   the cursor. Our completer wasn't doing that — it told autocli
   "user is on word #1, typed 'to'" rather than "user is on word
   #2, typed nothing yet". Fix: append "" to args when prefix
   ends in space/tab.

Both got dedicated regression tests.

**`:set vi/emacs` persistence** (shell/v0.1.4, ssh/v0.1.6,
ssql v4.44.2 + `-session-dir` flag).

The user typed `:set vi`, disconnected, reconnected, and `:set`
showed emacs again. They asked "so this is a bug in chzyer/
readline?" — the right framing surfaced the issue cleanly:

- chzyer/readline IS buggy: `SetVimMode` races with its own input
  goroutine. That's why I can't just call it mid-session. It's
  also why I wrote a "(takes effect on next session)" workaround
  in builtins.go.

- But MY workaround was incomplete. The "next session" half —
  actually persisting the choice — was documented in the
  proposal but never coded. Next session re-read the autocli/ssh-
  level default (emacs) and there was no file to override it.
  Net result: `:set vi` was functionally a no-op. The bookkeeping
  printed "vi", but readline stayed in emacs, and the next
  session was the same.

Fix delivered as designed in the autocli-shell proposal:

- `shell.Options.PrefsFile string` — empty = in-memory only,
  non-empty = read on session start, write on `:set`. JSON file
  with a flat schema (just `editing_mode` today; room for more).
  Atomic save via tmp + rename, 0600 perms. Corrupt/missing
  files fall back silently.

- `autocli/ssh` wires per-user prefs path when `HistoryDir` is
  set: `$HistoryDir/$user/prefs.json` alongside the existing
  `$HistoryDir/$user/history`. Empty `HistoryDir` keeps the
  old in-memory-only behaviour.

- `ssql serve -session-dir DIR` is the user-facing knob.
  Default empty (opt-in, no change to existing deployments).

Mid-session switch is still blocked on the chzyer/readline race
— operators have to `:exit` and reconnect for the new mode to
take effect. The `:set` builtin now prints "(saved — takes
effect on next session)" honestly: prefs.json actually gets
written.

Smoke-tested end-to-end: alice `:set vi`, exit, reconnect →
`:set` shows vi, prefs.json contains `{"editing_mode": "vi"}`.
charlie connects fresh → defaults to emacs, his prefs dir has
just `history` (no prefs.json yet). Per-user isolation working.

7 new tests for prefs load/save/atomicity/permissions/corruption
+ end-to-end :set → file → next-session round-trip.
