# Journal 2026-W41

## 2026-10-06 (Tue) — Library mode: `generate go -package` (DFC142 §5a)

The service-integration work's second half. Three Explore surveys
(record assembler, typed assembler + planner, generate go command +
test harness) fixed the design before any code: `package main` is
hardcoded in exactly two places, `writeMainCallingRun` is the one
skeleton writer, params are one `CodeParam` list rendered by `flagDecl`,
sinks are `final` fragments written verbatim, `rightSourceN()` is an
existing "pipeline as a function returning a sequence". Ross's two
further choices in plan mode: v1 is the **serial typed plan** (the input
is an `iter.Seq` the caller owns, not a file the planner can shard;
parallel library form is the follow-up — he flagged mid-session that
the loss of parallelism will matter; program mode is untouched) and
**type names are prefixed with the function name** so two pipelines over
one file share a package.

**Step 0, LazyTee.** Its broadcast `select` had a `default:` that dropped
the value for any consumer whose 100-slot buffer was full. Test with a
fast and a slow consumer over 1,000 values failed as 201/150; branch
removed, send blocks. `go test -race` green.

**Step 1, stage code never exits.** The typed survey found three stages
calling `os.Exit(1)` inside closures; a scan (`TestStageCodeNeverExits`,
`cmd/ssql/stage_exit_test.go`: run ten stage families in both modes,
assert no non-final fragment's Code contains `os.Exit(`) found **twenty**
emitters — every side-file read (join, union, merge, set-ops), the
sampled/Parquet/XLSX/WAV/SSH/catalog sources, the four signal commands,
resample, extract, update. Init-level ones now `return fmt.Errorf(…)`
from `run()` (the shape `from csv` already used — half of `from_xlsx`
and `from_wav` had been converted, the other branch not); closure-level
ones `panic(fmt.Errorf(…))`. Behaviour under `main()` is identical
(`ssql.Run` prints `Error:` and exits 1); inside a library `Safely`
delivers it. Bonus bugs: fft/ifft/convolve/correlate/spectrogram and the
typed `to table FIELDS` sink emitted `ctx.Stderr()`/`ctx.Stdout()`,
which do not exist in a generated program (corpus case
`to_table_selected_fields` watched to fail with `undefined: ctx`).

**Steps 2-5, the assembler.** `lib.AssembleOptions{Package, Func}`,
`AssembleCodeFragmentsWith`; `assembleLibrary` in
`cmd/ssql/lib/codefragment_library.go` is one skeleton for record and
typed fragments. Decisions worth remembering: (1) type prefixing is done
in the assembler by rewriting every `type X struct` name on word
boundaries, longest first — no env var to the stage processes, so it
works for stdin fragments and through the optimiser's re-exec; (2) the
params struct binds `flagX := &p.Field; _ = flagX` so stage code written
against `*flagX` compiles unchanged — the "second renderer of the one
list" DFC142 asked for, no per-command change; (3) subprocess functions
(`rightSourceN`) take `p` and the stmt call is rewritten `rightSource1(p)`;
(4) imports are pruned against the emitted text, because a stage that
listed `os` for an error path that is now a panic would otherwise fail
the build; (5) typed sources are downgraded to `AltCodeIfSeq` before the
planner runs, so phase 1 swaps every stage to its serial form and the
`.Serial()` case cannot arise (asserted). `-package` refuses `-run`/`-build`
(nothing to run); `-func` without `-package` is an error; the optimiser's
inner `generate go +O` gets both flags.

**The driver found a real gap.** The first compile-and-run test compared
the library's rows with exec and got `{"N":1,"Product":…}` against
`{"n":1,"product":…}`: group-by, join, update, cast, projection,
extract, resample, unpivot and rollup rendered their result structs with
an `ssql` tag only (join with none). The CLI never noticed because
`to jsonl` goes through the typed→Record boundary, which uses the schema
names. Every generated row struct now has `ssql:"x" json:"x"`, so a
service's `json.NewEncoder` prints the pipeline's columns.

**Gates.** `codefragment_library_test.go` (string-level, record + typed
+ refusals + the return→panic adaptation); `TestLibraryMode` (both modes
vs exec through the equivalence canonicaliser, params change the

`goRunGeneratedResult` generalised to `goRunGeneratedModule(files)`.

**Two things the gates found after the first green.** (1) The `go-lib`
lane disagreed on *column order* for every pipeline whose result is
`ssql.Record` (window, describe, cube, spill sorts): the driver printed
rows with `encoding/json`, and `Record.MarshalJSON` sorts keys, while
`to jsonl` writes them in schema order through
`WriteJSONLWithInferredSchemaToWriter`. The driver now picks the writer
by row shape, as the sinks do — a reminder that the lane must use the
sink's writer, not a convenient one. (2) `param_time_where` did not
compile: `where`'s VM thunk (`var exprFilterN =
runtime.MustCompileExprFilterParams(expr, func() … *flagParamSince …)`)
is hoisted to package level (through `StructDefs` in typed mode, through
`Code` in record mode), where a library's parameter bindings — locals of
the function — are out of scope. Any hoisted declaration that reads a
parameter now stays in the body. Also: `generate go … reports/x.go`
creates the directory on demand; the codelab block had failed on it.
