## 2026-10-06 (Tue) — Library mode: `generate go -package` (DFC142 §5a)

The service-integration work's second half. Three Explore surveys
(record assembler, typed assembler + planner, generate go command +
test harness) fixed the design before any code: `package main` is
hardcoded in exactly two places, `writeMainCallingRun` is the one
skeleton writer, params are one `CodeParam` list rendered by `flagDecl`,
sinks are `final` fragments written verbatim, `rightSourceN()` is an
existing "pipeline as a function returning a sequence". Ross's two
further choices in plan mode: v1 is the **serial typed plan** (the input
is an `iter.Seq` the caller owns, not a file the planner can shard;
parallel library form is the follow-up — he flagged mid-session that
the loss of parallelism will matter; program mode is untouched) and
**type names are prefixed with the function name** so two pipelines over
one file share a package.

**Step 0, LazyTee.** Its broadcast `select` had a `default:` that dropped
the value for any consumer whose 100-slot buffer was full. Test with a
fast and a slow consumer over 1,000 values failed as 201/150; branch
removed, send blocks. `go test -race` green.

**Step 1, stage code never exits.** The typed survey found three stages
calling `os.Exit(1)` inside closures; a scan (`TestStageCodeNeverExits`,
`cmd/ssql/stage_exit_test.go`: run ten stage families in both modes,
assert no non-final fragment's Code contains `os.Exit(`) found **twenty**
emitters — every side-file read (join, union, merge, set-ops), the
sampled/Parquet/XLSX/WAV/SSH/catalog sources, the four signal commands,
resample, extract, update. Init-level ones now `return fmt.Errorf(…)`
from `run()` (the shape `from csv` already used — half of `from_xlsx`
and `from_wav` had been converted, the other branch not); closure-level
ones `panic(fmt.Errorf(…))`. Behaviour under `main()` is identical
(`ssql.Run` prints `Error:` and exits 1); inside a library `Safely`
delivers it. Bonus bugs: fft/ifft/convolve/correlate/spectrogram and the
typed `to table FIELDS` sink emitted `ctx.Stderr()`/`ctx.Stdout()`,
which do not exist in a generated program (corpus case
`to_table_selected_fields` watched to fail with `undefined: ctx`).

**Steps 2-5, the assembler.** `lib.AssembleOptions{Package, Func}`,
`AssembleCodeFragmentsWith`; `assembleLibrary` in
`cmd/ssql/lib/codefragment_library.go` is one skeleton for record and
typed fragments. Decisions worth remembering: (1) type prefixing is done
in the assembler by rewriting every `type X struct` name on word
boundaries, longest first — no env var to the stage processes, so it
works for stdin fragments and through the optimiser's re-exec; (2) the
params struct binds `flagX := &p.Field; _ = flagX` so stage code written
against `*flagX` compiles unchanged — the "second renderer of the one
list" DFC142 asked for, no per-command change; (3) subprocess functions
(`rightSourceN`) take `p` and the stmt call is rewritten `rightSource1(p)`;
(4) imports are pruned against the emitted text, because a stage that
listed `os` for an error path that is now a panic would otherwise fail
the build; (5) typed sources are downgraded to `AltCodeIfSeq` before the
planner runs, so phase 1 swaps every stage to its serial form and the
`.Serial()` case cannot arise (asserted). `-package` refuses `-run`/`-build`
(nothing to run); `-func` without `-package` is an error; the optimiser's
inner `generate go +O` gets both flags.

**The driver found a real gap.** The first compile-and-run test compared
the library's rows with exec and got `{"N":1,"Product":…}` against
`{"n":1,"product":…}`: group-by, join, update, cast, projection,
extract, resample, unpivot and rollup rendered their result structs with
an `ssql` tag only (join with none). The CLI never noticed because
`to jsonl` goes through the typed→Record boundary, which uses the schema
names. Every generated row struct now has `ssql:"x" json:"x"`, so a
service's `json.NewEncoder` prints the pipeline's columns.

**Gates.** `codefragment_library_test.go` (string-level, record + typed

`go-lib` lane in `equivLanes()` (generates the library in typed mode,
drives `PipeFromCSV` on the fixture, skips when the source has no reader
form or library mode refuses; inherits `Skip["go-typed"]`).
`goRunGeneratedResult` generalised to `goRunGeneratedModule(files)`.

Docs: CLI codelab §7 "library" block that generates, compiles and runs
a caller (conditional `go mod edit -replace` on `SSQL_MODULE_DIR` so

## 2026-10-06 (Tue) — The parallel library form, the same afternoon

Ross: the serial-only library "will cause significant performance
degradation", so this went straight after the first commit. Design
follows claude/concurrency.md §1: never a channel per row. New
`typed.ParallelBatched(in, n)` — the feeder pulls rows into batches of
1024 and sends each batch once; shards take whole batches
(cooperative) and iterate them in stack code; a source panic is
captured in the feeder and re-raised by the shards; an early stop
releases the feeder through a `stop` channel; batches recycle through
a `sync.Pool`. The library's typed init is now `records :=
typed.ParallelBatched(in, *flagShards)` with `records := in` as its
`AltCodeIfSeq`, so the planner keeps or drops the parallel plan exactly
as it does for a program; a `Shards int` field (0 = every core) appears
in `FParams` only when the parallel source survived planning; a
`Stream` at the end is drained with `.Serial()`. Record mode is
unchanged (it has no parallel form).

**The benchmark lesson.** The first in-memory comparison said
`ParallelBatched` 4.4 s vs `ParallelFromSlice` 0.13 s and I went after
allocation: a `sync.Pool` cut 560 MB/op to 6 MB and the time did not
move. The profile said `chansend` 32% and lock contention, and the
chansend was not the feeder's 10k batch sends — my benchmark copies
inherited the per-row `Parallel` bench's `for range j3.Serial()` sink
(a fan-in channel over 7.25 M rows) while the slice bench counted with
`SerialCount()`. With the same sink: slice 0.13 s, batched in-memory
0.17 s (≈ 4 ns a row for the distributor), per-row 5.3 s, batched fed
by `typed.ReadCSV` 3.4 s (the serial parse bounds it; typed serial end
to end is 5.3 s). Compare distributors with the same sink. The three
new benches stay beside the slice one; the original per-row bench
keeps its `Serial()` sink as the preserved negative result.

Docs: typed-reference (`ParallelBatched` signature, `Parallel` marked
as the per-row ancestor), concurrency.md §1 and §10, library-tour,
typed-codelab, CHANGELOG, DFC142 §8, TODO.

Gates for the parallel form all green (race, doc-check, codelab,
library + equivalence + metamorphic, full cmd/ssql, 12:21–12:38).

## 2026-10-08 (Thu) — DFC144 Batch C built: explode, flatten, dotted paths

Level 2. The whole path feature is one hook: `ssql.Get` (every command's
field read) tries `pathValue` on a `Schema.Index` miss — longest leading
segment that is a field, then keys and 0-based indices through the JSON
text — so `where -if addr.city eq NYC`, `sort addr.zip`, `group-by
addr.city`, `include tags.0` and `to table addr.city` needed no
per-command code beyond their output HEADERS, which is where the three
real fixes were: `include` and `group-by` dropped a path column because
they built the header with `HasField` (the rows had it; the writer
dropped it — the schema-authority rule biting from the other side);
`validateFieldsSchema` got `HasFieldOrPath`; and `flagVarName` made
`flagAddr.cityNe` for a lifted literal. The typed lane cannot resolve a
path (a struct field is the text), so `where`/`sort`/`group-by` fall
back to record mode when a field name is a path into a `json` field.

`explode` and `flatten` are record-shaped stages (the planner inserts
the boundary); both learn their output header from the first row
(`peekFirst`). Decisions made while building, now in the help text:
exploding a non-list is an error (flatten is the verb for an object);
flatten's key set is fixed by the first row's object and a later new
key fails naming it, as a DuckDB STRUCT would, rather than a column that
silently exists for some rows; keys come out in the object's own order
(a tiny decoder scan, since encoding/json's map loses it). `explode` →
DuckDB `unnest` in a `* REPLACE` projection; flatten and `-keep-empty`
refused in SQL by name. Schema mode lists `addr.city: string` from the
first object, so Ctrl-O completes paths. New codelab data `events.jsonl`
and a §3 "Nested JSON" section with four runnable blocks.

## 2026-10-08 (Thu) — DFC145: nested tables (decision record)

Ross, after the release: "what do you think of the idea of having the
only structured data a real jsonl table — which would support real ssql
commands on it?", then "let's write it up in a DFC and update DFC144 to
point to it". DFC145 is the write-up: the idea is the nested relational
model (relation-valued attributes, nest/unnest), which ssql already
half-has (`group-by`'s `_group` sequence field, `-collect`, `explode`,
`flatten`, `DotFlatten`/`CrossFlatten`); the grammar that fits the
philosophy is a `-in FIELD` scope on every row command (one token,
completable, no sub-language; a scoped `sort`/`group-by`/`top` is
row-local and cheap), with `nest FIELD COL…` as flatten's inverse; the
type tier is `table{…}` in the header with `json` as the fallback; the
cost per lane and an order of work are recorded; and "not now": nothing
has asked for it that explode | … | -collect does not express. DFC144's
Level 3, recommendation and related list now point at it.

Then "also do some research on nested relational models and how they
handle the problems": DFC145 §7, seven problems with the literature's
answer, the systems' answer and ssql's position — nest/unnest not being
inverses (RKS 1988's Partitioned Normal Form; Dremel's definition
levels; ssql's `-keep-empty` and the typed `has()` gap); conservativity
(Paredaens–Van Gucht 1988: nesting adds no power for flat results, the
theorem behind building explode/collect before a typed tier, and
Cheney–Lindley–Wadler's shredding for nested results); the three ways to
query inside a value (NF² operators at depth = `-in`; SQL's
unnest/regroup; Spark/DuckDB lambdas = our expressions); the round trip
as a dependent join (Neumann–Kemper 2015) that a row-local scoped
operator never pays; two-tier typing in every real system; sets vs
lists and the 0/1 index split; Dremel's columnar striping as the typed
lane's eventual storage story. Sources listed.

## 2026-10-09 (Thu) — typed codegen for JSON array files; the array-file gate widened

Yesterday's recommendation, built: the typed and library lanes skipped
every array-file equivalence case because `from json FILE.json` had no
typed form (the sampler was JSON Lines only), which is how the
`REPLACE` bug hid for a day. Now:

- **`typed.ReadJSON` / `ReadJSONFromReader` / `ReadJSONParallel`**
  (`typed/json.go`). The serial reader streams elements with
  `encoding/json`'s Decoder (token walk, one `RawMessage` copy per
  element) and decodes each with the JSONL positional plan, so the
  nested-value-as-string contract is the same. An array has no newline
  index to shard on, so the parallel form is one scanner goroutine
  handing batches of raw elements to `n` decoding shards over a channel
  — `ParallelBatched`'s shape applied *before* the decode, which is the
  expensive part. `shardGroup` carries a scanner panic to every shard;
  a `stop` channel releases the scanner on early exit. Errors are
  `*ReadError` with `Row` = 1-based element index.
- **`lib.SampleJSONSchema`** (`typed_schema_jsonl.go`) replaces the
  lines-only sampler: one `observe(obj)` closure folds an object into
  the inference, fed by lines (with the `_schema` header rule) or by
  array elements; it reports `isArray` so `from json` pairs the schema
  with the right reader. `SampleJSONLSchema` stays as a wrapper.
- **`from json` typed emission** picks `ReadJSON`/`ReadJSONParallel`
  for an array file (`-explain` says `typed from json (array)`).
- **Gates:** the two array-file equivalence cases lost their typed/
  parallel Skips and run every Go lane; four more array-file cases
  (`explode_tags_array_file`, `flatten_addr_array_file`,
  `path_in_groupby_array_file`, `groupby_expr_over_lists_array_file`);
  reader unit tests incl. parallel-vs-serial over 5k elements, the bad
  element named, a JSONL file refused, early stop; the sampler test's
  array refusal became an array inference assertion; the scale gate
  derives `big.json` (3M-element array, `scaleGenVersion` 2) and runs
  `generate-go-run-json-array-typed` at the JSONL twin's ceiling.

Gotcha found on the way, recorded in TODO: inside `group-by -expr`,
`sum(X)` is rewritten as "X per row, summed", so a nested closure
`sum(map(scores, sum(#)))` fails with an opaque `map + int` error in
every lane; `len(flatten(scores))` works because `len` is not patched.
Not touched today — the case uses the working spelling.

Measured on the scale fixture (3M rows, 255 MB array / 165 MB JSONL,
24 cores, a count sink, benchtime 2x, alongside other tests so ±10%):

| reader | wall |
|---|---|
| `typed.ReadJSON` (serial) | 3.56 s |
| `typed.ReadJSONParallel` | 2.85 s |
| `typed.ReadJSONLParallel` (the twin) | 1.65 s |

The parallel array reader is scanner-bound: `encoding/json`'s Decoder
runs its full state machine to find each element's end and copies the
bytes into a `RawMessage`, and that single goroutine caps the shards.
The JSONL twin finds boundaries with `bytes.IndexByte` over an mmap.
A depth-and-quote byte scanner over an mmap'd array (the same shape,
`[`/`{` depth counting with string skipping) would make the two twins
equal; noted in TODO. Still: the typed program now runs the group-by
in the scale case in 4.5 s including `go build`, where the record
fallback it replaces was the 14.8 s / 3.9 GB class.
