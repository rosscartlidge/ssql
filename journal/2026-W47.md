## 2026-11-16 (Mon) — FAQ phase 2: the service on the LAN and the tailnet (DFC169 §11)

Ross answered DFC169 §9 and set the reach: the local network and his tailnet, **no Tailscale Funnel yet**. Decisions:
- the FAQ has its own page (the https playground can't call a plain-http LAN address, so answers link into it with `#p=`);
- CLI questions only;
- visitors paste their columns rather than upload;
- questions are logged with no addresses.

`scripts/faq -serve` (`serve.go`, `page.html`, `visitor.go`) serves the page and `POST /api/ask`. The `privateOnly` middleware allows loopback, RFC 1918 and Tailscale's ranges. It also refuses anything carrying `Tailscale-Funnel-Request`, because Funnel arrives over loopback and would otherwise pass an address check. So a stray `tailscale funnel` gives 403s, and going public is a deliberate code change. Questions run one at a time with four queued, and the rest get "busy".

**The jail** (`sandbox.run`, `jailArgs`) chains a `systemd-run --user --scope` (TasksMax, MemoryMax), `prlimit` (fsize, cpu) and `bwrap --unshare-all`, running the slim ssql built from the checkout.

Gotchas:
- `prlimit --nproc` made bwrap fail with "Resource temporarily unavailable". RLIMIT_NPROC counts every process the user owns, so the task cap moved to the cgroup scope, which costs about 15 ms.
- The first jail test found bwrap's root writable (`/run/ssql/x`), which `--remount-ro /` closed.

Every guard was watched failing by sabotage.

Pasted columns become `data.csv`, and verification stops at schema mode when no rows are pasted. A wrong column still comes back with the real ones (DFC170 paying off).

Under the jail with the slim build, the eval is unchanged at 31/33 for gemma4:26b, the same two model-error cases. Live tests over loopback, the LAN address and the tailnet address were all verified in about 3.7 s.

## 2026-11-16 (Mon) — typed codegen and blank text: the FAQ's first real bug report

Ross asked the FAQ a doc question with a sentence in the "paste your columns" box. The failure it logged was a real ssql bug: `generate go` refused `where` on any CSV column with no values (all blank, or a header with no rows): `where on *string field … not supported`.

The typed sampler (`colInfer.resolve`, `cmd/ssql/lib/typed_schema.go`) had inferred such a column as `*string` since typed codegen phase 2, while exec reads it as `string` with `""` values. A probe found the class:
- `where`, `sort`, `-max`, `update -set` and `cast` refused it;
- `to jsonl` wrote `null` where exec writes `""`;
- `fill -default` wrote `<nil>`.

One line fixed all of them: infer `string`.

The new equivalence case then exposed an older silent bug. Typed `group-by` took a blank text cell as a value, so `-min`, `-first`, `-last`, `-any`, `-mode`, `-count-distinct` and `-string-agg` answered `""` (or one distinct too many) where exec and DuckDB skip it. That breaks DFC124's rule that an empty text cell is missing. `presentCond` now treats `""` in a string column as missing, and a `skipMissing` helper guards the map and append aggregates. Window functions already agreed.

Equivalence cases, each watched failing:
- `blank_column_where_and_fill`
- `blank_column_kept_as_empty_string`
- `blank_text_skipped_by_aggregates`
- `header_only_csv_where`

Two gaps are left, named and in TODO:
- **SQL reads an empty text cell as NULL,** so `eq ''` and `ne x` differ from Go (accepted in DFC124 §2; the cases skip the SQL lanes with that reason).
- **A typed group with only blank values gives `""`,** not absent (DFC124 §3).

Gates: `make vet`, doc-check, lib and typed, and the full `cmd/ssql` suite (605 s), all green.
