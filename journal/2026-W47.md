## 2026-11-16 (Mon) — typed codegen and blank text: the FAQ's first real bug report

Ross asked the FAQ a doc question with a sentence in the "paste your columns" box. The failure it logged was a real ssql bug: `generate go` refused `where` on any CSV column with no values (all blank, or a header with no rows): `where on *string field … not supported`.

The typed sampler (`colInfer.resolve`, `cmd/ssql/lib/typed_schema.go`) had inferred such a column as `*string` since typed codegen phase 2, while exec reads it as `string` with `""` values. A probe found the class:
- `where`, `sort`, `-max`, `update -set` and `cast` refused it;
- `to jsonl` wrote `null` where exec writes `""`;
- `fill -default` wrote `<nil>`.

One line fixed all of them: infer `string`.

The new equivalence case then exposed an older silent bug. Typed `group-by` took a blank text cell as a value, so `-min`, `-first`, `-last`, `-any`, `-mode`, `-count-distinct` and `-string-agg` answered `""` (or one distinct too many) where exec and DuckDB skip it. That breaks DFC124's rule that an empty text cell is missing. `presentCond` now treats `""` in a string column as missing, and a `skipMissing` helper guards the map and append aggregates. Window functions already agreed.

Equivalence cases, each watched failing:
- `blank_column_where_and_fill`
- `blank_column_kept_as_empty_string`
- `blank_text_skipped_by_aggregates`
- `header_only_csv_where`

Two gaps are left, named and in TODO:
- **SQL reads an empty text cell as NULL,** so `eq ''` and `ne x` differ from Go (accepted in DFC124 §2; the cases skip the SQL lanes with that reason).
- **A typed group with only blank values gives `""`,** not absent (DFC124 §3).

Gates: `make vet`, doc-check, lib and typed, and the full `cmd/ssql` suite (605 s), all green.

## 2026-11-22 (Sun) — FAQ: a public instance for Tailscale Funnel (DFC169 §12)

Ross wants the FAQ opened through Funnel but was worried about security. Pipeline execution was already well walled: the checker allows ssql stages only, and runs happen in bubblewrap with no network, under systemd-run and prlimit caps. What a public service lacked was everything around that:
- the server ran as Ross, with his home readable;
- nothing limited how much one visitor could use the single GPU;
- the log had no cap;
- a hidden `*.ts.net` name protects nothing, because its certificate is in the Certificate Transparency logs.

**The public instance.** `-public` runs a second instance (`scripts/faq/public.go`) on loopback only, so the forwarded `X-Forwarded-For` can be trusted. I checked in tailscaled's source that Funnel overwrites a client-sent copy. It allows 10 questions per visitor per hour (IPv6 by /64) and 200 per day, with 429 and Retry-After past either. `/api/health` shows the day's answered and refused counts, and the page footer says the FAQ is public. The log is capped at 64 MB with one old generation; that cap applies to both instances.

**Install.** `install-public.sh` stages the committed user docs only, then with sudo creates the `ssql-faq` system user and a root-owned app tree. The hardened user unit is `ssql-faq-public.service`.

**Gotcha:** `ProtectKernelTunables` stops bubblewrap mounting its own `/proc`, so the unit leaves it out. A transient-unit trial as Ross found that before any sudo.

Every guard failed when broken, and a live trial on :8486 verified answers through the jail and gave a 429 on the 4th question. What's left is Ross's: run the sudo install, try it, then `tailscale funnel --bg 8485`. No whole-question deadline exists yet (TODO).
