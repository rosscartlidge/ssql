# 2026-W33

## 2026-08-11 (Tue) — gh-pages playground deploy automated

Closed the long-standing TODO: playground deployment to `gh-pages` is now a
GitHub Actions workflow (`.github/workflows/playground.yml`) instead of the
manual build-on-main / copy-to-/tmp / `git checkout gh-pages` dance we ran by
hand three times last week alone (v4.57–v4.59).

**How it works.** On push to `main` (path-filtered to `**.go`, `go.mod`,
`go.sum`, `cmd/ssql-playground/**`, and the workflow itself — doc-only and
`.deb`-baking pushes don't trigger it) plus `workflow_dispatch`: checkout main,
`make playground` (plain Go `js/wasm` slim build, no TinyGo — CI-friendly),
checkout `gh-pages` into a `ghp/` subdir, copy exactly three files
(`ssql-playground.wasm`, `wasm_exec.js`, `playground.html`), commit and push
only if they changed. Everything else on gh-pages (`data/`, `fs-polyfill.js`,
the gpu demo) stays untouched and remains manually deployed.

**Design notes for future-me:**
- The CI checkout of gh-pages into a subdir sidesteps the shared-working-tree
  gotcha entirely (that hazard only exists locally where both branches share
  one tree). The branch's mirrored `.gitignore` is irrelevant here anyway —
  all three targets are already *tracked* on gh-pages, and ignore rules never
  apply to tracked files.
- `git add` names the three files explicitly (not `-A`), so the workflow can
  never sweep anything unexpected into the branch.
- `permissions: contents: write` with the default `GITHUB_TOKEN` is enough to
  push to gh-pages — no PAT needed (unlike goreleaser's Homebrew-tap push).
- Concurrency group `deploy-playground` with `cancel-in-progress` so a rapid
  push series only deploys the latest.

**Doc updates:** `claude/playground.md` now leads with the automation and
demotes the manual steps to fallback; CLAUDE.md post-release checklist replaces
"update gh-pages branch" with "verify the workflow ran"
(`gh run list --workflow=playground.yml -L 1`); TODO item checked off.

The commit landing this change is itself the live test — it touches the
workflow path, so the first automated deploy fires on push.

## 2026-08-11 (Tue) — `limit 0` = no limit (pass-through dial)

Ross's idea: keep a `limit N` sampling stage permanently in a pipeline and
dial it to `0` for full runs, instead of editing the stage out. So `limit 0`
now passes everything through (previously "limit must be positive"), and in
code generation a zero-valued stage emits NO fragment — it vanishes from
generated go, sql, and ssql alike, since all three generators are
fragment-driven. `offset 0` (already accepted, but it emitted a useless
zero-skip fragment) gets the identical treatment.

Testing per the multi-backend doctrine: `limit_zero_passthrough` equivalence
case (`where | offset 0 | limit 0` with a golden — all lanes incl. DuckDB
must return exactly the where result) plus `TestLimitZeroSkipsGeneration`
(12 subtests pinning no Limit/Offset marker in generated go/sql/ssql across
record+typed modes). Both gates watched failing under deliberate sabotage
(re-enabled fragment emission → 6 leak failures + equivalence divergence,
because generated code then ran `Limit(0)` = zero rows). Bonus lesson: the
generation test's first version failed on its own fixture *filename*
containing "limit" — reject-substring oracles need token-ish patterns.

Docs: codelab pagination section, CHANGELOG under [Unreleased].

## 2026-08-11 (Tue) — `-cube`/`-rollup` unblocked in typed mode

Ross hit `group-by ... -cube` erroring under SSQL_MODE=typed ("not yet
supported in typed mode; drop -typed") and asked how hard a fix was. Answer:
nearly free, because the Phase B ejection machinery (v4.40.0) already does
all the work — `tagRecordModeFragments` gives a capability-less record
fragment `{Accepts: SeqRecord}`, and the planner's `RecordBoundaryBefore`
inserts the typed→Record adapter (plus `Serial()` if upstream is a Stream).
So the fix in `group_by.go` is: replace the `WriteErrorAndExit` with a
fallback note and restructure the typed branch so rollup/cube skip
`emitTypedGroupBy` and fall through to the existing record `ssql.Rollup`
emission. Typed/parallel CSV parse upstream is preserved; the ejection is
visible under `-explain`.

Gate: `groupby_cube_typed_eject` equivalence case on sales.csv (repeated
Widget/US pair so wrong grouping diverges) with a hand-checked golden of the
full enrichment output; duckdb lane skipped because `generate sql` refuses
rollup/cube loudly (pre-existing, tracked). Watched it fail under a
mode-swap sabotage (cube→hierarchical). Gotcha for future-me: I reverted
the sabotage with `git checkout <file>` and wiped the real fix along with
it — sabotage a file you have uncommitted work in ONLY via a re-appliable
edit, or commit first.

Native typed rollup (derived struct with per-grouping-set prefixed fields)
judged not worth 1-2 days speculatively — noted in TODO with the estimate.

## 2026-08-12 (Wed) — playground share links

Shipped the share-links TODO: a Share button in the playground encodes the
current pipeline as `#p=<base64url(utf8)>` in the URL fragment and copies
the link (clipboard API with an address-bar fallback); on load, a `#p=`
hash preloads the pipeline into the textarea and runs it — auto-optimizing
instead for `from ssh`/`from catalog` pipelines, same rule as the example
buttons. Fragment rather than query string so shared pipelines never appear
in server logs and GitHub Pages caching is untouched. All in
`cmd/ssql-playground/playground.html` — no WASM change.

Encoding is manual UTF-8→binary-string→btoa with `+/`→`-_` and padding
stripped (charset `[A-Za-z0-9_-]`, regex-validated on parse; malformed
hashes are console-warned and ignored, page falls back to the default
example). Roundtrip tested in node over unicode/quotes/procsub cases —
a typical 5-stage pipeline link is ~150 chars.

End-to-end verified with headless Chrome (`--headless=new
--virtual-time-budget=20000 --dump-dom` against a local http.server): the
shared link boots WASM, decodes, auto-runs and renders the group-by table;
the no-hash page keeps the original "Click Run" default; a garbage hash
still reaches Ready. Headless Chrome + virtual-time-budget is a nice
found-pattern for testing the playground without a human — worth reusing.

Deploy rides yesterday's gh-pages workflow (playground.html is in its
path filter): push to main is the release.

## 2026-08-12 (Wed) — playground help-at-cursor button

Ross proposed playground Tab completion + a help-at-cursor button; started
with help (cheapest, and it forces the plumbing the rest will reuse). Key
discovery: the CLI's Alt-h machinery is entirely argv→stdout protocol flags
(`-cursor-stage`, `-help-at`, `-complete-source`), so the browser version is
the SAME Go code called through the existing `ssqlExec` WASM bridge — no new
wasm exports.

Refactor: moved `cursor_context.go` (+test) from cmd/ssql package main into
`commands`, added `commands.HandleCursorProtocol` — one protocol handler now
shared by `cmd/ssql/main.go` and the playground's `execCommand` (the same
single-source-of-truth medicine as the registration-drift test). CLI-side
regression: all four keybinding tests incl. the real-pty ones pass.

JS side (~50 lines in playground.html): "? Help" button (onmousedown
preventDefault so the textarea keeps its caret) + Alt-h keydown → text up to
caret → `-cursor-stage` → COMP_WORDS index math ported from the bash binding
(trailing whitespace = new empty word) → `-help-at` → output panel. Uses the
existing quote-aware `shellSplit`.

Testing: promoted the headless-Chrome pattern into a committed gate —
`cmd/ssql-playground/test-harness.html` iframes the REAL page, sets
caret/value, calls `helpAtCursor()`, dispatches Alt-h KeyboardEvent, loads a
`#p=` share iframe; `scripts/playground-test.sh` serves + drives + greps.
Seven scenarios (incl. share-link regression). Watched it fail under an
off-by-one caret-index sabotage (caught by the expr-arg case). Headless
gotchas documented in claude/playground.md: virtual-time vs real WASM fetch
(anchor polls to real fetches), `let` not a window property (probe button
disabled state), dump-dom is main-frame-only.

## 2026-08-12 (Wed) — stale-test cleanup + tmux popup leak in pty tests

Running the FULL cmd/ssql suite (first time since the transpiler landed, it
turns out) surfaced two failures that were stale pre-transpiler expectations,
not regressions:

- `TestTypedUpdateSetExprErrors` asserted `-set-expr` always fails in typed
  mode ("Tier 3") — inverted by transpiler Phase 1 (v4.57.0), which compiles
  it natively. Repurposed as `TestTypedUpdateSetExprUnknownFieldLoud`: the
  thing that must STILL fail — an unknown field — errors loudly naming the
  field and schema. (Success path was already covered by "update set-expr
  goes native typed setter".)
- `TestRunKeybinding`'s "pipeline that can't generate" fixture used
  `-set-expr x '3*4'` — v4.57.0 learned to compile it, silently inverting
  the test. New fixture: unknown field, a PERMANENT loud error.

Lesson: a test that asserts "feature X errors" is a time bomb when X is on
the roadmap — the fixture inverts silently the day X ships. Assert on a
scenario that is *semantically* invalid (unknown field), not one that's
merely unimplemented.

Separate find, reported live by Ross: pty keybinding tests were POPPING TMUX
WINDOWS on his desktop — five of the eight pty tests (`field`, `run`,
`field_procsub`, `field_tab_handoff`, `optimise`) didn't scrub `$TMUX`, so
the keybinding scripts inside them took the `tmux display-popup` path in his
session. All five now match the help/code pty tests: `os.environ.pop("TMUX")`
in the pty child + `unset TMUX` in the shell. Hermetic now.

Also: the full suite had NOT been part of the recent release gates in
practice — corpus/equivalence/metamorphic ran, the plain `go test
./cmd/ssql/...` didn't. It is now (that's how these were found).
