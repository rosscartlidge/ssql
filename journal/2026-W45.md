# 2026-W45

## 2026-11-02 (Mon) — graph traversal moves to its own command, `traverse`

Ross: "do you think the graph traversal functions should be moved to its
own command, say "traverse", rather than in join, where it could be hard
to find". Agreed. Findability was the obvious reason; the less visible
one was that in either mode about half of `join -help` was refused.
Ross chose `-from NODE SRC -to DST` over keeping `-on`/`-follow`, and
`join -follow` is removed, two days after v4.135.0 shipped it. DFC161 §10
records why the §2 objections to a separate command don't apply: they
were against a different shape (edges on stdin), and the model is
unchanged (seeds are the stream, edges the file, same walk). The library
keeps `ssql.Follow` / `typed.Follow`, since renaming them would break
v4 callers.

Shape of the change (467dc1f, docs b5b6b02):
- `generateJoinCode`'s side handling became `generateSideCode`
  (`commands/side_source.go`). It covers procsub fragments or a file,
  the `rightSourceN` func, typed sampling and the record fallback.
  `join` and `traverse` each pass in a typed and a record emitter. This
  took the traversal branches out of join's codegen entirely.
- The Ctrl-O helpers from yesterday became command-neutral
  (`rightFieldSlot`, `sideFile`). The declaration alone decides the
  slot, so traverse's side fields needed no new completion code.
- `generate sql` dispatches `traverse` to `translateTraverse`.
  `traverse` keeps its known columns, where join reset them.

Found on the way:
- **`generate ssql` printed a dead procsub.** The optimiser rebuilt
  `<(…)` from the func fragment only for `IsJoin`. So `traverse <(…)`
  rendered with the generation run's `/dev/fd/63` and replayed empty.
  The `ssql-opt` lane of `traverse_procsub_edges` caught it on the first
  run. Fix: `HasSideFile` covers any side-file command, and `IsJoin`
  stays the marker for join's pushdown rules. So traverse is still a
  barrier, because the optimiser doesn't know it.
- **A third registration list.** `TestServeConsoleRegistration` wants
  every CLI command either in `serve`'s console or excluded with a
  reason. join is excluded because it reads server-side file paths, so
  traverse gets the same exclusion. CLAUDE.md names only main.go and
  the playground; the test names the third list itself, which is
  enough.

Gates: doc-check, lanes (684 s), vet, slim, race, doc-test, scale and the
playground e2e were green on the first chain. The full cmd/ssql run
failed only on the console registration; I fixed it (test-only) and the
rerun was green (1306 s). Watched fail: dropping the SQL dispatch fails
the duckdb lane, and the procsub bug was a real catch. Not released.

## 2026-11-02 (Mon) — lookup joins: -type honoured, typed and SQL forms

Ross's pipeline (`join kind.csv -on a_kind kind -as kind_name a_kind_name
- -on z_kind kind -as kind_name z_kind_name | join relationship.csv …`
over the 1.2 GB `~/csvs/shuffled.csv`) failed in typed mode twice: first
from the wrong directory (the typed sampler opens the source), then
"only single-clause joins without -as renames are supported in v1".

The real problem underneath: a lookup join (`-as`, or several `-on`
clauses) ran `ssql.LookupJoin`, which keeps an unmatched row with the
clause's fields absent, whatever `-type` said, even an explicit `-type
inner`. A struct can't hold absence, so a faithful typed form was
impossible. Ross chose to honour `-type`: inner (the default) is the new
`ssql.InnerLookupJoin`, left keeps `LookupJoin`, right/full are refused.
This is a breaking change for lookups with unmatched keys, and the
CHANGELOG says how to keep the old output (`-type left`).

- Typed: `typed.LookupJoin[Parallel]` (`typed/lookup.go`), one key pair
  per clause, all of one K, `merge func(L, []R) O` with a reused slice.
  Edge shapes fall back to record for the stage (handled=false in
  `generateSideCode`).
- SQL (`generate_sql_lookup.go`): one JOIN per clause, aliased `__rN`.
  It used to refuse `-as` and translate only the LAST `-on` of a
  multi-clause join; I confirmed that with the old binary.
- The rust lane failed on its first run: its escape hatch replaces a
  layer's FROM with a registered view and lost my `__l` alias. The fix
  is `fromTemplate` + `sqlOnly`, as except/intersect do it. Any new
  translator that aliases the folded left side needs the same.
- `resolveJoin` now refuses a rename onto a left field or onto another
  rename (silent overwrite before). In the other direction, it no
  longer reports an uncopied right column as a collision when every
  clause names its fields.

Benchmark of Ross's pipeline across the lanes (24 cores, idle; every
lane gives the same 103,037 rows; the script is in the session
scratchpad):

| lane | wall | peak RSS |
|---|---:|---:|
| exec | 86.9 s | 39 MB |
| record (`generate go`) | 125.1 s | 198 MB |
| typed / parallel | **0.98 s** | 1.2 GB |
| DuckDB 1.5.0 | 1.40 s | 851 MB |
| DataFusion 55 (SQL via Python) | 1.61 s | 3.9 GB |
| generated Rust (DataFusion) | 2.51 s | 3.9 GB |

Surprise worth chasing: record codegen is 1.4× SLOWER than exec on this
pipeline. Postgres was not run: it would mean copying 1.2 GB into the
rig first. Gates: lanes (452 s), full cmd/ssql (1318 s), race, scale
(the new `lookup-join` case), doc-test and the playground were green.
Commits 17fc3bc6 and 293e0ee7. Not released.

## 2026-11-02 (Mon) — the lookup pipeline in bench-engines; why exec beats record

`scripts/bench-engines.sh` now runs Ross's lookup pipeline as its eighth
row (`lookup`). New options: `-engines …,record,exec` for the two Go
lanes the engine table leaves out, and `-only` to run one row. The
refreshed table is in `doc/performance.md` §1a; the write-up is DFC158
§3.15, with rows added to DFC157/159/160.

Ross guessed that exec beats record because of the process per stage.
Confirmed with CPU against wall time and `taskset -c 0`. Exec runs at
396% CPU/wall and record at 196% (that 196% is GC, not stage overlap).
Exec spends 40% more CPU in total on JSONL between stages. Pinned to one
core, exec takes 267 s and record 170 s. So record does less work, but
it is one goroutine chain. A record lane parallel by stage would need
batched hand-offs, not per-row channels.

Found on the way: generated Rust is the slowest fast lane on this row
(2.45 s, 3.8 GB, vs 1.03 typed). Its physical plan (EXPLAIN through the
Python bindings) builds every HashJoinExec on the 14.6 M-row CSV side,
Partitioned, so those rows are hash-partitioned three times. A CSV has
no row count for the planner. It goes in TODO (DFC158 §4 item 8): measure
small-side-first, a row count, and a broadcast threshold before choosing.
