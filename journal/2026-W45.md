## 2026-11-02 (Mon) — graph traversal moves to its own command, `traverse`

Ross: "do you think the graph traversal functions should be moved to its
own command, say "traverse", rather than in join, where it could be hard
to find". Agreed. Findability was the obvious reason; the less visible
one was that in either mode about half of `join -help` was refused.
Ross chose `-from NODE SRC -to DST` over keeping `-on`/`-follow`, and
`join -follow` is removed, two days after v4.135.0 shipped it. DFC161 §10
records why the §2 objections to a separate command don't apply: they
were against a different shape (edges on stdin), and the model is
unchanged (seeds are the stream, edges the file, same walk). The library
keeps `ssql.Follow` / `typed.Follow`, since renaming them would break
v4 callers.

Shape of the change (467dc1f, docs b5b6b02):
- `generateJoinCode`'s side handling became `generateSideCode`
  (`commands/side_source.go`). It covers procsub fragments or a file,
  the `rightSourceN` func, typed sampling and the record fallback.
  `join` and `traverse` each pass in a typed and a record emitter. This
  took the traversal branches out of join's codegen entirely.
- The Ctrl-O helpers from yesterday became command-neutral
  (`rightFieldSlot`, `sideFile`). The declaration alone decides the
  slot, so traverse's side fields needed no new completion code.
- `generate sql` dispatches `traverse` to `translateTraverse`.
  `traverse` keeps its known columns, where join reset them.

Found on the way:
- **`generate ssql` printed a dead procsub.** The optimiser rebuilt
  `<(…)` from the func fragment only for `IsJoin`. So `traverse <(…)`
  rendered with the generation run's `/dev/fd/63` and replayed empty.
  The `ssql-opt` lane of `traverse_procsub_edges` caught it on the first
  run. Fix: `HasSideFile` covers any side-file command, and `IsJoin`
  stays the marker for join's pushdown rules. So traverse is still a
  barrier, because the optimiser doesn't know it.
- **A third registration list.** `TestServeConsoleRegistration` wants
  every CLI command either in `serve`'s console or excluded with a
  reason. join is excluded because it reads server-side file paths, so
  traverse gets the same exclusion. CLAUDE.md names only main.go and
  the playground; the test names the third list itself, which is
  enough.

Gates: doc-check, lanes (684 s), vet, slim, race, doc-test, scale and the
playground e2e were green on the first chain. The full cmd/ssql run
failed only on the console registration; I fixed it (test-only) and the
rerun was green (1306 s). Watched fail: dropping the SQL dispatch fails
the duckdb lane, and the procsub bug was a real catch. Not released.

## 2026-11-02 (Mon) — lookup joins: -type honoured, typed and SQL forms

Ross's pipeline (`join kind.csv -on a_kind kind -as kind_name a_kind_name
- -on z_kind kind -as kind_name z_kind_name | join relationship.csv …`
over the 1.2 GB `~/csvs/shuffled.csv`) failed in typed mode twice: first
from the wrong directory (the typed sampler opens the source), then
"only single-clause joins without -as renames are supported in v1".

The real problem underneath: a lookup join (`-as`, or several `-on`
clauses) ran `ssql.LookupJoin`, which keeps an unmatched row with the
clause's fields absent, whatever `-type` said, even an explicit `-type
inner`. A struct can't hold absence, so a faithful typed form was
impossible. Ross chose to honour `-type`: inner (the default) is the new
`ssql.InnerLookupJoin`, left keeps `LookupJoin`, right/full are refused.
This is a breaking change for lookups with unmatched keys, and the
CHANGELOG says how to keep the old output (`-type left`).

- Typed: `typed.LookupJoin[Parallel]` (`typed/lookup.go`), one key pair
  per clause, all of one K, `merge func(L, []R) O` with a reused slice.
  Edge shapes fall back to record for the stage (handled=false in
  `generateSideCode`).
- SQL (`generate_sql_lookup.go`): one JOIN per clause, aliased `__rN`.
  It used to refuse `-as` and translate only the LAST `-on` of a
  multi-clause join; I confirmed that with the old binary.
- The rust lane failed on its first run: its escape hatch replaces a
  layer's FROM with a registered view and lost my `__l` alias. The fix
  is `fromTemplate` + `sqlOnly`, as except/intersect do it. Any new
  translator that aliases the folded left side needs the same.
- `resolveJoin` now refuses a rename onto a left field or onto another
  rename (silent overwrite before). In the other direction, it no
  longer reports an uncopied right column as a collision when every
  clause names its fields.

Benchmark of Ross's pipeline across the lanes (24 cores, idle; every
lane gives the same 103,037 rows; the script is in the session
scratchpad):

| lane | wall | peak RSS |
|---|---:|---:|
| exec | 86.9 s | 39 MB |
| record (`generate go`) | 125.1 s | 198 MB |
| typed / parallel | **0.98 s** | 1.2 GB |
| DuckDB 1.5.0 | 1.40 s | 851 MB |
| DataFusion 55 (SQL via Python) | 1.61 s | 3.9 GB |
| generated Rust (DataFusion) | 2.51 s | 3.9 GB |

Surprise worth chasing: record codegen is 1.4× SLOWER than exec on this
pipeline. Postgres was not run: it would mean copying 1.2 GB into the
rig first. Gates: lanes (452 s), full cmd/ssql (1318 s), race, scale
(the new `lookup-join` case), doc-test and the playground were green.
Commits 17fc3bc6 and 293e0ee7. Not released.

## 2026-11-02 (Mon) — the lookup pipeline in bench-engines; why exec beats record

`scripts/bench-engines.sh` now runs Ross's lookup pipeline as its eighth
row (`lookup`). New options: `-engines …,record,exec` for the two Go
lanes the engine table leaves out, and `-only` to run one row. The
refreshed table is in `doc/performance.md` §1a; the write-up is DFC158
§3.15, with rows added to DFC157/159/160.

Ross guessed that exec beats record because of the process per stage.
Confirmed with CPU against wall time and `taskset -c 0`. Exec runs at
396% CPU/wall and record at 196% (that 196% is GC, not stage overlap).
Exec spends 40% more CPU in total on JSONL between stages. Pinned to one
core, exec takes 267 s and record 170 s. So record does less work, but
it is one goroutine chain. A record lane parallel by stage would need
batched hand-offs, not per-row channels.

Found on the way: generated Rust is the slowest fast lane on this row
(2.45 s, 3.8 GB, vs 1.03 typed). Its physical plan (EXPLAIN through the
Python bindings) builds every HashJoinExec on the 14.6 M-row CSV side,
Partitioned, so those rows are hash-partitioned three times. A CSV has
no row count for the planner. It goes in TODO (DFC158 §4 item 8): measure
small-side-first, a row count, and a broadcast threshold before choosing.

## 2026-11-03 (Tue) — traverse: the edges are the stream, the starts are flags

Ross: "I have a feeling that the set of links should be the stdin to
traverse and the srcs to follow should be in the args", then asked for
a `-start-file` whose start column must carry the `-from` name. Agreed
and built (DFC161 §11, fbb64edc). The case for it: the edge list is the
big table (his link table is 14.6 M rows) and the starts a handful of
values, so stdin should carry the edges; filtering them becomes a
`where` before `traverse` rather than a procsub. DFC161 §2 had argued
the other way, but its objections were to a design that also needed a
second join implementation. The walk already hashed the edges and took
the seeds, so only the plumbing moved.

Grammar: `… edges … | traverse -from SRC -to DST [-start NODE]…
[-start-file FILE]`. Output rows are SRC (the start, no longer
overwritten), DST (the node reached), then the results, so traverse
turns an edge list into a reachability list of the same shape. A start
file's other columns carry through (the seed attributes the switch
would otherwise lose). Each distinct start row is walked once
(`FollowStarts`), and a `-start` text converts to the SRC column's type
through one function shared by every lane (`traverseStartValues`).

Gotchas worth remembering:
- **Record codegen's assembler finds a stage's input after the last
  `)(`**, so `ssql.Follow(input, cfg)(starts)` compiled into the wrong
  program ("undefined: filtered"). Hence `ssql.FollowEdges(starts,
  cfg)(input)`, a filter over the edges.
- **DataFusion re-evaluates a CTE each time it is read.** `__seeds`
  numbered by `row_number() OVER ()` is read by the anchor and by the
  final join; once the starts were a UNION with no fixed order, the two
  readings numbered them differently and PER's routes carried SYD's
  label. Only the DataFusion and rust lanes saw it; DuckDB and Postgres
  happened to agree. The starts are now numbered by their own columns,
  which is a total order because they are distinct.
- **The SQL side's columns came back sorted** from the fragments'
  advisory types; the equivalence harness checks column order, so the
  start file's columns are taken from the translated side query.
- `generate ssql` rebuilt procsubs only in join's FILE and union's
  `-file`; `procSubFlags(kind)` now names the flags per command, and
  traverse's is `-start-file`.

Ctrl-O completes `-start` values from the `-from` column upstream
(`startValueCompleter`, pinned in `TestFieldKeybinding`). The codelab
section, playground example 28 and its `cities.csv` (now `city,name,
state`, with a codelab copy) use the new grammar. Gates: vet, slim, race,
full cmd/ssql (1327 s), doc-check, doc-test, lanes (Postgres, DataFusion,
rust), scale, and the playground e2e, all green. Not released.

## 2026-11-03 (Tue) — vi mode: no Esc-prefixed bindings, Ctrl-X keys instead

Ross uses `set -o vi`: "I hit <esc>h to move cursor to left and I end up
with ssql help". The Alt keys (Alt-h, Alt-H, Alt-g, Alt-r) were bound in
vi-insert and vi-command too. Alt sends Esc, and in vi Esc leaves insert
mode, so readline held every Esc for keyseq-timeout to see whether h
followed, and a fast Esc h ran help. The old pty tests even said "Alt-h
is ESC-prefixed, so vi mode is the real test", but they only checked the
action *fired* in vi, never that ordinary vi editing survived.

Single-character keys were the alternative, but there are hardly any
free ones (Ctrl-G, Ctrl-H and Ctrl-R all mean something). So the Alt
keys are now emacs-only, and vi gets Ctrl-X h / H / g / r (also bound in
emacs; Ctrl-X has no meaning in vi-insert, so readline never waits on
it). Re-sourcing the script unbinds the old Esc keys from the vi maps,
so a running shell is fixed by one `eval`. The `bind` lines are now
generated from the KeyBindings table (`KeyBindLines`); before, each
emitter hand-wrote its own and a test scanned the sources for them.
`TestKeyBindingsInSync` checks the emitted scripts per keymap and fails
on an Esc key in a vi map; the help pty test types Esc h in vi (must not
be help), Ctrl-X h (must be), and re-sources over a stale vi binding.
Both failure modes were watched failing first, and the stale-binding
case was itself wrong at first (a doubled backslash bound the wrong key
and passed with the unbind removed). Fix 5bdba856; vet, slim, race,
full cmd/ssql (1333 s) and doc-test green. Not released. CLAUDE.md gains
the rule.

## 2026-11-03 (Tue) — Ctrl-X keys in vi-insert: the default Ctrl-X binding

wrote Ctrl-X h in one burst (no gap, so no ambiguity), and it pressed
it after Esc h, i.e. in vi-command, where Ctrl-X is unbound. It now
pauses between the keys and tests vi-command and vi-insert. Fix
e71ff0ab; full gates green (cmd/ssql 1344 s). CLAUDE.md's vi rule now says

## 2026-11-03 (Tue) — DFC162: UUIDs and IP addresses (survey), two Parquet read bugs

Ross asked whether ssql has a uuid function. It doesn't. He asked for a
write-up of the UUID alternatives, and of whether IPv4/IPv6 deserve a
type. DFC162 is a survey; nothing is built. Every engine fact in it was
measured: DuckDB 1.5 with `inet`, Postgres 16 on the rig, DataFusion 55.

**UUIDs need no type.** The canonical lowercase text is fixed-width, so
string order is the 128-bit order.

- The recommendation is `uuid5(ns, name)` first. It is deterministic
  and interoperable, and Python's `uuid` is its independent oracle.
- DuckDB has no v5, but one can be built in SQL from
  `sha1(unhex(ns) || encode(name))` with a 16-character lookup string
  for the variant nibble. Verified identical to Python, including a
  UTF-8 name.
- Postgres needs `uuid-ossp` and DataFusion has no sha1, so both refuse.
- A random `uuid()` or `uuid7()` would be the first nondeterministic
  function to get an equivalence case. It needs a shape normaliser.
  DataFusion re-evaluating a CTE per read means a random column read
  twice can differ (the traverse `OVER ()` lesson again).

**IP addresses are not fine as strings.** `sort ip` puts 10.x before
9.x.

- The recommendation is functions on strings now (`ipin`, `ipnet`,
  `ipint`, `ipfamily`, …, all on `net/netip`, already in slim's deps),
  and an `inet` type later. That type has no arithmetic, so it is about
  a day of DFC155's census.
- Gotchas measured:
  - no engine keeps an address exactly in Parquet; DuckDB's INET is a
    struct with a DOUBLE address, so v6 is rounded;
  - Postgres `inet::text` appends `/128`, so the SQL must use `host()`;
  - DuckDB has no INET → integer cast;
  - DuckDB keeps host bits;
  - DataFusion has nothing for IP addresses.

**Two bugs found by the probing**, both in TODO.md:

- A Parquet struct column silently shifts or drops columns.
  `parquet.go` passes field indices where pqarrow's `ReadRowGroups`
  wants leaf indices.
- A Parquet UUID column reads as base64.

The first is silent data loss on any nested Parquet file. It ranks
above the proposal.

## 2026-11-03 (Tue) — v4.137.2 released: Parquet nested columns and UUIDs

Ross: "push and commit the DFC and then fix the parquet bugs", then "and
then cut a patch release". DFC162 went in as 4e52b515. The fix is
5323507d. The release commits are b74c2b16, 0d0a998a (bake, tagged) and
dab23ed3 (debs, pins, explore engine).

**The cause.** pqarrow's `ReadRowGroups` and `GetRecordReader` take
*leaf* column indices. Both readers passed top-level field indices: the
record reader in `parquet.go`, and the typed reader in
`typed/io_parquet.go`, serial and parallel. With no nested column the
two coincide, which is why nothing caught it. With one, every later
column read the wrong leaves, and a partially selected map panicked
inside arrow.

The shared fix is `internal/pqcols`:
- `Leaves` maps fields to their leaves through the manifest.
- **Gotcha:** pqarrow's `SchemaField.IsLeaf()` tests `ColIndex != -1`,
  but group fields carry `ColIndex` 0. So leafness is "no children".
- `UUIDFields` reads the Parquet logical type. pqarrow hands a UUID over
  as plain `FixedSizeBinary(16)`, so only the logical type says it is a
  UUID.
- `JSON` renders nested values. A map is an object, as DuckDB's
  `to_json` writes it; Arrow's `ValueStr` gives a list of key/value
  pairs. arrow-go's `GetOneForMarshal` quotes floats and decimals, so
  both are handled explicitly. NaN is null.

**DFC144 Level 0 had missed these readers.** A nested Parquet or Arrow
column is now `json`. Before, it was a string, and typed codegen
refused it outright.

**Tests.**
- DuckDB-written fixtures in `testdata/`, with DuckDB's `to_json` as
  the oracle for the deep one.
- Equivalence cases `parquet_nested_uuid` and
  `parquet_past_nested_columns`. All of the unit tests and the

- The DataFusion lane's Python runner now uses
  `to_arrow_table().to_pylist(maps_as_pydicts="strict")`, so a map is an
  object as in the other lanes.
- DataFusion has no UUID type (it reads raw bytes), so that case skips
  DataFusion and rust. The typed lanes skip it too: they read the null

## 2026-11-04 (Wed) — uuid4, uuid5 and uuid7 (DFC162 §8)

Ross: "lets do uuid 4, 5 and 7". All three are expression functions.
Each returns its canonical lower-case text, and there is no UUID type;
DFC162 §3 U4 stands.

**What and where.**
- `exprfn/uuid.go` is the one implementation. Random bits come from
  `crypto/rand`. `uuid7` is the plain RFC form (48 bits of ms, then
  random) with no per-millisecond counter, because a counter is a lock
  per row in the parallel lanes and still would not order across
  shards.
- `expr_uuid.go` binds the VM, with the shadowing alias.
- The transpiler cases are in `expr_go.go`.
- `generate_sql_uuid.go` holds the SQL. `uuid4` translates in all
  three dialects. `uuid7` and `uuid5` translate on DuckDB only: uuid5
  is the sha1-slicing form from DFC162 §3 U1, and a column namespace
  goes through a CASE.
- `uuid5` requires a namespace, as Python does (§6 Q2): an
  ssql-invented default would make keys nobody else can reproduce.

**Testing random functions without a harness hook.** The pipeline
checks its own shape:
- a regex on the version and variant nibbles;
- `count-distinct` equal to the row count;
- a copy of the column equal to the id;
- for v7, the leading 48 bits within 2022–2039.

It reduces to one deterministic row, which serves as a Golden in every
lane, Postgres, DataFusion and rust included. The read-twice hazard
(§3 U2) did not appear: an `update` chain is nested subqueries, which
every engine evaluates once. `uuid5` has a Golden from Python's
`uuid.uuid5`.

**Found on the way.** `+` on strings had no SQL translation; it was
emitted as a numeric `+`, and DuckDB rejected `'x' + CAST(n AS
VARCHAR)`. `sqlStringOperand` now turns it into `||` when either side
is a literal, a text column or a string-valued function. Gotcha:
`upper`/`lower`/`string` are expr builtins, so they parse as
`BuiltinNode`, not `CallNode`. The fix has its own equivalence case,
`expr_string_concat`. All the new cases were watched failing under
planted bugs, uuid5's version nibble with the concat fix in place so it
was not confounded.

Ross chose DFC162's I2: a real `inet` type from day one. That came with
the core functions (`isip`, `ip`, `inet`, `ipfamily`, `ipint`, `ipkey`,
`ipnet`, `ipin`), with DataFusion refusing. In plan mode he decided:
- `ipint` is two's complement (his question, "why can't we use negative
  numbers?", settled it);
- `ipkey` has a width per family;
- `ipnet` returns an inet;
- Postgres refuses `ipint`.

It was built in six gated units: the type, the VM, typed, SQL, interchange
and docs.

**Measured first, then built on it.** DuckDB's INET and Postgres's inet
both order exactly as `netip.Prefix.Compare`, so the Go form is a
`netip.Prefix`, wrapped in `ssql.Inet` for the engines' text.

**SQL took two engine workarounds:**
- DuckDB folds an INET range into BETWEEN, which INET lacks, so the range
  comparisons are emitted as `(…) IS TRUE`.
- `duckdb -json` prints an INET as a non-JSON struct, so the final SELECT
  is wrapped to cast it. The wrap is a subquery, because an outer ORDER BY
  would sort the text.

DuckDB's `ipint`/`ipkey` read the undocumented INET→STRUCT cast, which a
test pins. Every function gives byte-identical CSV on DuckDB and in exec,
including both sides of 2^127.

**The census found seven bugs that predate inet,** all of one shape: a
type switch or a Go-type table that a newer type was never added to. The
worst were these:
- `from jsonl -type` silently left decimals and times as text;
- `update -set-expr x 'decimal(x)'` left the old type in the header;
- typed `top` on a decimal or time column did not compile.

All seven are listed in DFC162 §9.4, each fixed with a test watched
failing. Ross: "great that you are finding new bugs — can you think of a
way of finding these more proactively?" The answer is a type × operation
matrix plus a partial-type-switch lint. He asked to finish inet first and
then write it as a DFC (TODO).
