## 2026-09-14 (Mon) — popups without tmux, and the Alt-h quoting bug it found

Ross: "build the less popup fallback" (DFC127 §3). `_ssql_show_help`:
in tmux unchanged; else, when stdout+stdin are a terminal and the text
has more lines than the terminal minus three (`$LINES`, else `tput

Writing that test exposed a bug nobody had hit: `_ssql_help_at` split
the stage into words with `read -ra`, which ignores quotes, so an
`-if-expr 'salary > 1000 && bucket(ts, ` became five words and the
cursor landed past the expression argument — Alt-h showed only the
flag. Ross's earlier manual check used `'upper(trim(name` (no spaces),
which is why it seemed fine. Fix per DFC115: stop tokenising in bash.
`ssql -help-at-cursor BEFORE` finds the stage (paren-aware) and the
words (quote-aware `tokenizeStageOpen`; an unclosed quote keeps its
trailing space — the first cut appended an empty "new word" and missed
again), then the shared `helpAtWords`. The binding is now four lines.
Two test-writing gotchas: `PAGER` is word-split by the shell, so a
quoted command in it breaks — use a script path; and a python driver's
`open(...).write` needs the pty size set AFTER fork (TIOCSWINSZ).
Docs: codelab §1, README key table note, tmux page §5, DFC127.

## 2026-09-14 (Mon) — DFC128: JSON interchange with DuckDB, and the time type

Ross: "have you actually checked that duckdb can import json/jsonl from
ssql? and the reverse?" Honest answer: no — Saturday's "check" is the
one that wrote the stray `select 1 as a, 'x' as b` DuckDB file (the SQL
went in as a database name), so it never ran. Ran it today against
DuckDB 1.5.0 with the codelab data, both directions, and wrote it up as
[DFC128](../doc/research/dfc128_json_interchange_and_time_type.md).
The §2 claim holds (`to jsonl`/`to json` are what DuckDB reads; the bare
stream gives a `_schema` STRUCT column and a phantom NULL row — Ross's
"I had assumed you needed to use the to/from commands to exclude the
schema" is exactly right). The reverse loads through `from jsonl`,
`from f.json`, `from json -`, with three findings: (F1) a field NULL in
the first record is dropped by every sink — nil skipped by the reader,
header inferred from ONE record, sinks trust the header; (F2)
`_line_number` — Ross: "what is the real use … is it needed?" — none:
injected by the headerless readers since the initial commit, read by
nothing in the CLI, called a bug in the `from ssh` comments, and the
only "documentation" is the signal codelab explaining it as "the row
counter every ssql stream carries", which is really the signal family
(fft/convolve/correlate/spectrogram) emitting no `_schema` header;
(F3) time exists in the package (GetOr[time.Time] converts three string
forms; JSON writer emits RFC 3339; typed infers time.Time from CSV
samples; SQL translator knows TIMESTAMP) but not on the wire — no
`time` in `_schema`, `cast` refuses it — and `coerceToString`'s default
`%v` branch turns a time written into an existing string field into
`2026-01-02 10:30:00 +0000 UTC`, which neither DuckDB nor ssql's own
parser reads as a time. Six decisions in DFC128 §6; recommendation is a
`time` wire type, explicit (no auto-detect), `_line_number` gone from
the CLI path, sample-based schema inference with late fields loud,
headers on the signal commands, and a DuckDB-gated interchange test so
the doc claim has a gate. Postgres unverified (no psql here).
