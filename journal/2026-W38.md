## 2026-09-14 (Mon) — DFC128: JSON interchange with DuckDB, and the time type

Ross: "have you actually checked that duckdb can import json/jsonl from
ssql? and the reverse?" Honest answer: no — Saturday's "check" is the
one that wrote the stray `select 1 as a, 'x' as b` DuckDB file (the SQL
went in as a database name), so it never ran. Ran it today against
DuckDB 1.5.0 with the codelab data, both directions, and wrote it up as
[DFC128](../doc/research/dfc128_json_interchange_and_time_type.md).
The §2 claim holds (`to jsonl`/`to json` are what DuckDB reads; the bare
stream gives a `_schema` STRUCT column and a phantom NULL row — Ross's
"I had assumed you needed to use the to/from commands to exclude the
schema" is exactly right). The reverse loads through `from jsonl`,
`from f.json`, `from json -`, with three findings: (F1) a field NULL in
the first record is dropped by every sink — nil skipped by the reader,
header inferred from ONE record, sinks trust the header; (F2)
`_line_number` — Ross: "what is the real use … is it needed?" — none:
injected by the headerless readers since the initial commit, read by
nothing in the CLI, called a bug in the `from ssh` comments, and the
only "documentation" is the signal codelab explaining it as "the row
counter every ssql stream carries", which is really the signal family
(fft/convolve/correlate/spectrogram) emitting no `_schema` header;
(F3) time exists in the package (GetOr[time.Time] converts three string
forms; JSON writer emits RFC 3339; typed infers time.Time from CSV
samples; SQL translator knows TIMESTAMP) but not on the wire — no
`time` in `_schema`, `cast` refuses it — and `coerceToString`'s default
`%v` branch turns a time written into an existing string field into
`2026-01-02 10:30:00 +0000 UTC`, which neither DuckDB nor ssql's own
parser reads as a time. Six decisions in DFC128 §6; recommendation is a
`time` wire type, explicit (no auto-detect), `_line_number` gone from
the CLI path, sample-based schema inference with late fields loud,
headers on the signal commands, and a DuckDB-gated interchange test so
the doc claim has a gate. Postgres unverified (no psql here).

## 2026-09-19 (Sat) — DFC128 D1 core: `time` is a wire type; ssql owns `date()`

Taken as DFC128 §4 recommended: a wire type, explicit only, one type
for dates and timestamps. The design decision that mattered was small:
`date()` had to be registered with `expr.Function` (compile-time
binding), not dropped into the environment the way `bucket` is — an env
entry named `date` collides with a record FIELD named `date`, which is
the single most likely column name in the data this is for. With the
compile-time form `date(date)` works; the price was one validator that
started reading the `date` callee as a field reference once it was no
longer a BuiltinNode (`extractIdentifiers` now discounts callee uses of
`ssql.ExprCompiledFunctions`). Everything that turns a value into a time
goes through one list of layouts, `ssql.ParseTime`, so `GetOr`, the
header-aware readers, `cast` and `date()` cannot disagree again — the
original F3 finding was exactly that disagreement.

The differential gate did the real work. Four cases, and each run found
the next lane that did not know about times: typed cast (no target),
typed where (eq/ne only, against a literal whose parse error was
discarded — a silent zero time, now parsed at generation time), typed
sort, a missing `time` import on the derived struct, then SQL (`abs()`
of a TIMESTAMP from the numeric-epoch bucket arithmetic — fixed by
tracking cast-to-time columns in the assembler and emitting
`time_bucket`/`date_bin` pinned to the 1970 origin, because the engines'
default 2000-01-03 origin is a different grid), then a representation
question (three spellings of one instant — normalised in the harness,
goldens included), and last a genuinely old bug: record-mode `update
-set-expr` stored any non-scalar result with `%v`, so `now()`/`date(x)`
in generated code had always written `… +0000 UTC` text where exec wrote
a time. Nobody had grouped by a time before. Final state: all four cases
agree on exec, record, typed, parallel, generate-ssql, DuckDB, Postgres
and DataFusion, with two reasoned DuckDB skips (session-time-zone shift
of `+00` strings; method calls on a time have no SQL form).

Semantics chosen for bad data: an explicit request (`cast`, a `where`
operand) that is not a time stops the pipeline; an implicit one (a header
that says `time` over a value `ParseTime` cannot read) leaves the value
as it was. Never a zero time in place of data. Left for a second unit:
`resample` SQL over time columns, null-key visibility in the JSON
parser. Working method after this morning's accident: a patch
checkpoint outside the tree after every green step (eleven for this

## 2026-09-19 (Sat) — null keys, and what NULL means in each lane (DFC128 §6g)

failed in go-record: generated Go compared an absent value as zero, in

Also deleted: a third copy of the JSONL loop and schema cache in
`lib.ReadJSON`'s lines branch, with its own first-record type lock; it
delegates to the one reader now. DFC128 is fully closed.

Release-timing gotcha from the same unit: the first full run failed two
script tests with `r.HasValue undefined`. They ran `generate go -run`
with no `SSQL_MODULE_DIR`, so the generated program compiled against the
PUBLISHED module (v4.102.0), which predates the method — and since
`where` now emits it, nearly every generated program needs it. Users are
unaffected (a released binary pins its own version), but a test that
compiles generated code against the proxy is testing release timing and
the network, not the code under test. Both now set `SSQL_MODULE_DIR` to
the checkout (helper `scriptRunLocal`, which also returns stdout only,
because the override announces itself on stderr). Worth remembering
before any release whose codegen starts calling a new library symbol in
a common command: run the full suite BEFORE the bump, as usual, and
expect exactly this class of failure from any test that forgot the
override.

## 2026-09-20 (Sun) — DFC133: two sweeps, seven bugs nobody had asked about

Ross: "I am worried we might have bugs we don't know about — can you
think of a way of exercising the system to find bugs?" The week's own
evidence gave the answer: every case in the differential gate is
hand-written, so it only sees what someone thought to try (`gt 5` could
not see an absent value read as zero; `ge 0` could). Classifying the
week's defects showed the largest class — the result depends on which row
is first — needs no oracle at all, just the observation that a multiset
result cannot depend on input order. DFC133 sets out four instruments;
two are built.

**Row-order sweep.** Reruns the equivalence corpus with rows reordered
(each row moved first, reversal, a seeded shuffle), adversarial rows
appended, in CSV, JSONL and JSON-array form. Thirty seconds. Found: a
join that silently matches NOTHING when the key is int on one side and
float on the other (one `2.5` in a column is enough) — the hash key
printed values, the confirming Match compared raw interfaces, two
predicates in one file disagreed; a CSV header type taken from row one;
a JSON array reader coercing each column to its first value's type
(deleted with 150 lines of lock code). The join is the one that worries
me in retrospect: ordinary data, empty result, exit 0, green suite.

**Crash sweep.** Every command and flag from `ssql -spec-json` —
the CLI describing itself, no second grammar — with degenerate values and
inputs: 4,998 runs in 55 s. Found `sample <huge>` panicking in `make`
(same shape in `TakeLast`), and 22 flags accepting a field that does not
exist, including `fft -field typo` transforming a signal of zeros into a
confident spectrum. The first run's 92 "silent failures" were my own
sweep passing a NUL byte as an argument; a sweep's first run mostly tests
the sweep.

Both are opt-in gates (`SSQL_SWEEP=1`); every finding was promoted to a
permanent test, because the sweep is the search and the corpus is the
memory. Next: random differential testing against DuckDB with a shrinker,
then parser fuzz targets.

## 2026-09-20 (Sun) — DFC133 instruments 3 and 4: fuzz targets and random differential testing

"Let's do both." Fuzz targets first (cheap): six targets, 45–90 s each.
The JSON parsers disagreed on `{"a":true,"a":null}` within two seconds
(last-wins vs first-non-null); negative zero was not a write/read fixed
point. The valuable find was a side probe the fuzzing prompted — text
cannot make a NaN, so I asked what the WRITER does with one: `update
-set-expr z '0.0/0.0'` wrote the bare word `NaN`, not JSON, and the next
stage skipped the line. Whole rows gone, exit 0. Written as `null` now.
The reader's skip-on-parse-error is what made it silent; that is filed
as a decision, not changed.

Then the random differential tester: adversarial tables × random valid
pipelines, interpreter vs DuckDB on `generate sql`, shrinker, ~70/s. Its
first run agreed on 81 of 300, and nearly all of that was MY comparison
and shrinker, not ssql — `""` vs NULL for text (DFC124's decision),
DuckDB printing sums and decimals as strings, the shrinker emptying
columns. Every artifact became a generator constraint or a per-column
representation rule. What remained was real: SQL literals typed by their
spelling (`code = 12` against text); `update`'s SQL negation missed by
§6g; aggregates over nothing answering `""` — a present string the next
`where` compared — or 0; aggregates counting `""` as a value against
DFC124's own definition; `cast` of an empty cell → 0. The last two came
only after I wrote a golden by hand and the looser comparison stopped
hiding them: `update -set zip 02134` gave THREE answers in four lanes
("2134", the number 2134, "02134"), and with the comparison made strict
the tester immediately found that a CSV column of `007`s is read as
sevens. Zero-padded numbers are identifiers now, at all three inference
sites, as in DuckDB.

Two things to remember. A convenient normalisation hides exactly the
class it normalises: number-looking text → number cost me the two most
user-visible findings until a hand-written golden contradicted it. And I
broke the `-sum` registry line with a trailing comment mid-line (rest of
the struct literal commented out, wire type nil); the tester caught it in
one run, and `TestAggRegistryEntriesAreComplete` now pins the class.
