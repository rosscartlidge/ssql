## 2026-09-07 (Mon) — readers finish the job: the typed lane stops being silent

Ross picked the "readers finish the job" unit off the list ("convinced
me - silent dropping scary..."). The reproduction on one fixture — 1001
int rows then `1002,1.5` — was worse than the TODO entry said. exec CSV:
`Error: row 1002 … "1.5" is not int`, exit 1 (v4.88.0). Typed CSV: **1002
rows, sum 501501, exit 0** — the row kept, the cell zeroed (the exact
signal-became-zeros shape DFC124 fixed in exec, alive in the compiled
lane). Typed JSONL: 1001 rows, exit 0 — the row dropped. And a missing
input file: an empty table, exit 0, from every typed reader. My own
path mistake found that last one (the program ran in a subdirectory the
fixture wasn't in, and printed a header with no rows).

The fix has one shape across `typed/`: the lossy readers panic with a
`*typed.ReadError` (Op, Source, Row or Line, Err) — the root package's
`ssql.ReadCSV` / `*CellError` contract, mirrored — and the `*Safe`
readers yield it. `rowSchema.decode` and the JSONL plan now say
`column "v": "1.5" is not int64` (the strconv text was useless to a
user). The part that needed thought: a panic inside a shard goroutine
does not reach the generated program's `recover` in main — the process
dies with a goroutine trace, exit 2. So `shardGroup` (read_error.go)
runs every fan-out consumer's workers (`Serial`, `SerialCount`,
`GroupByParallel`, the CSV/Delim/Parquet per-shard sinks, top-k,
`DistinctParallel`, `Parallel`'s feeder) and re-raises the first panic in
the waiting goroutine; `Serial` rethrows after its fan-in channel
closes. `TestStreamConsumersPropagateShardPanic` drives each consumer
with the parallel CSV reader on the late fixture. Race clean.

Then the remedy had to exist. The exec error says "override with `-type
v float`" — and typed codegen REFUSED `-type` ("column overrides not
supported in typed mode"), `from tsv` and `from jsonl` had no such flag
at all, and the `-sample` / `-last` record fragments dropped the
overrides they were given. Now `lib.TypeOptions` flows into all three
samplers (an overridden column takes the named Go type; a `_schema`
header is re-rendered with it), `from tsv` grew `-type` / `-default-type`
(a `typeArgs` bundle threads flags + resolved `CSVConfig` through
exec/sample/last/codegen), and `from jsonl -type` is a strict per-record
coercion, `ssql.CoerceFieldTypes` — JSON has one number type, so a
whole float into int is exact and `1.5` into int is a `CellError`
("explicit column type" — `recoverCellError` words the hint
differently). `TestTypeOverrideMakesEveryLaneAgree`: exec, record and
typed × csv/tsv/jsonl all give 1002 rows / 501502.5.

TSV was the third item: `parseTSVValue` typed each value on its own, so
it never erred — it produced a mixed column, and `""` for an empty
cell. `readCSVRows` split into `readRows(rowReader, …)` and
`tsvRowReader` (header fixes the separator, no quoting, blank lines
skipped, row slice reused — readRows clones what it keeps for the
sample) is the second implementation of that interface. One typing
implementation for both formats. `int_first_tsv_floats_survive` joins
the equivalence corpus.

The union/merge side-file item (TODO 2026-09-04) turned out to be
bigger than "use the schema-aware reader": the first codegen test of a
regular-file union or merge found neither template had ever compiled.
Union's generated code referenced `ctx.Stderr()`; merge inlined the
`os.Open` + read into a stmt fragment, which the assembler treats as a
filter expression (`extractFilter` strips the first `X :=` and applies
`(records)`) — the sabotage run with the v4.90.0 binary died at `go
build`. Merge now emits an init fragment per side file plus a filter
closure, union's shape. Noted the sibling: join's record right-side
reader does `if err != nil { return nil }` — a missing right file is an
empty join with exit 0. In TODO.

Lessons for the file: (1) "fails loudly in exec" says nothing about the
compiled lanes — the equivalence gate compares OUTPUTS of pipelines
that succeed; a lane that exits 0 with a different row count only
diverges if a case's data has a late mismatch, and none did. The
readers_loud tests assert exit status and message per lane, which the
equivalence normaliser cannot. (2) Whenever an error message names a
remedy, the remedy needs a test in every lane the error can appear in —
the `-type` advice was three-lanes-wide and one-lane-true. (3) A panic
in a worker goroutine is not "loud" — it is a crash; recover has to be
where the caller can see it.

`limit 0` thread: Ross explained the dial use (journal W33) and asked
about a bare `limit` meaning "no limit". My view, given: prefer bare
`limit` as the dial and `limit 0` as SQL's zero rows (header-only reads,
DuckDB agrees); changing it is a CHANGELOG-worthy semantics change.
Untouched pending his call.

## 2026-09-07 (Mon) — three decisions Ross recalled from a killed session: limit dial, typed empties, join swallow

Ross remembered agreeing to these in a session that died before it
journaled; nothing in the transcripts or journals recorded them, so
they were re-stated and built:

**`limit` / `sample` dial.** Bare `limit` (no N) and bare `sample` (no
N, no `-percent`) pass everything through and emit no fragment; `limit
0` is SQL's LIMIT 0 (no records — header-only `to csv`) and `sample 0`
keeps no rows (USING SAMPLE 0 ROWS). Until now `limit 0`/`sample 0`
were the dials (W33), which collided with SQL and `head -n 0`; the
dial is now "delete the number". N carries Default(-1) as the
not-given marker (sample already did). `translateSample` lost its
`n == "0"` skip. Tests flipped: `TestBareLimitSkipsGeneration` (bare
stages vanish from go/sql/ssql in both modes; `limit 0` must appear
as Limit / LIMIT 0 / `ssql limit 0`), equivalence
`limit_bare_passthrough`, `limit_zero_is_empty` (Golden `{}`),
`sample_bare_passthrough`, `sample_zero_is_empty`. Gotcha: DuckDB
1.5.0 prints the malformed `[{]` for an empty `-json` result — the
duckdb lane now reads that as zero rows. DFC110 amended (both the
convention and the workspace's `limit 100000 | sample 1000` window,
whose whole-file dial is now the bare `limit`).

**Typed empties (DFC124 (a)).** Ross: "add an error check to typed
provided it doesn't slow things down too much." An empty cell in a
non-pointer, non-string typed field is now a fatal `ReadError` via
the existing row wrapper — `column "Age": "" is not int64` — from
every typed reader (CSV, parallel, delim; the JSONL positional decoder
shares `decoderFor`, so `"v": ""` into an int field errors too; JSON
`null` is unchanged). Zero cost: the decoders already branched on
`s == ""`, the branch now returns `errEmptyCell` instead of writing 0.
`*T` fields still take nil, `string` keeps `""`. Pointer inference for
partially-empty columns stays future work; remedies documented

became `TestReadCSVEmptyCellIsLoud`; typed-reference and the DFC124

iter.Seq and died on "invalid memory address or nil pointer
dereference" instead of the open error (so the old behaviour was a
confusing crash, not the silent exit 0 I had written in the TODO —
corrected). The rewrite is now `panic(err)` (main's recover prints

## 2026-09-08 (Tue) — expr: field when bare, function when called

Ross: "what to do about the date problem in expr?" → recommended, he
agreed. Root cause: expr's type checker resolves a bare identifier to a
builtin (`date`, `len`, `type`, `max`…) when the compile environment
does not declare it — and ours cannot, it knows no field names
(AllowUndefinedVariables). So `date > "…"` refused to compile while
`date(date)` worked (the call parses to a BuiltinNode; the argument
resolves at run time). The Go transpiler never had the problem: every
bare identifier is a struct field, only a call position is a function
— so the VM lane was the divergent one.

Fix: `ssql.ExprFieldShadowing()` (expr_shadow.go) — an `expr.Patch`
visitor (same hook as the aggregation patcher) that rewrites a bare
IdentifierNode whose name is in `builtin.Names` (71 of them) to the
MemberNode `$env["name"]`; calls are BuiltinNodes and untouched.
Passed at every compile site: runtime.CompileExpr / CompileExprEnv and
the three expr_agg.go sites. `extractIdentifiers` (first-record field
validation) learned the `$env["x"]` form via `ssql.ExprFieldName`, so a
