## 2026-11-09 (Mon) — `generate rust` writes JSON and JSONL files

Ross: "add the rust jsonl and json file sinks". This follows the CSV/TSV sinks from yesterday
(W45, f8cc916e). `rustJSONSink` (`cmd/ssql/commands/sink_output.go`) writes through Arrow's
JSON writer:
- `to jsonl`, and no sink at all, use `LineDelimitedWriter`: a null is left out, and no rows
  gives an empty file, as exec writes it.
- `to json` uses `ArrayWriter` with explicit nulls, so every key is in every object, and no rows
  gives `[]\n`, as exec writes it. The difference is that exec indents the array and Arrow does
  not.
- Both write to stdout or to a file. A file that can't be created is named in the error.

The CSV and JSON sinks now share `rustSinkWriter`, which opens stdout or the file, and the batch
loop.

A time now has its `Z`, in JSONL on stdout as well. Before, Arrow wrote
`2024-03-05T01:02:03` with no `Z`, which any reader but ssql takes as local time. The rust lane
is unaffected, because its harness (`equivalence_rust_test.go`) has its own writer. Floats are
spelled `1.0e20` where exec writes `1e+20`; this is added to the float-spelling TODO item.

Found on the way: `rustMain`'s `default:` branch printed JSONL for every sink it didn't know.
That included `to json` and stdout `to markdown`/`to lines`, all exit 0. A parquet with no
file would have done the same, but exec requires the file anyway. `rustRefuseSink` now lists
what the program writes (table; csv, tsv, json and jsonl to stdout or a file; parquet to a
file) and refuses everything else.

Tests:
- `TestGenerateRustWritesTheSinkFile` gains `json`, `jsonl` and `stdout_json` subtests. They
  check that:
  - the rows read back equal exec's file;
  - the JSONL bytes equal exec's, and the JSON parses to the same value as exec's (`sameJSON`),
    on the columns spelled the same;
  - a UTC time carries its `Z`;
  - no rows matches exec byte for byte.

  The byte checks also leave out `s`: DataFusion reads an empty CSV cell as null, exec as "".
  The reader decides that, not the sink.
- `unwritable` covers json too.
- `TestSinkFileIsWrittenOrRefused`: `rust_jsonl` moved from refused to written, and stdout
  `to markdown` and `to xlsx` are refused.

Watched fail: with the time format removed from the JSON builder, the `Z` checks failed in both
kinds. With `to json` sent back to the JSONL default, the array, no-rows and stdout checks
failed.

Gates: vet; the sink, no-trace, interchange and Rust-run tests with `SSQL_RUST_LANE=1` (green);
the full suite and doc-check.

## 2026-11-10 (Tue) — `generate rust`: pinned dependencies, `-run` at opt-level 0; DFC166

Ross asked whether `generate rust -run` should compile at minimal optimisation, then "measure it",
then "do 1 and 2" (the pinned lock and opt 0 for `-run`). Along the way he asked why DataFusion
kept being rebuilt, and why the Rust binary has so much sys time. The last became DFC166.

**DataFusion rebuilt for minutes, again and again.** While I was measuring, Ross's own run was
recompiling DataFusion. Each crate had no `Cargo.lock`, so cargo resolved the newest compatible
version of all ~280 dependencies, and a patch release anywhere changed every hash above it:
`itoa`, `syn` and `uuid` that morning at 07:33, `fixedbitset` the day before. The cache held ten
builds of the same DataFusion 55.2.0, 9 GB in all.

The fix:
- `cmd/ssql/commands/rust_cargo.lock` is embedded in ssql. `RustCargoLock(pkg)` renames its root
  `ssqlgen` package, and every build uses `--locked`.
- The rust lane now builds with the same `RustCargoToml` and lock: its own copy of the manifest
  is deleted.
- `TestRustCargoLock` checks the lock's shape and that a renamed root still sorts where cargo
  writes it. `--locked` refuses a lock that would change on rewrite, and both a `ssqlgen_<n>`
  and a `ssqllane` root are accepted. `SSQL_RUST_LOCK_UPDATE=1` regenerates the lock.
- I deleted `target/` (9 GB). After one DataFusion build (4 m 33 s), the lanes and the Rust tests
  left exactly one DataFusion build, 1.5 GB.

**opt-level 0 for `-run`.** The program builds a plan, and DataFusion, still at opt 3, does the
work. Across the bench's pipelines, compile falls from 6–16 s to 2–6 s with equal run times. The
exception is Arrow's CSV writer: it is generic over its output, so it is compiled in the program,
and a 14.6 M-row CSV file takes 9.07 s against 3.98 s. The JSON writer's encoders are not
generic, so JSONL is unaffected.

A helper crate at opt 3 holding the CSV sink got that to 6.0 s. The same program at opt 3 ran in
3.93 s, so the boxed writer costs nothing, and about 2 s is other library code instantiated in
the program. I couldn't profile it: `perf_event_paranoid` is 4. `-build` stays at opt 3, and
`TestRustCargoTomlOptLevel` pins both. The table is in DFC157 §3.4; the CSV writer is in TODO.

**DFC166: where the sys time goes.** On the lookup program, Rust took 1.31 M minor faults and 3.6 s
of sys; Go took 84 k faults and 0.74 s. RSS split from `/proc/PID/status`: Go's heap peaks at
65 MB, and its other 1.15 GB is the input, memory-mapped. Rust's heap peaks at 3.6 GB, every page
faulted in at 4 KB. Go with `GOGC=off` grows to 2.3 GB of heap and its sys more than doubles, the
same mechanism. glibc settings:
- No trimming: changed nothing.
- `hugetlb=1`: 494 MB in huge pages, wall 2.30 → 1.77 s.

mimalloc (built in a separate target with the pinned versions) put 4.37 GB in 2 MB pages:
10–48 k faults, sys 1.4 s, wall 1.37 s, 0.8 GB more memory. Adopting it is in TODO, along with
why DataFusion's heap is 3.6 GB at all.

DFC166 is published as a private page for Ross to share:
https://claude.ai/artifact/TSo54HcHhFjwazefKGV7tz

Gotchas:
- My first measurement pass used the wrong bench cache path: I had hashed the path without the
  trailing newline that `echo` adds. The program exits fast and "same" on an empty input, so the
  script now treats a non-zero exit as a failure.
- `smaps_rollup` has no `RssAnon`; `/proc/PID/status` has it.
- My measurement crates left 4 GB in the shared cache, removed by package name afterwards.

## 2026-11-10 (Tue) — `generate pretty`; `-script` backslash continuations

Ross: "a generate mode that writes out a ssql pipeline in a 'pretty format' - one ssql command to
a line and breaking long lines so they always fit in 80 columns. The output should be runable as a
bash pipeline". He chose the pipeline as written, not the optimiser's rewrite, as a new
`generate pretty`, and a `|` at the end of each line rather than at the start of the next.

`cmd/ssql/commands/generate_pretty.go` works from the pipeline document (`generate json`'s
`pipelineDocFromFragments`): each stage's own argv, a process substitution as a nested pipeline.
It applies the as-written restore first (`dropResolvedZone`, `restoreAsWritten`), so no `-tz`
appears that wasn't typed.

The layout:
- Stages after the first are indented two; continuation lines end in a backslash and are
  indented two more.
- A stage breaks where one of its clauses starts. That is decided from the stage's own declared
  flag names and clause separators (`cf.Subcommand.Flags`, `.Separators`), not by guessing from
  the text.
- A clause too long for a line breaks between words, and the clause after it starts a fresh line.
- A process substitution that doesn't fit is laid out inside its `<(…)`, its stages aligned under
  the first.

A newline after `|` and a backslash-newline never change the words bash passes, so the layout
can't change what runs; the flag lookup only decides where the breaks read best. The one thing
that can't fit is an argument longer than a line, such as a quoted expression. Its line runs
over, and stderr names it.

Found on the way: `preprocessScript` (behind `-script` and `-pipeline`) joined lines with a space
and kept a trailing backslash, which then escaped the space. Pretty output fed back failed with
`update` receiving `" -set-expr"`, and so would any hand-written script with backslash
continuations. `continuesLine` now drops a backslash that ends a line outside quotes, unescaped.
`TestPreprocessScript` (the function had no test) failed on both continuation cases with the fix
off.

`TestGeneratePretty` runs 5 pipelines at widths 40, 60 and 80. Each must:
- give the same `generate json` document from the pretty text as from the original, through both
  `-pipeline` and `-script`;
- lay itself out unchanged;
- produce the same output under bash;
- keep one stage per line;
- have every line over the width named by the warning, holding only that argument.

Watched fail: with the continuation backslash dropped from the layout, bash ran `-using` as a
command.
