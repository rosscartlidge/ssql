### WASM Module for In-Browser Data Transformations - Phase 5

Added a WebAssembly module that exposes ssql data operations to JavaScript, enabling the `to explore` data explorer to run real ssql transforms client-side instead of reimplementing them in JS.

**Architecture:**
- WASM module registers 6 global JS functions via `syscall/js`
- Explorer HTML inlines the JS runtime (~21KB), loads `ssql.wasm` (~15MB raw, ~3MB gzip) via fetch
- Falls back to JS aggregation if WASM fails to load
- Green "WASM" badge appears in explorer header when module is active

**New files:**
- `cmd/ssql-wasm/main.go` - WASM entry point, registers ssqlWhere/Sort/GroupBy/Distinct/Limit/Pipeline
- `cmd/ssql-wasm/bridge.go` - JSON↔Record conversion using ReadJSONFastFromReader + AppendJSON
- `cmd/ssql-wasm/operators.go` - Thin wrappers around ssql.Where, SortBy, GroupByFields, Aggregate, DistinctBy, Limit, Offset
- `cmd/ssql-wasm/js/ssql-wasm.js` - JS wrapper class (SsqlWasm) with clean API

**Modified files:**
- `chart.go` - Added WasmEnabled/WasmExecJS/SsqlWasmJS to ExploreConfig; template inlines JS when WASM enabled; aggregation uses WASM with JS fallback; added CopyExploreWasmFile()
- `cmd/ssql/commands/to.go` - Added `-wasm` flag to `to explore`; loads JS files and copies ssql.wasm alongside HTML
- `Makefile` - Added `wasm` target (GOOS=js GOARCH=wasm build + wasm_exec.js copy)
- `.gitignore` - Added WASM build artifacts

**Design decisions:**
- Build-tagged files (`//go:build js && wasm`) so `go build ./...` excludes WASM package
- JS files inlined in HTML template (small enough at ~21KB) to avoid extra file management
- Only `ssql.wasm` binary copied as separate file (15MB too large to inline)
- Comparison operators duplicated from CLI helpers.go (can't import `commands` package from WASM `main`)

**CLI usage:**
```bash
make wasm
ssql from data.csv | ssql to explore -wasm cmd/ssql-wasm/ssql.wasm output.html
```

### Distributed SSH Processing Design Document

Created research document exploring how ssql can support distributed processing — running pipelines where the data lives and streaming only results back locally.

**Key design insights:**
- `from -- ssh server 'ssql ...'` already works as a degenerate case
- JSONL schema headers are already the wire format between pipeline stages
- Process substitution in `join` is structurally identical to remote data sources
- SSH provides auth, encryption, multiplexing with zero new infrastructure

**Proposed features:**
- `ssh://` URL syntax for `from` and `join` (sugar over `from -- ssh`)
- `--remote` flag for explicit pipeline push-down (filter/aggregate on server)
- GPU auto-detection on remote hosts (`ssql_gpu` vs `ssql`)
- 5 implementation phases from basic URL support to connection optimization

### Fix: `-format` Flag Ignored for File Arguments

Bug: `ssql from -format csv <(cat kind.csv)` produced no output, while `cat kind.csv | ssql from -format csv` worked fine.

**Root cause (two issues):**
1. `-format` flag only applied to stdin mode. When FILE was provided (e.g. `/dev/fd/63` from process substitution), only extension detection was used. No extension → fell through to JSON reader → silent empty output.
2. CSV case called `readCSVHeaders(inputFile)` then `ReadCSV(inputFile)` — two separate `os.Open` calls. For pipes, the first consumed the header and the second got an empty stream.

**Fix:**
- Added `effectiveFormat` logic: checks `-format` flag first, falls back to extension detection
- CSV/TSV cases now open file once and use `FromReader` variants
- For CSV, uses `Seek(0,0)` to detect seekable files for header ordering; pipes skip ordering but read correctly
- Updated `-format` help text to indicate it works for files too
- Added error for unrecognized `-format` values

**Modified files:**
- `cmd/ssql/commands/from.go` - Refactored file reading to respect `-format` flag

**Commits:**
- `ba57579` - fix: -format flag now works with file arguments and process substitution
