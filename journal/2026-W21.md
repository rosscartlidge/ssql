# Week 21, 2026

The autocli-shell stack from W19/W20 finally got a feature that
isn't a bug fix: `:set` is now alive again, this time as a generic
service-supplied registry rather than the dead vi/emacs toggle it
became after the x/term migration.

## 2026-05-18 (Monday)

### `:set` resurrected as a generic registry (v4.44.5, commits 0d8a924 / bc20f82 / 62ba239)

User question after Friday's x/term migration: "so does `:set` have
any use now?"

Honest answer: no. Its only purpose was switching vi/emacs, which
x/term doesn't support, so the command was vestigial. Three
options sketched (remove, deprecate-and-print, or repurpose). User
picked the third: turn `:set` into a service-supplied registry.

### Three-layer ship

**autocli/shell v0.2.1 — Setting type + rewritten dispatch.**

```go
type Setting struct {
    Name        string
    Description string
    Get         func() string
    Set         func(value string) error
}

type Options struct {
    ...
    Settings []Setting
}
```

Operators get:

```
> :set                    list all settings + current values
> :set NAME               show one
> :set NAME VALUE ...     write
```

`Setting.Set` returning an error surfaces to the operator without
ending the session. Concurrent reads/writes across sessions are
the service's responsibility (closures must lock if needed).

The old `:set vi`/`:set emacs` hardcoding is gone — those words
now hit the unknown-setting error path. Backward-compat scaffolding
deleted; x/term migration in v0.2.0 had already made them no-ops.

**autocli/ssh v0.1.10 — Options.Settings pass-through.**

`autocli/ssh.Options` gains a `Settings []shell.Setting` field; the
per-session handler copies it into `shell.Options.Settings`. Same
closures shared across all sessions on the server (and concurrent
reads/writes touch the same underlying value).

**ssql v4.44.5 — first real setting wired: head-default-rows.**

`serveState.headDefault atomic.Int64` initialised to 10. The
`head` subcommand's `-n` flag default changed to -1 (sentinel for
"use the setting"); handler detects the sentinel and falls back to
`srv.headDefault.Load()`. Explicit `-n N` still overrides.

```
> :set
  head-default-rows = 10
                      (default row count for `head` when -n isn't passed)
> :set head-default-rows 3
head-default-rows = 3
> head                          # 3 rows
> head -n 5                     # explicit -n overrides → 5 rows
> :set head-default-rows bogus
:set head-default-rows: must be an integer, got "bogus"
> _                             # session continues
```

Future settings (verbose, reload-interval, log-level, etc.) plug
into `buildServeSettings(srv)` by appending another `shell.Setting`
with Get/Set closures. The interface is service-extensible —
operators get a discoverable runtime knob mechanism for free.

### Still on the list

The W20 evening follow-ups still stand minus chzyer/readline
(retired by the x/term migration):

- **SSH window-size propagation** — autocli/ssh accepts
  window-change requests but doesn't surface them to readline's
  SetSize. Lines wrap at 80.
- **Pipes in autocli/shell (Position 2)** — `from-loaded | where ...
  | to table` at the prompt.
- **`let $name = pipeline` variables** — REPL-natural replacement
  for bash process substitution.
- **Position 3 in-process composition** — full perf, no JSONL
  serialization between stages.
- **Schema-aware completion** — TAB on `head -if <TAB>` should
  complete loaded field names.
- **Kube-style two-signal shutdown** — second Ctrl-C escalates to
  force-close. Currently every ctx-cancel force-closes; opt-out
  not yet exposed.

The chzyer/readline upstream PR is no longer needed — we don't
depend on the library any more.

### Reflection on the W19-W21 arc

Three-and-a-half weeks ago I shipped the first autocli-shell
proposal (W19 Tue). Three days later: Phase A-D shipped, smoke-
tested, documented. Then the polish wave: nine user-reported
issues across three days, three of them all the same root cause
(chzyer/readline assumes os.Stdin), one migration that retired the
class. Total: 13 user-visible issues found and fixed, two library
migrations (autocli/shell got two), one `:set` feature added,
~1500 lines of documentation.

What worked well:
- Iterative ship-test-fix loop with short cycles.
- Treating each user report as a real signal, not noise.
- After bug #3 of the same shape, stopping to ask "is the
  dependency wrong?"

What I'd do differently:
- Migration after bug #2 not bug #3. The pattern was visible
  earlier than I committed to acting on it.
- Better integration tests for SSH-channel-side termios behaviour.
  All three chzyer/readline bugs would have been caught by tests
  that ran the server in raw-terminal mode with stty inspection
  from another process — that test didn't exist.

## 2026-05-20 (Wednesday)

### Position 2 pipes — ssql v4.45.0 + shell v0.3.1

Final shape of the feature that's been brewing for a week: operators
in `ssql serve` can now compose pipelines just like at the bash
prompt. `from-loaded | where -if dept eq Engineering | to table`
just works, plus all the standard transforms (count, limit, sort,
group-by, pivot, window, …) on top of the in-memory dataset.

shell v0.3.0 (yesterday) carried the bones — splitOnPipe +
runPipeline + io.Pipe between stages. Today's session was the long
tail of "actually run real pipelines and see what breaks". Five
real bugs surfaced:

1. **`to table` produced no output in serve pipes.** Root cause:
   `ssql.DisplayTable` / `DisplayTableWithFields` hardcoded
   os.Stdout. Fix: added writer-accepting `*To` variants in io.go,
   existing functions delegate. to_table.go now passes
   `ctx.Stdout()`.

2. **Early-exit pipelines erred with "io: read/write on closed
   pipe".** `... | limit 3 | to table` finishes after `limit`
   stops reading; upstream sort/from-loaded hit closed write ends.
   Fix in shell.runPipeline: errors.Is(err, io.ErrClosedPipe)
   gets suppressed — Unix SIGPIPE convention.

3. **Tab completion after `|` was useless** — it offered the
   upstream command's flags, not the next stage's subcommands.
   Fix in tabComplete: slice args after the last `|`.

4. **Ctrl-C killed the SSH session instead of cancelling the
   line.** Tricky one. x/term returns io.EOF on Ctrl-C *without*
   consuming the 0x03 from its remainder buffer, so the NEXT
   ReadLine sees the stuck 0x03 and returns io.EOF again. Our
   first fix (sniff 0x03 in the reader, check after EOF) handled
   the first Ctrl-C but session still exited on the second
   ReadLine because no read happened to set the flag. Final fix:
   ctrlCReader translates 0x03 → 0x0d in-stream so x/term sees
   Enter, returns the partial line, resets cleanly. Loop checks
   consumeCtrlC after each ReadLine and discards the line with
   a ^C banner.

5. **Bare transforms hung the session.** Typing `where -if ...`
   without a `from-loaded |` upstream was wiring opts.Stdin (the
   keyboard) into the command's stdin — so `where` would happily
   eat your next keystrokes waiting for JSONL. Fix: single
   commands and pipeline stage 0 read from `bytes.NewReader(nil)`.
   Bare transforms now degrade to zero-record processing — same
   as `where < /dev/null` at the bash prompt.

The completion question got a richer answer than the immediate
fix. After `from-loaded | group-by <tab>` the operator naturally
wants schema-aware suggestions ("name, dept, salary"). The shell
*can* do this (full pipeline visibility); bash can't (per-stage
isolation). Discussion landed on a clean design for both: a
fourth fragment-generation mode, `SSQLGO=schema`, that runs the
upstream pipeline through fragments-without-data and emits the
cumulative schema. bash completion can `eval` it; the autocli
shell runs the same fragments in-process. Same fragment table
that drives generate go / generate sql / generate ssql — single
source of truth. Deferred to a follow-up session (TODO logged).
