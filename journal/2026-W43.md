# Journal 2026-W43

## 2026-10-22 (Thu) — hash(n[, seed]) in every lane; the digests reach SQL and typed Go

Ross asked what the queued "seeded hash(n)" TODO was for and how it
differed from `md5`/`sha1`/`sha256`, then "lets do the seeded hash(n)
and the md5 sql translation". The difference: the digests take a
string and give hex, exist only in the VM (`generate sql` refused
them, the typed lane fell back to the interpreter) and cost a
cryptographic hash per row; a fixture over `from range` wants an
INTEGER it can bucket (`hash(n) % 10`) that every lane computes
identically, cheaply.

**Design (DFC154 §6, now annotated).** Not FNV — a byte loop has no
SQL form. `exprfn.Hash(n, seed)` is lowbias32 (Wellons 2022: xorshift
16, ×0x21f0aaad, xorshift 15, ×0x735a2d97, xorshift 15) over the
input's low word xor high word, with `(fold(seed) + 1) * 0x27d4eb2f`
xored in first. Chosen for its SQL: both multipliers are below 2^31
and every operand below 2^32, so `&`, `>>`, `*` and xor on a BIGINT
never overflow the signed 64-bit arithmetic DuckDB, Postgres and
DataFusion all raise on (`generate_sql_hash.go`; xor is `xor()` on
DuckDB and `#` elsewhere, the only dialect difference). The cost is
text: each xorshift repeats its operand, so the argument appears 16
times — fine over a column, which is the use. A literal seed, negated
or not, folds to its constant. Catalog `hash` category, EXPRESSIONS.md
"Hash Functions", a codelab block (1000 rows into 10 keys with
realistic counts), CHANGELOG, TODO ticked.

**The DuckDB lane caught a typing bug on its first run.** Exec, Python
oracle, record, typed and parallel agreed on every row including
int64 extremes; DuckDB disagreed on `hash(n, -3)` only. The literal
`-3` is a 32-bit INTEGER in DuckDB and a shift by 32 on it is 0, so
the fold lost the high word. Fix: `sqlFold32` casts its operand to
BIGINT (a column could be INTEGER too). Then "a gate you haven't
watched fail": one multiplier nudged in the SQL renderer made
`hash_every_lane` report the duckdb lane's disagreement, restored.

**Digests.** One implementation in `exprfn` (`MD5`, `SHA1`, `SHA256`)
behind the runtime helpers and the typed transpiler; SQL is each
engine's own — DuckDB by name, Postgres `md5` and
`encode(sha256(convert_to(s,'UTF8')),'hex')` with `sha1` refused by
design (pgcrypto), DataFusion `md5` and `encode(shaN(s),'hex')`. The
DataFusion and Postgres forms are written to their documented shape;
neither lane is configured in this shell, so the rig verifies them.
Cases `expr_digests`, `expr_sha1` (Skip postgres), Goldens from
hashlib; `TestHash` vectors from the Python oracle; `TestHashSQL` per
dialect; transpiler rows and the differential corpus.

Gates: vet, slim build, root/exprfn/typed/lib/runtime/sshgo/commands
under -race, doc-test L1+L2 green; the full `cmd/ssql` package (1056 s)
failed only `TestTierVKeepsTypedPipeline`, whose canonical "expression
outside the native subset" was `sha256(city)` — now native, so the
