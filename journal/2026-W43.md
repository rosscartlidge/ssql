## 2026-10-22 (Thu) — hash(n[, seed]) in every lane; the digests reach SQL and typed Go

Ross asked what the queued "seeded hash(n)" TODO was for and how it
differed from `md5`/`sha1`/`sha256`, then "lets do the seeded hash(n)
and the md5 sql translation". The difference: the digests take a
string and give hex, exist only in the VM (`generate sql` refused
them, the typed lane fell back to the interpreter) and cost a
cryptographic hash per row; a fixture over `from range` wants an
INTEGER it can bucket (`hash(n) % 10`) that every lane computes
identically, cheaply.

**Design (DFC154 §6, now annotated).** Not FNV — a byte loop has no
SQL form. `exprfn.Hash(n, seed)` is lowbias32 (Wellons 2022: xorshift
16, ×0x21f0aaad, xorshift 15, ×0x735a2d97, xorshift 15) over the
input's low word xor high word, with `(fold(seed) + 1) * 0x27d4eb2f`
xored in first. Chosen for its SQL: both multipliers are below 2^31
and every operand below 2^32, so `&`, `>>`, `*` and xor on a BIGINT
never overflow the signed 64-bit arithmetic DuckDB, Postgres and
DataFusion all raise on (`generate_sql_hash.go`; xor is `xor()` on
DuckDB and `#` elsewhere, the only dialect difference). The cost is
text: each xorshift repeats its operand, so the argument appears 16
times — fine over a column, which is the use. A literal seed, negated
or not, folds to its constant. Catalog `hash` category, EXPRESSIONS.md
"Hash Functions", a codelab block (1000 rows into 10 keys with
realistic counts), CHANGELOG, TODO ticked.

**The DuckDB lane caught a typing bug on its first run.** Exec, Python
oracle, record, typed and parallel agreed on every row including
int64 extremes; DuckDB disagreed on `hash(n, -3)` only. The literal
`-3` is a 32-bit INTEGER in DuckDB and a shift by 32 on it is 0, so
the fold lost the high word. Fix: `sqlFold32` casts its operand to
BIGINT (a column could be INTEGER too). Then "a gate you haven't
watched fail": one multiplier nudged in the SQL renderer made
`hash_every_lane` report the duckdb lane's disagreement, restored.

**Digests.** One implementation in `exprfn` (`MD5`, `SHA1`, `SHA256`)
behind the runtime helpers and the typed transpiler; SQL is each
engine's own — DuckDB by name, Postgres `md5` and
`encode(sha256(convert_to(s,'UTF8')),'hex')` with `sha1` refused by
design (pgcrypto), DataFusion `md5` and `encode(shaN(s),'hex')`. The
DataFusion and Postgres forms are written to their documented shape;
neither lane is configured in this shell, so the rig verifies them.
Cases `expr_digests`, `expr_sha1` (Skip postgres), Goldens from
hashlib; `TestHash` vectors from the Python oracle; `TestHashSQL` per
dialect; transpiler rows and the differential corpus.

Gates: vet, slim build, root/exprfn/typed/lib/runtime/sshgo/commands
under -race, doc-test L1+L2 green; the full `cmd/ssql` package (1056 s)
failed only `TestTierVKeepsTypedPipeline`, whose canonical "expression
outside the native subset" was `sha256(city)` — now native, so the
tier-V and record-fallback assertions had nothing to fall back on. It
uses `replaceRegex`, the one VM-only helper left; green in isolation.

## 2026-10-22 (Thu) — DFC155: big numbers, a survey

Ross, after the Fibonacci fold: "we dont support BigInts or BigFloats
— I am not sure that we should but its worth investigating. What is
duckdb's support? Lets write a DFC on our options." Measured rather
than recalled, on DuckDB 1.5.0 and on v4.122.0 in every lane
(`doc/research/dfc155_big_numbers.md`). The finding that matters is
not capacity but correctness: an int64 `+`/`*` that overflows wraps
silently in exec, record and typed and raises in DuckDB (Postgres and
DataFusion raise too) — a lane divergence `TestPipelineEquivalence`
has never seen because no fixture overflows; and `-sum` of integers
accumulates a float64, exact to 2^53, where DuckDB widens to HUGEINT.
DuckDB's own support: `HUGEINT` is native 128-bit and checked (fib to
186); `BIGNUM` (the renamed VARINT) is arbitrary precision for `+ -
sum max` but `* // % **` return DOUBLE, so it is half a type;
`DECIMAL(38, s)` exact for `+ - *`, DOUBLE on `/`; CSV/JSON readers
infer DOUBLE for a wide literal exactly as ssql does; no big float.
Options A–F with costs; recommendation: loud int64 overflow in every
lane now (expr `Operator` overloading in the VM, `exprfn.Add` in the
transpiler, nothing in SQL — a day), int128 or scaled-int64 decimals
only when a use asks, big floats never. TODO carries the DECIDE item.

## 2026-10-22 (Thu) — DFC155 costed: performance and code per option

Ross asked for each option's cost on existing code and in code to write;
measured rather than guessed (`doc/research/dfc155_big_numbers.md` §3,
commit after 21b17e0). A scratch micro-benchmark (3-op expression): plain
int64 0.85 ns, overflow-checked 2.3 ns, int128 struct 1.0 ns, `math/big`
205 ns and 5 allocs in the Record shape; the expr VM 290 ns alone, 350 ns
with `+ - *` patched to checked calls (+1 alloc per operator from boxing).
Real pipeline, 2M rows of `from range | update -set-expr | to jsonl`:
exec/record 2.4 µs per row for the update step, typed 0.85 µs per whole
row — so B's check is +2.5% of the update step in the VM lanes and under
0.2% in typed; nothing elsewhere.

Gotcha that changes B's design: `expr.Operator` overloading does NOT fire
on ssql's untyped `map[string]any` env (`runtime.go:115`,
`AllowUndefinedVariables`) — `MaxInt64 + 1` wrapped with the overload
installed; it fires only on a typed struct env. An `expr.Patch` visitor
rewriting the BinaryNode to a checked call works (the `expr_agg.go:376`
precedent) and is the one place C/D/E would also route arithmetic. The
DFC's B bullet and the earlier journal line saying "expr `Operator`
overloading" are superseded by this.

Census for C/D/E: 78 `case int64` arms in 36 files, 26 `ParseInt` sites,
31 int-formatting sites, 14 `TypeInt` uses; typed `-sum` casts every
summand to float64 (`typed_groupby.go:462–499`).

## 2026-10-22 (Thu) — DFC155 §C: widen where the engines widen

Ross asked whether C would convert int64 to int128 automatically. The
draft's "promote on overflow" rule cannot be kept by the SQL lane (every
engine raises on BIGINT overflow; matching would mean HUGEINT for every
integer expression) or by typed codegen (a struct field's Go type is
fixed at generation). Settled rule, now in the DFC: a column is int128
because it was declared so — `cast -type int128`, a wide literal in the
source, or `-sum` over int64 (DuckDB's `SUM(BIGINT) → HUGEINT`); mixing
widens; an operator overflow on int64 is B's error. Question 3 answered
the same way: widen the sum once C exists, int64 with loud overflow until
then.

## 2026-10-22 (Thu) — DFC155 B built: integer overflow is an error in every lane

Ross: "ok lets do B" (B before C: under §C's rule an operator overflow
is loud in C too, so B is C's first part). Shape: `exprfn.CheckedAdd/
Sub/Mul` + panicking `Add/Sub/Mul` (tested against math/big); the VM gets
`ExprCheckedIntArithmetic` in `ExprStandardOptions` — an `expr.Patch`
that rewrites `+ - *` into `_ssql_add(a, b)` calls which check an int64
pair and hand everything else to expr's `vm/runtime` operator; the
transpiler emits `exprfn.Add(a, b)` for int pairs and accepts the patched
call (the `-expr` lowering walks a compiled AST); `ssql.Sum`/`Avg` go
through `numericSum` (int64 until a float appears); `-sum`'s wire type is
`int` for an int column (`wireSum`); typed sums, merges and `-expr` terms
through `exprfn.Add`. Gate `TestIntOverflowEveryLane` (new
`cmd/ssql/overflow_test.go`): overflow fails in exec/record/typed/
parallel/DuckDB, and 2^53+1 + 2^53+2 prints `18014398509481987` verbatim
everywhere (the equivalence harness can hold neither: lanes must succeed,
numbers parse as float64).

Gotchas: (1) expr's runtime returns **int** for every integer pair
(`int(x) + int(y)`), so the checked call returns int too or
`TestExprTimeFunctions` sees `8 (int64)`; (2) the identifier walker in
`lib/runtime` counted `_ssql_add` as an unknown field until it learned
`ssql.ExprCheckedArithFunction`; (3) the exact int sum was still printed
as a float because `-sum`'s wire type was `wireFixed("float")` — the
writer coerced it; (4) DuckDB `-json` prints a HUGEINT as a string;
(5) expr's compiler emits `OpDeref` before its own binary operator for an
operand of unknown type but not for a call's variadic parameters, so
`salary - prev` with a nullable lag (`*int64`) failed in the record lane
(`window_lag_nil_guard`) until the checked function dereferences its
operands the way `internal/deref` does — the disassembly
(`Program.Disassemble()`) showed it in one look.
Known gaps in TODO: expr's `sum()` builtin in `-expr`, unary minus of
MinInt64, window/resample float sums. CHANGELOG Unreleased, EXPRESSIONS,
api-reference, CLAUDE.md rule, DFC155 §6.

## 2026-10-22 (Thu) — nested values keep wide integers (found by Ross's fib list)

Ross ran `group-by -stream-expr '{f1:0, f2:1, fs:[]}' '{f1:f2, f2:f2+f1,
fs:concat(fs, [f2])}' fs fib | explode fib` and asked why the output
switched to scientific notation from fib(79). Not B: `ExprValue`
(nested.go), the one parser behind explode, flatten and dotted paths,
decoded JSON with encoding/json (float64) and `normaliseJSONNumbers`
recovered int64 only within ±2^53 — so 2^53+1 exploded to 2^53 (an int,
wrong by one, silently) and anything wider stayed a float. Fixed with
`Decoder.UseNumber` and a `json.Number` arm: an integer literal that
fits is the exact int64, else float64. `JSONString.Parse()` is
unchanged (public, float64 shapes). Gate `TestWideIntegersThroughNestedValues`
(explode, path, flatten; exec/record/typed/parallel); unit test in
nested_test.go. Found on the way: `generate sql` panics on an explode
pipeline fed from stdin (TODO).
