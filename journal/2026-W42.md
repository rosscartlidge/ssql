## 2026-10-12 (Mon) — `to parquet` wrote times as text

Found while recording real output for the walk-through Ross is sending
John (a friend who sent the DuckDB post): the day-partitioned files that
`ssql to parquet` wrote had `date` and `departure_time` as VARCHAR
holding Go's `Time.String()` (`2023-05-15 00:00:00 +0000 UTC`). The
record writer's `goTypeToArrowType` (arrow.go) knew int, float, string
and bool, and took each column's type from the FIRST record, so it also
turned a column null in row 1 into a string (`arrival_time`), truncated
a float that followed an int, and dropped fields first seen later. An
empty input returned before writing, leaving a 0-byte file that the
next reader rejected — that is what an earlier typo in the partition
loop left behind.

Ross: "fix the to parquet bug". `collectForArrow` now types every
column from all its values (null joins anything, int+float → float,
other mixes → string) and from the `_schema` header (`WithColumnTypes`
/ `WithArrowColumnTypes`, which the CLI sinks pass), writes times as
Timestamp(µs, "UTC") — exactly what `typed.WriteParquet` already wrote,
so the lanes produce the same file — and the file is created only after
the records are collected: an empty result with a header writes a valid
zero-row file, no input at all is "nothing to write" with no file.
`wireTypeForArrow` reports timestamp/date as `time` (schema mode said
`string` while the data was a time).

The all-lanes test found that the generated sinks had never compiled:
`to parquet`, `to arrow` and `to wav` printed errors through an
undefined `ctx`, and typed `to parquet` emitted only the Stream form,
which fails after a serial source; it now carries both forms like `to
csv`. Nothing exercised `to parquet` under `generate go` before, which
is how all of this survived. Gates: `TestToParquetTypesAllLanes`
(exec/record/typed/parallel, DuckDB `DESCRIBE` when present, arrow
exec/record; failed on the old code at the exec lane's types and the
record build) and `TestWriteColumnTypes` (library).

Two more bugs surfaced and are logged, not fixed, because they live in
the generated programs' JSONL readers rather than the writer: record
codegen's `ReadJSONAuto` ignores the header's `time` type, and typed
codegen decodes a JSON null into a non-pointer field as its zero value
(`n: null` → `0`; the silent zero DFC124 made fatal for CSV).

## 2026-10-12 (Mon) — the generated programs' JSONL readers: header types and absent values

Ross: "I would rather fix the bugs first" (before DFC148's feature gaps).
The two reader bugs from the `to parquet` fix:

(a) The root `readJSONL` (behind `ReadJSONAuto`, which generated record
programs use for files) parsed a `_schema` header for its field list and
threw the types away, so a tee'd file's `time` column was a string in the
record lane. It now coerces by the header like each stage's stdin reader;
the slot mapping moved into `ssql.SchemaWireTypes`, which
`lib/jsonl.go` now calls instead of its own loop.

(b) Typed JSONL turned an absent value into a zero. The probe showed the
case that matters is not `null` but a missing key: ssql writes an absent
value by omitting the key (`to jsonl`, `tee`), so every tee'd file with
a gap hit it. A plain struct field cannot hold absence; pointer inference
for nullable columns is still the DFC124 §3 slice that ripples through
every typed template. So this takes DFC124's CSV answer: the read fails
naming the line. Because the library documents JSON fields as optional
(encoding/json semantics — and the decoder's own differential test
against encoding/json depends on it), the check is an option,
`typed.RequireValues()`, threaded through every typed JSON reader;
generated programs pass it, library callers keep the old behaviour. It
costs one bit per required field per row (a stack `[4]uint64`).

Gates: `TestJSONLAbsentValueIsLoudInTyped` (missing and null, parallel
and serial reader, record lane equals exec), the record lane of
`TestToParquetTypesAllLanes` (was exec-only), `TestJSONLRequireValues`.
Both CLI tests failed with the fixes reverted. The equivalence corpus's
typed-lane skip reasons for JSONL/CSV absent values said "→ zero value";
they now say the typed reader refuses it.

## 2026-10-13 (Tue) — a null date broke the rows after it

Ross: "a nil date seem to break later exprs", with `ssql run
services.json | limit 10 | update -set-expr time 'date(departure_time)'
| to table`: an Error line, then a full table in which `time` is blank
from the null row on. Four things, found by probing the same fixture
through every lane:

1. `date(nil)` errored ("invalid date <nil>") where every DFC147
   function reads nil as nil (`exprTimeArg`). Now nil.
2. `update`'s error path set `evalErr` and let every later record pass
   through unchanged — the output was thinned, not ended, and exit 1 came
   after a complete-looking table. `stopOnError` ends the stream at the
   failing record; the stage counts its input records and the error
   names it ("record 2: …"). `where` got the same.
3. `where -if-expr` printed "Error evaluating expression", dropped the
   row and exited 0. Now fatal — except a null operand (expr-lang's
   "invalid operation: <nil> > time.Time"), which is "no match" in every
   other lane (SQL NULL, the transpiled Go). `runtime.IsAbsentValueError`
   is the one place that knows expr-lang's wording; `TestIsAbsentValueError`
   pins it against the real VM (and found that `x == "a"` on a nil is
   simply false, no error). The generated record filter (`exprFilter`)
   returned false on EVERY error — a silent drop of the bad rows where
   exec now stops; it panics as exec does, absent → false.
4. A nil expression result was the empty STRING in exec
   (`applyValueToRecord`'s `case nil`) and the text `<nil>` in record
   programs (the type switch's catch-all): `hour(x)` over nulls was a
   mixed column. Both are a nil slot (`mut.Null`) now.

Gates: `date_of_null_update` and `date_of_null_where` in the equivalence
corpus (DuckDB the oracle; typed skipped — it cannot hold a null time),
`TestExprErrorStopsTheStream` (bad and null values through update,
update -if-expr and where; the record lane loud), `TestIsAbsentValueError`,
`TestApplyValueToRecord` re-pinned. The update case failed on the old
code at exec (the error) and the record lane ("<nil>").

## 2026-10-14 (Wed) — DFC149 §4.4: local Parquet shards read in-process

Ross: "now do DFC149 4.4 the local in-process fast path". Per shard
rather than per catalog: `catalogLocalParquet(entry, pushdown)` — a
local host, Parquet by format column or extension, no `--` stages —
sends the shard to `readLocalParquetShard` (`catalog_local.go`), which
is `ReadParquet` + the hive-clash check on the first record + a
`catalogEnricher`. All three shard runners take it: exec's
`ProcessCatalogShards` loop, and `runShardStream`/`runShardCollect`
behind `ProcessCatalogShardsRemoteGo` (generated programs, completion
and catalog order), so a mixed catalog still reads its local Parquet
shards directly. Everything else — remote hosts, CSV shards, pushdown —
keeps the child-ssql path where the shard's ssql owns its format.

The enricher builds one output schema per source schema (a Parquet
file's records share one; keyed by the `*Schema` pointer), copies the
values and appends the metadata; a metadata column that is also a file
column is overwritten in place, as `enrichCatalogRecord` does. That
function ranged `entry.Metadata`, so the column order differed from
record to record and `-catalog-used`'s header shuffled between runs
(the "metadata order randomness" note from 2026-10-13):
`CatalogEntry.Columns` now holds the header order, hive keys appended,
`catalogMetaColumns` gives it to enrichment and `WriteCatalog`.

Numbers: the seven rail files 3.0 s → 0.93 s in exec; the six
500k-row scale partitions (written with `exclude dept`, since the key
must not be a file column — my first split kept it and the fast path
refused every file, correctly) glob read 1.9 s, fast path 2.2 s,
subprocess path 8.9 s. Scale case `catalog-hive-local-fast-path`
(ceiling 6 s, pruned read 2 s; `scaleGenVersion` 3 adds the layout to
the fixture). Unit test `TestCatalogLocalParquetFastPath` with a
`remoteBin` that cannot exist, so a record proves the path; schema
pointer equality across a shard's records pins the #1 rule. A missing

## 2026-10-14 (Tue) — DFC149 §4.6: the SQL lane for `from catalog`

`generate sql` now translates `from catalog` when every pruned shard is
a local Parquet file (`translateCatalogSource` in
`cmd/ssql/commands/generate_sql.go`, DuckDB dialect only). The design
point: ssql expands and prunes the catalog AS THE SQL IS GENERATED,

re-prunes. A `-hive` layout whose metadata is the path's keys alone

metadata column the file also has — is a literal per file, `SELECT *,

…` in record order (`* REPLACE` for the file's own column; the file's
columns come from `ssql.ParquetSchemaFields`, which also raises the
hive-clash error the shard reader would). Metadata columns are
registered in `sqlColumnKinds` as text so a `where` literal on one is
quoted. Refused: another host, another format, `--`, `-catalog-used`,

## 2026-10-14 (Tue) — the aggregation pushdown was wrong over several shards

Measuring what the typed lane would buy for a catalog (answer: a
generated program over a catalog is no faster than the shell pipeline,
about three times slower than the typed program over the same files as
a glob; nobody in library mode has asked), the hive layout failed under
the optimiser: `catalog-aggregation-pushdown` shipped `group-by dept
region` into the shards, where `dept` does not exist, and the shard's
empty `dept` column then hit the hive-clash check. Chasing that showed
the rule was wrong for every catalog with more than one shard: it
pushed the group-by down and DELETED it from the parent, so a key that
spans shards came out once per shard with the shard's metadata column
appended. Wrong since the rule shipped (the codelab's hand-written form
does the re-aggregation itself, so the example was right while the rule
was not), and `run` inherited it yesterday with the optimiser pass. The
`merge -catalog` twin had the same shape. No test had ever exercised
either rule; the single-shard-per-key fixtures that existed were
accidentally right.

Fix (`splitGroupByPushdown`, `cmd/ssql/commands/generate_ssql.go`): the
shard runs a partial group-by over the keys it holds (none means one
row per shard), the parent re-aggregates every key with the merge flag
from the registry — new `aggDef.merge`: -count/-sum partials are summed,
-min/-max take the extreme; -avg, -count-distinct, -collect and the rest
have none, so the rule does not fire; nor for -expr, rollup, cube or any
other flag. Keys that are metadata columns (catalog columns minus range
pairs, hive keys, the shard field — `catalogMetaCols`) are grouped in
the parent only, where the records carry them. The predicate pushdown
got the matching guard: a where that reads a metadata column
(`whereReferences`, structured fields or a word match inside an
expression) stays in the parent. Gates: `TestCatalogAggregationPushdown`
pins six rewrites; equivalence `catalog_pushdown_groupby` (new fixture
`pqcat2.csv`, region north in both files — watched fail: go-record
disagrees with exec), `catalog_hive_pushdown_groupby_key`,
`catalog_pushdown_groupby_avg`. Found on the way, not fixed: a
generated record program with `group-by` on an unknown field emitted an
empty column and exited 0 where exec and `run` stop (TODO).

Gate discipline lesson, again: the full run for the SQL lane came back
with eight 0.4 s failures (`TestScriptFlag_*`, `TestRunKeybinding*`,

## 2026-10-16 (Fri) — `from URL` reads in every lane

Ross: "I just found a problem in go -typed: it doesn't read URLs. do

## 2026-10-21 (Wed) — DFC154 built: `from range N` in every lane

**What exists now.** `ssql from range N [-start S] [-step K] [-field

column name. Noted in DFC154 §9, CLAUDE.md (code-generation rules) and

## 2026-10-21 (Wed) — aggregation results keep their type (Fibonacci fold)

Ross answered the Fibonacci question better than I had: `seq 10 | ssql
from lines | ssql group-by -stream-expr '{f1:1, f2:1, fs:[1]}' '{f1:f2,
f2:f2+f1, fs:concat(fs,[f2])}' 'fs' fib | ssql explode fib`. A fold is a
recurrence, and `-stream-expr` is literally init / every / final; I had
said ssql had no way to see the previous row and reached for Binet's
formula. Checking the fold exposed the ceiling: fib(92) printed as
7540113804746346000 in exec and typed alike, because `aggResult`
(`expr_agg.go`) coerced every numeric result to float64 "as it always
was", and the typed lowering matched it (`asFloat` on the final, a
`float64` result field) for parity. Exact to 2^53, where int64 reaches
2^63.

**The fix is in the type, not the arithmetic.** The VM's state was
already exact; only the result was rounded. `aggResult` now keeps an
int result as int64 (`toInt64`, every width) and a float as float64 —
and since `-min`/`-max`/`-first`/`-last`/`-mode`/`-arg-max` all return
through it, their carried value keeps its width too, which is what the
typed lane (`aggResultGoType`: the source field's type) and the wire
(`aggWireType`) already said. The typed lowering carries
`streamAggPlan.FinalType` and `exprAggPlan.ResultType` into both result
structs (`typed_groupby.go`); `/` still transpiles to a float division,
so the avg fold is unchanged. The exec header was the subtle part: it
said `float` for every expression result before any row existed, and
the NEXT stage reads a column by its declared type, so an exact int64
in the JSON would have been rounded at the pipe boundary.
`writeAggregatedWithExprTypes` (`group_by.go`) pulls the first
aggregated row and types each `-expr`/`-stream-expr` column from its
value (`lib.InferTypeString`): `int`, `float`, `string`, `bool`.

**The gate could not see it.** The equivalence harness unmarshals
every number to float64 (by design, to normalise int-vs-float), so a
Golden of 7540113804746346429 would have "passed" against
7540113804746346000. The two new cases (`groupby_stream_int_exact`,
`groupby_expr_int_exact`) cast the result with `string()` after the
pipe and compare the text. Root tests that pinned `float64(60)` for a
sum of ints, `9.0` for `max(n)`, `float64(7)` for a `Mode` tie and so
on now expect int64; the DuckDB lane skips both by design.

## 2026-10-21 (Wed) — window -stream-expr: the fold per row, and the fold documented

Ross: "how about we add -stream-expr to the window aggregation functions
and also document it properly". The group-by fold answered Fibonacci
with a list and an `explode`; a window makes it one stage, because the
default frame (UNBOUNDED PRECEDING → CURRENT ROW) is exactly a running
fold: `ssql from range 10 | ssql window -stream-expr '{a:0, b:1}'
'{a:b, b:a+b}' 'b' fib` is Fibonacci per row, int64, exact to fib(92).

**One engine for both commands.** `exprFold` (`window_fold.go`) is the
compiled init / every / final fold: INIT compiles on first use, EVERY on
the first step (it needs a record's field names — an unknown field is a
loud compile error, as every expression flag), FINAL on the first
result, all three shared by every group, frame and partition.
`StreamExprAgg` now runs on it — it used to recompile the three programs
for every group. `WStreamExpr(init, every, final)` is the window
function; `aggResult` split into `aggValue` (the typing) so the window's
per-row value gets the same int64 / float64 / string / bool / time /
JSON typing, with nil kept as the absent value (a fold that carries the
previous row has none at the first — `'{prev: nil, cur: nil}' '{prev:
cur, cur: price}' 'prev'` is `-lag price 1`).

**The running frame is O(n), not O(n²).** `computeWindowFunc` is called
per (spec, row) with no carried state, so a fold would restart at the
partition's first row for every row. `Window` now asks
`runningFoldValues` for every fold spec whose frame is the running one
and gets the whole partition in one pass; any other frame (bounded,
following, RANGE, whole partition) re-folds the frame per row, which is
what the semantics say. The typed runtime (`typed.WFold`: Init / Step /
Final closures over a pointer state) does the same split inside
`typed.Window`. `-presorted` streams both shapes: `swFold` carries the
state and resets at the partition boundary; `swSlidingFold` keeps a ring
of the bounded frame and re-folds it (a fold has no Remove).

**Typed lowering reused whole.** `lowerStreamAgg` (the group-by
lowering) gives the state struct fields, the simultaneous EVERY
assignment and FINAL in its own type; `emitTypedWindow` renders a
`<Row>WindowedFold<i>` state struct and a `typed.WFold` spec literal
whose Step is `a := s.(*State); a.x, a.y = …; return a`. Unknown fields
are loud, any other refusal is the record path with its reason. The
exec header types the fold's column from the first row through
`writeJSONLTypedFromFirstRow` (the group-by helper, moved to
`expr_result_types.go` and shared), so a big int survives the pipe.
`generate sql` refuses `-stream-expr` loudly like group-by's; the
optimiser's `extractWindowFields` reports "all fields" for a window with
a fold (it cannot see what the expressions read); schema mode knows the
flag's arity and result position.

**Gates.** Root: running fold, every frame shape against `WSum`/`WFirst`
as the oracle, streaming vs materialised parity, absent/typed results,
loud failures, code/describe. Typed: `TestWindowFold`. Commands: clause
decode, SQL refusal, optimiser, the rendered spec literal (the swap
assignment, a constant FINAL without an unused `a`), a schema-op case.
Equivalence: `window_stream_expr_running` (Golden = the sequence),
`window_stream_expr_frame_matches_sum` (the fold's sum and avg equal
the built-in `-sum`/`-avg` over the same partitioned bounded frame — an
oracle inside the pipeline), `window_stream_expr_presorted`; corpus
`window_stream_expr_every_mode`. DuckDB skips by design.

**Docs.** `doc/EXPRESSIONS.md` has a "Folds" section (the rules:
shadowing, the whole-object swap, result type, group-by vs window
frames, which lanes run it); the codelab shows a level-weighted average
as a group-by fold and Fibonacci as a window fold; `ai-cli-generation`
rows; `api-reference` (`WStreamExpr`, StreamWindow's support);
`typed-reference` (`WFold`). The TODO item "document -stream-expr as the
fold it is" is closed by this.

**The benchmark found a 20% regression that was not the fold.** Ross
asked whether the change costs the other window functions anything; by
inspection it was a nil-map lookup per row. `BenchmarkWindow` against a
HEAD worktree (benchstat, 5 rounds) said otherwise: the materialised
`Window` path was +15–25% time and +3 allocations per row on every
function (lag, lead, sliding sum/min), with `StreamWindow` unchanged.
The alloc profile showed `Record.ToMutable` going from "partial-inline"
to a real call: the fold's precompute pushed `Window`'s closure over the
compiler's big-function threshold, past which it inlines only tiny
callees, and the un-inlined ToMutable in the emission loop heap-allocated
what had been on the stack. Extracting the per-clause work into
`windowResults` (a named function; the closure is now materialise →
compute → emit) restored it: B/op identical to HEAD, time within noise
(geomean +0.5%). Lesson in CLAUDE.md: a hot closure that grows stops
inlining its callees — put the growth in a named function and let the
benchmark say so.
