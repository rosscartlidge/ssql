# Journal — 2026-W44

## 2026-10-26 (Mon) — DFC156: the fold in SQL as a recursive CTE

Ross: "I see that duckdb has recursive CTEs - so it can do our fibonacci
example", then the counter-driven form from the DuckDB docs, then "write
a design DFC and then do it". Measured first (§2 of the DFC): a join to
the source per step is quadratic (20k rows 28 s), the counter form has
no source but still costs ~47 µs a step, and the list form — each
partition aggregated once into an ordered list of its rows, the recursion
indexing it — is linear (20k rows 2.5 s). So: `__parts` builds
`list(s ORDER BY …)` per partition, the anchor is INIT at `__i = 0`
cast to the state's type, the step applies EVERY to the state columns
and `__xs[__i + 1]."col"`, FINAL is read per row (window,
`unnest(__xs[__i])` expands the row) or at `__i = len(__xs)` (group-by,
registry aggregates carried beside the list). DuckDB only; Postgres
(no field access into an anonymous ROW) and DataFusion (lane not
configured) refuse with their reasons. The Fibonacci fold now runs in all
five lanes, HUGEINT to fib(184).

Found on the way: (1) the optimiser's dead-sort rule dropped a `sort`
before a `group-by` with `-first`/`-last`/`-stream-expr`… — those read
arrival order, so the sort was load-bearing in every lane; the flags now
declare group-by an order consumer (`DeclareOrderWhenFlag` takes several
flags per command). (2) The SQL assembler wraps the query before a
group-by whenever an ORDER BY is pending (`needsWrap`), hiding the sort
from the fold: `wrapAsSubquery` carries it as `wrappedOrder`. (3) The
typed lowering's numeric-FINAL rule refused a string fold; the SQL fold
uses `lowerStreamAggAnyFinal`. (4) The harness's quoted-HUGEINT rule
turned a `string(fib)` text column into a number once DuckDB ran the
case; it now applies only in columns exec holds as numbers. Also
`dfc.py --new` died on a non-UTF-8 docsearch hit (`errors="replace"`).

Ross tested the build on his machine straight away ("is it ready to test
on this machine?") with the golden-ratio pipeline through `generate sql`
and found two refusals in a row: the fold's type pass wanted a kind for
every column of the row (`phi`, a `-set-expr` result the assembler cannot
type) where it needs only the columns EVERY reads; and `-lag-default`
without `-order` refused on a `from range` source, whose arrival order
IS its column — the rule the fold already used now serves every window
function (`window_lag_on_range` pins it). Gates on 235a6c6 all green:
vet, slim build, race packages, full `cmd/ssql`, doc-test, triples
258.9 s, scale 60.0 s, explore e2e, playground e2e. Pushed to main; no
release cut (not asked).

## 2026-10-27 (Tue) — DFC155 E: decimals, stage 0–1 (branch dfc155-e)

Ross: "lets pick up E now - cant wait to have decimals :-)". Plan mode
settled three choices with him: the spelling `decimal:S` everywhere
(cast, `-type` on from, the `_schema` header, the typed tag), `/` and
`avg` as float64 (DuckDB's DOUBLE, ssql's int rule), `*` adding the
scales (DuckDB's rule, exact). The rest was measured on DuckDB 1.5.0:
half-away-from-zero rounding on every rescale, `floor/ceil/trunc` at
scale 0, decimal beside DOUBLE is DOUBLE, a float literal `1.5` is
DECIMAL(2,1) there (so generated SQL will cast float literals to DOUBLE),
and DOUBLE→DECIMAL rounds the binary value engine-style (1.005 → 1.00
but 2.675 → 2.68) where ssql rounds the float's shortest form — a
documented divergence; fixtures cast from text. Six technical decisions
in the plan (`~/.claude/plans/peaceful-chasing-teacup.md`): FieldType
ENCODES the scale (`FieldTypeDecimal = 1<<8 | scale`) rather than a side
map, the transpiler carries `exprGo.Scale`, one scale per column with
`Normalized()` hash keys, typed tags gain options (`columnName` splits
at the comma), the Arrow kind encodes the scale the same way, the
harness canonicalises a decimal column's digits.

Stage 0 baselines on HEAD 57b6153 (3 runs): ExprCompare 324–356 ns,
ExprArith 334–363 ns, GroupBySum 187–201 ms, NumericSum 3.4–3.7 ms,
Int128Add 4.5–4.9 ns. Scale budgets ran green on this code yesterday.

Stage 1: `decimal.go` — `Decimal{units Int128; scale uint8}`, the
38-digit bound as `|units| < 10^38`, alignment to the larger scale,
`*` summing scales, half-away rounding on `Rescale`, `Cmp` exact across
scales (an aligned mantissa that overflows 128 bits is already the
larger magnitude, so its sign decides), `String` with the scale's
digits, `Normalized`, JSON bare/quoted, `ParseDecimal` with an exponent
form. Oracle `math/big.Rat` on 200k random pairs + edges. Two things it
found: doubling the remainder for the half-way test overflows near
10^38 (compare against half the divisor instead), and `1 − 1e-38` is an
overflow because `1` at scale 38 is 10^38 units — DuckDB cannot bind
that pair either, so the oracle now expects it. `BenchmarkDecimalAdd`
6.9 ns, `DecimalString` 88 ns.

## 2026-10-27 (Tue) — DFC155 E: decimals, stages 2–7 (branch dfc155-e)

Built in one day on the branch, a commit per stage, every stage's
targeted tests green and the full `cmd/ssql` package green at stages 2
and 4 (19 minutes each). The write-up is DFC155 §8; the short form:

- **Stage 2, exec**: `FieldType` encodes the scale (`FieldTypeDecimal =
  1<<8 | scale`), `ParseWireType` splits a wire name, the doors are all
  declarations (cast, `-type`, header, sidecar), sums accumulate in a
  Decimal at the column's scale, compares are `exactNumCmp`, hash keys
  normalized. `TestDecimalExec` through the binary. GroupBySum and
  ExprCompare unchanged.
- **Stage 3, VM**: `exprDecimalPair` after the int128 pair; a third
  function on `checkedArith`; `decimal()`, decimal `round`/`trunc`,
  patched `floor`/`ceil`. `0.1 + 0.2` as Go constants folds exactly —
  the test needed variables.
- **Stage 4, codegen**: `exprGo.Scale`, `asDec`; `TypedSchemaField.Scale`
  rendered into the tag; `columnName` splits the tag's options; the
  templates carry the scale into every output field. Found: the join
  merge let the RIGHT side's key value win on a collision — invisible
  with integer keys, visible when `1.00` met `1`; the merge keeps the
  left's when equal.
- **Stage 5, SQL + harness**: `DECIMAL(38,S)`/`NUMERIC(38,S)`; float
  literals as `CAST(x AS DOUBLE)` (ends the old `n * 1.5 → DECIMAL(21,1)`
  on DuckDB); `EquivCase.Decimals` compares decimal columns as exact
  digits. First form used a package-level map — the cases run as
  parallel subtests and a sibling's cleanup emptied it; threaded per
  case. The typed window's `-order` comparator emitted `<` on a struct
  (an int128 gap too): `Cmp`. Watched fail: a `String()` dropping a digit
  fails `money_sum_shuffled` against its golden.
- **Stage 6, Parquet/Arrow**: `Decimal128(38,S)` both ways; a DuckDB-
  written `DECIMAL(10,2)` reads back as `decimal:2`.
- **The Postgres lane, on the rig again** (Ross: "we did have a test
  harness for postgres - we should start using it again"): `lxc list`
  showed the three nodes up and PostgreSQL 16 on node1 answering;
  `SSQL_TEST_PG_HOST=ssql-node1` ran the decimal, int128 and hash cases
  — all agreed except `int128_avg_exact`: Postgres's AVG over NUMERIC
  (and over BIGINT) is an exact NUMERIC where every other lane averages
  as a float; `sqlAggAvg` casts it on Postgres and DataFusion. The
  dialect forms shipped as documented text in v4.122.0 (hash, md5,
  sha256) and v4.125.0 (int128) are now lane-verified on Postgres. The
  whole suite on the lane: 24 cases Postgres rejects outright (none
  disagree) — the DFC153 math guards (`exp` overflow is an ERROR there,
  not Infinity) and the DFC147 calendar family, shipped while the lane
  sat unused. Listed in TODO for a pass of their own; the checklist runs
  the verified subset until then.
- **Stage 7**: docs (EXPRESSIONS, typed reference, codelab money block,
  AI guide, CLAUDE.md numeric line, CHANGELOG, TODO), DFC155 §8, and —
  Ross: "we should add a decimal and int128 example to the playground"
  — examples 26 (a sum past 2^63 and 39-digit squares) and 27 (orders
  summed to the cent beside the float sum).
