## 2026-10-26 (Mon) — DFC156: the fold in SQL as a recursive CTE

Ross: "I see that duckdb has recursive CTEs - so it can do our fibonacci
example", then the counter-driven form from the DuckDB docs, then "write
a design DFC and then do it". Measured first (§2 of the DFC): a join to
the source per step is quadratic (20k rows 28 s), the counter form has
no source but still costs ~47 µs a step, and the list form — each
partition aggregated once into an ordered list of its rows, the recursion
indexing it — is linear (20k rows 2.5 s). So: `__parts` builds
`list(s ORDER BY …)` per partition, the anchor is INIT at `__i = 0`
cast to the state's type, the step applies EVERY to the state columns
and `__xs[__i + 1]."col"`, FINAL is read per row (window,
`unnest(__xs[__i])` expands the row) or at `__i = len(__xs)` (group-by,
registry aggregates carried beside the list). DuckDB only; Postgres
(no field access into an anonymous ROW) and DataFusion (lane not
configured) refuse with their reasons. The Fibonacci fold now runs in all
five lanes, HUGEINT to fib(184).

Found on the way: (1) the optimiser's dead-sort rule dropped a `sort`
before a `group-by` with `-first`/`-last`/`-stream-expr`… — those read
arrival order, so the sort was load-bearing in every lane; the flags now
declare group-by an order consumer (`DeclareOrderWhenFlag` takes several
flags per command). (2) The SQL assembler wraps the query before a
group-by whenever an ORDER BY is pending (`needsWrap`), hiding the sort
from the fold: `wrapAsSubquery` carries it as `wrappedOrder`. (3) The
typed lowering's numeric-FINAL rule refused a string fold; the SQL fold
uses `lowerStreamAggAnyFinal`. (4) The harness's quoted-HUGEINT rule
turned a `string(fib)` text column into a number once DuckDB ran the
case; it now applies only in columns exec holds as numbers. Also
`dfc.py --new` died on a non-UTF-8 docsearch hit (`errors="replace"`).

Ross tested the build on his machine straight away ("is it ready to test
on this machine?") with the golden-ratio pipeline through `generate sql`
and found two refusals in a row: the fold's type pass wanted a kind for
every column of the row (`phi`, a `-set-expr` result the assembler cannot
type) where it needs only the columns EVERY reads; and `-lag-default`
without `-order` refused on a `from range` source, whose arrival order
IS its column — the rule the fold already used now serves every window
function (`window_lag_on_range` pins it). Gates on 235a6c6 all green:
vet, slim build, race packages, full `cmd/ssql`, doc-test, triples
258.9 s, scale 60.0 s, explore e2e, playground e2e. Pushed to main; no

harness canonicalises a decimal column's digits.

Stage 0 baselines on HEAD 57b6153 (3 runs): ExprCompare 324–356 ns,
ExprArith 334–363 ns, GroupBySum 187–201 ms, NumericSum 3.4–3.7 ms,
Int128Add 4.5–4.9 ns. Scale budgets ran green on this code yesterday.

Stage 1: `decimal.go` — `Decimal{units Int128; scale uint8}`, the
38-digit bound as `|units| < 10^38`, alignment to the larger scale,
`*` summing scales, half-away rounding on `Rescale`, `Cmp` exact across
scales (an aligned mantissa that overflows 128 bits is already the

## 2026-10-27 (Tue) — the window was quadratic; now one pass

Ross: "ok lets investigate the typed window now". Measured first:
`from range N | window -order n -sum n run -dense-rank dr | count` —
exec 52.8 s at 50 k rows and 210.7 s at 100 k, typed 9.0 s and 29.8 s;
doubling the rows quadrupled the time. Cause, in both lanes and read
before the measurement finished: `computeWindowFunc` (sql.go) and
`typed.windowValue` compute one row's value by scanning that row's
frame, and over the default frame (UNBOUNDED PRECEDING → CURRENT ROW)
the frame always starts at the partition's first row — n²/2 steps per
partition. Dense rank walked the prefix per row, exec's rank walked
every earlier row. Only the `-presorted` streaming path was linear.

**Fix** (`window_running.go`, `typed/window_running.go`): for the
running frame, the sums, averages, counts, extremes and ranks (rank,
dense rank, percent rank, cume dist) are carried across the sorted
partition in one pass — the same operations in the same order as the
scan, so a compensated float sum carried forward IS the sum the scan
from 0 would compute and every value is byte-identical; for the
whole-partition frame (no -order, no bounds) each frame aggregate is
computed once and shared. Bounded ROWS frames (O(n·k)), RANGE frames,
lag and lead stay per row. The fold had this since DFC156
(`runningFoldValues`); this widens the same precompute to the
aggregates, keyed by spec index, merged into the same map. Typed keeps
a `done` mask per spec so the per-row loop skips what the pass filled.

**Proof.** `TestWindowRunningMatchesPerRow` builds 400 records with
ties, missing values and int/float/string mixes and asserts the one-pass
value equals the per-row value at every position for all ten functions
and both frames — the gate that would have caught a drift between the
two paths, since the equivalence lanes compare lanes, not paths. The
equivalence window cases pass (exec, typed, DuckDB); the scale gate has
its first window cases, exec and typed, over six partitions of 500 k
rows: 11.6 s and 4.3 s against 60/90 s budgets. After: 50 k rows 0.15 s
exec, 0.02 s typed; a million rows 2.3 s and 0.25 s; the 14.6 M-row
benchmark pipeline 35 s typed (was still running at 1800 s) and 219 s /
28 GB exec (the record path materialising 14.6 M maps — not where that
pipeline should run). DataFusion's 5.7 s is still 6× ahead of typed:
the remaining time is materialisation, a per-partition `SliceStable`
over a closure, and a boxed `[]any` of results per row; TODO has it as
the next shave.

Lesson for the rules: the DFC113 rule says a perf-sensitive path needs
a scale case, and the window never had one; the quadratic had been
there since the window was written, invisible to every fixture that
fits in a pipe buffer, until a 14.6 M-row benchmark run for another
reason timed out on it. CLAUDE.md's performance rule now names the
carried form as the requirement for every window function.

## 2026-10-31 (Sat) — DataFusion overflow over a derived column

Closed most of the "unknown-kind" gap left open by v4.134.0's checked
integer arithmetic on DataFusion (DFC157 §7c). The checked form
(`DECIMAL(38,0)` and back to `BIGINT`) is only emitted where
`sqlIntOperand` can see both operands are ints, and `sqlColumnKinds` knew
only source columns. So `update -set-expr c 'b * 2' | update -set-expr d
'a + c'` wrapped on DataFusion (`d = -9223372036854775807`, reproduced in
the Python bindings) while exec stopped with an overflow error. The
existing overflow cases all overflowed on sampled source columns, which is
why the lane never saw it.

Fix, all in the translator so `generate rust` inherits it:
`exprToSQLKind` (`generate_sql_expr.go`) translates an expression and
reports "int" when `sqlIntOperand` accepts it, with the params still
installed. `translateUpdate` gives each assignment a kind (`-set-expr` via
that, an integer `-set` literal, `-set-field` the source's kind). A column
is an int only if every value it can take is one, its own value included
where some row keeps it. Kinds are recorded after the whole update is
rendered, because values in one update see the input's kinds. Only "int" is
decided. A column overwritten with something untyped loses a stale int
claim (it was the reverse latent bug: `update -set-expr n 'n / 2'` left
`n` "int").

Gate: `overflow_derived_add` and `overflow_set_add` in
`TestIntOverflowEveryLane`, watched fail on both the datafusion and rust
rows with the recording switched off; translator text pinned in
`TestDataFusionCheckedIntArith`. Still open in TODO: identifiers resolved
through join/fold scopes, expression parameters, group-by/window `-expr`
results, unsampled sources. Aside: in one update, `-set-expr c … -set-expr
d 'a + c'` is an error in exec (unknown field c) but DuckDB accepts it via
lateral alias references; not pursued.

## 2026-10-31 (Sat) — `generate sql` let an update read a field it creates

Found while answering a question about the derived-column overflow: in
one `update`, `-set-expr c … -set-expr d 'a + c'` is an error in exec
("unknown field c") and in record and typed, as the evaluation convention
says (`ssql conventions -category evaluation`: every assignment sees the
row as it entered). `generate sql` put both assignments in one select
list, and DuckDB resolves an earlier select-list alias, so it returned a
value. For the convention's own example, `update -set t 100 -set-expr u
't + 1'`, that value was `u = 101`. Postgres and DataFusion failed with
engine errors.

`translateUpdate` now collects every field the update reads (`-if`,
`-if-field` on both sides, `-set-field`, `-set-bucket`, and expression
reads via the new `exprFieldRefs`, which follows exec's rule that a name
used only as a function callee is not a field, plus the names given to
`has`/`getOr`). It refuses in every dialect if any of them is a column
the same update creates. Exec skips its unknown-field check for an
expression with `has`/`getOr`/`??` and sees the field as absent; SQL
cannot express that, so the refusal is the faithful answer there.
`TestUpdateCannotReadItsOwnNewField` covers seven shapes in three
dialects and was watched failing (21 failures) with the check off.
