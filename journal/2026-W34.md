## 2026-08-20 (Thu) — the pipe-ownership deadlock (found live by Ross)

Ross served /home/rossc/csvs and ran head `ssql from csv shuffled.csv
| ssql limit 10` — 1.2GB file, instant in a shell (0.015s), and the
serve chain HUNG (my repro curl died at the 5-minute timeout). Cause:
startStageChain wired stages with exec.StdoutPipe, whose read end the
PARENT keeps until Wait — so when limit exited after 10 rows, from
never got EPIPE (the parent still held the pipe), filled the 64KB
buffer, and blocked forever while wait() waited for it. A shell never
does this: children own pipe ends exclusively. Fix: explicit os.Pipe
per link, parent closes its copies right after Start; wait() gets
shell status semantics (last stage's error wins; upstream signal
deaths — SIGPIPE after early exit — are normal termination, detected
via ExitCode()==-1, no syscall import so wasm builds stay clean).
Repro now 0.024s. Pinned by TestServeExecuteEarlyExit (2MB fixture >>
pipe buffer; sabotage-verified by dropping the parent close).

Second footgun from the same session: clicking a huge file in the
index ran `from FILE | to explore` — the WHOLE 1.2GB materialized into
the page. Files >32MB now open with a VISIBLE `ssql limit 1000` head
stage (edit it to change; honest sampling, not silent truncation);
direct ?file= hits redirect to the same sampled form.

## 2026-08-22 (Sat) — ssql sample implemented (DFC110)

"Yes, build it." The DFC's hard constraint drove the whole shape:
seeded selection must be byte-identical across every lane, so the RNG
is reference SplitMix64 in the ssql package (spec pinned by
TestSampleHashSpecVectors against the published vector — sabotage-
verified by flipping a constant) and selection is a pure function of
(seed, row index). ssql.SampleN = deterministic Algorithm R emitting
in INPUT order (sample selects, it doesn't shuffle);
ssql.SamplePercent = streaming Bernoulli. CLI: sample N | -percent P,
-seed optional with the chosen seed printed to stderr (loud
reproducibility); sample 0 = the limit-0 dial (stage vanishes from
all generated forms); -percent 0 = loud error (emendation from the
DFC — zero-percent-means-everything was too confusing). Codegen:
record + typed (SerialOnly per DFC; typed programs call the same root
primitives — generic over T, so one implementation serves Record and
struct rows). generate sql: unseeded → DuckDB USING SAMPLE (verified
against duckdb -json), seeded → loud refusal. Registered in both
mains (drift gate green).

Gates: equivalence sample_seeded (byte-identical exec/record/typed/
parallel; duckdb lane skipped WITH REASON via the case Skip map) +
sample_zero_passthrough (all lanes incl duckdb);
corpus sample_seeded (3 modes); TestTranslateSampleSQL (forms,
seeded refusal, zero dial, wrap rules); primitive property tests.
The workspace big-file redirect now opens `sample 1000` instead of
prefix-biased `limit 1000` — the motivating consumer from the DFC.

"It is very slow - I assume it reads the whole file." Correct, and

itself is unchanged — the semantics are right; the default was wrong.

### Addendum: byte-offset sampling at the source (Ross's algorithm)

Ross, unsatisfied with the windowed compromise: pick N random byte
positions, seek, take the line there — "fast and every line has equal
chance." Built as ssql.SampleCSVFile + `from csv -sample N
[-sample-seed S]`: offsets via the same splitmix64, backward scan to
line start, dedupe by start, parse under the header schema through
the STANDARD CSV reader (no second dialect). One honest asterisk on
his equal-chance claim: probability ∝ line length (system sampling) —
documented, negligible for near-uniform rows. Performance war story:
first version measured 1.1s and the profile smell was wrong — each
readLineAt fetched the full 4MB line-cap, ~4GB of page-cache traffic
for 1000 lines; chunked grow-on-demand reads took it to **14ms**
(1500× the exact reservoir, same rows). Two more finds: the SQL
translator's file collector read "-sample 5"'s VALUE as a second
file (read_csv_auto(['kind.csv','5'])) — value-taking flags now
skipped; and DuckDB's system sampling is percentage-only, so the
translation uses reservoir N ROWS (both sides unseeded statistical;

### Addendum: parquet field completion from the footer (Ross's ask)

wire types via arrow type mapping) + a schemaMode() branch in from

### Addendum 2: -columns ^O — the own-file field slot (found by Ross)

`from parquet shuffled.parquet -columns ^O` did nothing: the slot's
fields come from the stage's OWN file, and CompleteSource only knew
upstream-of and join-right-side — a first stage has no upstream, so
it answered "". New fromOwnFileFieldSlot: cursor on a -columns value
(Accumulate-aware; other flags end the run; value-flags skipped) →
synthesize a BARE "ssql from <fmt> FILE" (bare so all columns offer
even after some are picked) → footer schema mode answers in 13ms.
CompleteSource table +4 cases. autocli hardening committed for its
next release (binary extensions error into the FieldNameHint path
instead of the CSV fallback — currently works by luck: real parquet
bytes fail the CSV parse); no go.mod bump needed. Browser note: the
tail bar's wasm can't read parquet (slim) — status hint there; the
HEAD input resolves via /api/schema-fields on the full-build server,
which is where parquet lives anyway.
