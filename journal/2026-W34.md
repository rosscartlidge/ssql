## 2026-08-20 (Thu) — the pipe-ownership deadlock (found live by Ross)

Ross served /home/rossc/csvs and ran head `ssql from csv shuffled.csv
| ssql limit 10` — 1.2GB file, instant in a shell (0.015s), and the
serve chain HUNG (my repro curl died at the 5-minute timeout). Cause:
startStageChain wired stages with exec.StdoutPipe, whose read end the
PARENT keeps until Wait — so when limit exited after 10 rows, from
never got EPIPE (the parent still held the pipe), filled the 64KB
buffer, and blocked forever while wait() waited for it. A shell never
does this: children own pipe ends exclusively. Fix: explicit os.Pipe
per link, parent closes its copies right after Start; wait() gets
shell status semantics (last stage's error wins; upstream signal
deaths — SIGPIPE after early exit — are normal termination, detected
via ExitCode()==-1, no syscall import so wasm builds stay clean).
Repro now 0.024s. Pinned by TestServeExecuteEarlyExit (2MB fixture >>
pipe buffer; sabotage-verified by dropping the parent close).

Second footgun from the same session: clicking a huge file in the
index ran `from FILE | to explore` — the WHOLE 1.2GB materialized into
the page. Files >32MB now open with a VISIBLE `ssql limit 1000` head
stage (edit it to change; honest sampling, not silent truncation);
direct ?file= hits redirect to the same sampled form.
