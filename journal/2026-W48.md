## 2026-11-23 (Mon) — flatten in schema mode: unknown, not empty (DFC169 §12.7)

A public FAQ follow-up ("what about handling structured data") came back unverified after 2 corrections. The model's pipeline (`extract … (?P<payload>\{.*\}) | flatten payload | group-by payload.user_id`) was wrong: `extract` gives strings, and `flatten` needs `cast -type payload json` first. But ssql made it worse. `app.log` isn't in the sample data, so only the schema pre-flight ran. flatten's schema op returned a header minus `payload`, with no keys, even though its own comment said the keys are "not known here". Every try got "unknown field(s): payload.user_id", and the corrected pipeline would have been refused the same way.

The fix:
- the op declines unless the input header already lists `FIELD.key`, so schema mode writes no header (DFC170: unknown is no header);
- schema mode refuses a field typed string, int and so on, as exec does on its first row;
- both modes name `cast -type FIELD json` when the string is JSON text.

`TestFlattenSchemaMode` (`cmd/ssql/flatten_schema_test.go`) failed on all three counts first. CHANGELOG Unreleased, and `doc/cli-nested-data.md` §9. The full cmd/ssql suite, doc-check and vet are green. Live on the LAN instance, two wordings of the question now get `extract | cast -type payload json | flatten payload`; a third ("count requests and sum the amount per user_id") still got a wrong UNSUPPORTED. New eval case `doc-json-in-logs` passes.

**Lesson:** a schema op whose comment says "not known here" and which returns ok=true is a contradiction worth grepping for. The FAQ's pre-flight trusts schema mode, so every such over-confident op misleads the model.
