## 2026-08-09 (Sun) — fixed the duplicate field+op flag-naming bug

Followed up the TODO filed this morning: record codegen for `where` with
duplicate field+op conditions silently replaced the first value with the
last (`-if pop gt 5 -if pop gt 8` → both references emitted as
`flagPopGt2`), and three duplicates didn't compile (`flagPopGt32`,
undeclared). Root cause was TWO stacked defects:

1. `generateCondition` (where.go) derived flag var names from field+op
   only, so duplicates collided within a fragment.
2. `collectParams` (lib/codefragment.go) uniquified declarations but
   rewrote references with a bare `strings.ReplaceAll` — which (a) cannot
   distinguish two identical `*flagPopGt` references in one fragment (both
   got the last name), (b) corrupted by prefix (`*flagPopGt` matched inside
   `*flagPopGt2` → `*flagPopGt32`), and (c) never registered renamed names,
   so a rename could collide with a genuine later name.

Fix mirrors the layering: emission-time numbering of duplicate field+op
names in `generateCondition` (within-fragment uniqueness is the emitters'
contract — identical references are indistinguishable to any later textual
rename), plus a two-pass `collectParams` (claim all keepers first, THEN
rename collisions to the first free suffix, rewriting with
`\*name\b` word-boundary regex). The two-pass shape matters: my first
attempt renamed in one pass and the new `TestCollectParamsRename` unit test
immediately caught a rename landing on a name a later param in the same
fragment still held — recreating the double reference one level up.

Gates, each watched failing against the exact defect it guards:
`where_dup_fieldop_negated` (silent wrong results, 2 dups + `+if`),
`where_dup_fieldop_three` (compile failure), `where_dup_fieldop_two_stages`
(passes pre-fix — it exists to fail against the emission fix WITHOUT the
collectParams registry fix, verified by temporarily restoring the old
collectParams). Typed codegen inlines condition values and was immune;
exec / generate sql / generate ssql don't use Go flags. Full equivalence +
permutations + corpus + lib/commands tests + vet green.

Findings worth remembering:
- **The parser desugars chained comparisons** (`1 < x < 3` arrives as `&&`
  of two BinaryNodes) and pipe syntax (`x | upper()` arrives as the
  builtin) — two planned "open questions" that needed zero code.
- **The differential harness earned its keep on its FIRST run**: the plan's
  §2d table said mixed int/float `min()` promotes to float64; the VM
  actually returns the WINNING operand with its own type (min(-3, -2.5) is
  int64 -3). No static Go type expresses that → mixed min/max refuses and
  falls back. Plan table corrected.
- **`-set-expr` into an existing int64 column with a float result is a
  RETYPE, not a coercion** — exec makes pop/2 into 3.5; emitting int64(…)

  value-preserving int64→float64 widening is inserted.

## 2026-08-10 (Mon) — expr transpiler Phase 1.5: Tier V + -explain

Tier V shipped: an expression outside exprToGo's native subset no longer
ejects the stage (and everything downstream) to record mode. The generated
typed code evaluates it with the expr-lang VM against a static env built
from the struct — `runtime.CompileExprEnv`/`CompileExprFilterEnv` in the
new `runtime/env.go` (CompileExpr minus the Record→env copy; has/getOr
close over the FIELD map so helper names aren't visible as fields), plus a
generated per-schema env constructor (`exprEnvWRow(r)`) and hoisted
compiled-VM vars, all content-addressed and assembler-deduped. Verified
end-to-end: `where -if-expr 'sha256(city) > "8"' | group-by` in parallel
mode keeps GroupByParallel — the whole point.

Design decisions:
- **-set-expr Tier V is existing-columns-only**, typed at runtime by loud
  `runtime.MustCoerce*` helpers (exact match or int64→float64 widening;
  anything else = a retype → stderr + exit 1 pointing at SSQL_MODE=record).
  A NEW field from an untranspilable expression has no knowable Go type →
  record fallback, as the plan's §10 predicted.
- **Codegen validates VM-compilability before emitting Tier V** — an
  expression invalid in every mode errors at codegen listing the parse
  error, instead of panicking at generated-program startup.
- **-explain tier lines ride a new CodeFragment.PlanNotes field** (fragments
  cross process boundaries — the where command can't see generate go's
  flag), printed centrally in AssembleCodeFragments under
  SSQL_EXPLAIN_PLAN: `expr "pop > 8": native`, `expr "sha256(city)": VM
  with static env (function "sha256" has no native Go emission)`, `record
  fallback (reason)`.

Gotchas:
- Parallel programs import stdlib `runtime` (GOMAXPROCS) — collides with
  `cmd/ssql/lib/runtime`. Both assemblers' import renderers now accept
  "alias path" entries; Tier V imports as `exprvm`. (First attempt also
  double-quoted the alias path — invalid import — fixed.)
- `generate go -run` pins the PUBLISHED module version in its temp go.mod,
  so new runtime APIs (exprfn, env.go) fail under -run until the next
  release. Pre-existing behaviour (any new API), test harnesses use
  replace directives. Worth remembering when smoke-testing pre-release.

Gates: TestTierVKeepsTypedPipeline (parallel group-by survives; record
markers asserted ABSENT; -explain assertions incl. the fallback note),
equivalence where_expr_tier_v (sha256 golden — 5/12 cities precomputed,
duckdb lane skipped: sha256 has no SQL translation by design) +
update_set_expr_tier_v, runtime env/coerce unit tests. Full equivalence +
permutations + corpus + vet + doc-check green.

## 2026-08-10 (Mon) — expr transpiler Phase 2: -stream-expr typed accumulators

`group-by -stream-expr INIT EVERY FINAL RESULT` now lowers onto the same
synthesized aggregator struct the built-in aggregations use
(`lowerStreamAgg` in expr_stream.go): init keys → typed state fields with
init values in the aggregator CONSTRUCTOR (`&T{}` zero value is wrong for
`{s:1}`), every → Add() statements, final → the Result() expression
(float64-coerced, mustAggFloat64 parity). Mixes freely with -count/-sum/…
in one aggregator. Forces the serial group-by form (SerialOnly fragment —
fold state is not mergeable; the planner serialises upstream and -explain
says why).

The two semantics traps, both caught by reading evalStreamAggExpr before
writing code:

1. **Record SHADOWS state** — the env build is maps.Copy(state) then
   maps.Insert(record), so a state key colliding with a schema field
   resolves to the RECORD in every-exprs. The plan's §5c assumed the
   opposite and (wisely) said "VERIFY at impl". Corrected in the plan;
   locked by the record_shadows_state unit case.
2. **Every's object replaces the state SIMULTANEOUSLY** — `{a: b, b: a}`
   must swap. Emitted as ONE Go multi-assignment; the
   groupby_stream_swap equivalence golden (flip=0 after 12 rows vs 1 for
   the sequential bug) was watched failing against sabotaged sequential
   assignments — both typed lanes diverged, exactly as designed.

Also: type inference runs to a widening fixpoint (init `{s:0}` + every
`{s: s+pop/2}` widens s to float64 — division semantics inside folds gated
by the groupby_stream_widening golden, 199/2=99.5). Every-keys ≠ init-keys
is a refusal (the VM legitimately reshapes its state map; a struct can't)
→ record fallback with -explain note. duckdb lane skipped on all four new
equivalence cases: generate sql rejects -stream-expr loudly (v4.56.0).

Gates: TestLowerStreamAgg, TestStreamExprTypedGeneration, equivalence

## 2026-08-10 (Mon) — expr transpiler Phase 3: -expr mergeable accumulators

`group-by -expr` aggregations now lower to native typed accumulators that
KEEP GroupByParallel — the reason Phase 3 exists. `lowerExprAgg`
(expr_agg_lower.go) walks the patcher normal form: each distinct
sum(_records, elem) → a `+=` accumulator field (deduped by transpiled
element source), count() → a shared counter, the outer arithmetic →
Result() over placeholder identifiers substituted into the tree. Merge
adds terms and counts (associative) → dual templates preserved; watched
the gate fail by sabotaging Merge — the go-parallel lane diverged on the
avg golden.

Three lessons from the session:

1. **Don't re-parse what exec compiles — reuse exec's compile.** Bare
   `count()` is a PARSE error under parser.Parse (the arity-checked
   builtin); it only parses in exec because buildAggBatchEnv installs a
   dummy `count` env function that shadows the builtin. First attempt
   re-parsed + re-patched and every `count()` silently fell back to record
   (caught because the smoke test greped for an accumulator that wasn't
   there). Fix: export `ssql.CompileAggExprPatched` — exec's own
   expr.Compile with the same env dummies and patcher — and lower from
   `program.Node()`. One compile path, two consumers.
2. **Accumulators keep the element's own type.** The plan's §5d said
   `accN float64`; but the VM's sum of ints is an INT, and `sum(pop) % 5`
   must stay integer modulo (a float accumulator would refuse `%` and
   silently fall back). Locked by the groupby_expr_int_mod golden
   (199 % 5 = 4).
3. **A field OUTSIDE an aggregation is legal exec** — the batch env binds
   it to the group's value ARRAY, so `sum(salary)/len(salary)` works (len
   of array = group size). No typed lowering exists → REFUSAL (record
   fallback preserves the behaviour), deliberately NOT the loud
   unknown-field error that a typo inside sum() gets. Getting loud-vs-
   fallback wrong here would have broken working pipelines in typed mode.

Gates: TestLowerExprAgg, TestExprAggTypedGeneration (emission + parallel
kept + fallback note), equivalence groupby_expr_{avg,arith,int_mod,
grouped} with goldens, Merge sabotage watched failing. Full equivalence +
permutations + corpus + root-package tests + vet + doc-check green.

Phases 1–3 of the transpiler are now done. Remaining: Phase 4
(record-mode native where/update) and Phase 5 (breadth: time.Time,
string→int, split/join/replace via exprfn — grow from -explain
telemetry). Phase 1.5's Tier V means Phase 4 is now purely a performance
win, not a correctness one.

## 2026-08-10 (Mon) — expr transpiler Phase 4: record-mode native

Record pipelines get native expressions too. The plan's §5e sketched
"whole-expression inference" over unknown field types; what actually
shipped is better: REAL types. `from csv` now samples column types in
record mode (same lib.SampleCSVSchema typed mode trusts) and carries them
as a new `AdvisoryTypes` map on the fragment — deliberately NOT
OutputTypedSchema, which would flip the pipeline into the typed
assembler. The walker grew a record resolver emitting typed GetOr calls;
with advisory types, `where -if-expr` emits a native predicate and
`update -set-expr` collapses eval + the per-row runtime type-switch into
ONE typed setter (result type known at codegen; native expressions are
total, so no eval-error path).

Design calls worth remembering:
- **Exact per-type GetOr emission, not a float64 blanket** — int
  arithmetic and % keep VM parity. The GetOr conversion semantics
  (float→int truncates, string parses, silent default) make the emission
  type LOAD-BEARING; the well-typed-column contract matches typed mode's
  and the existing -if GetOr emission's.
- **Advisory propagation is conservative**: where passes it through;
  update tracks assignments and DROPS a field on retype
  (`-set-expr salary 'salary/2'` on an int column → no downstream
  expression may use the stale int64 type — gated by a generation case);
  new fields aren't added (conditional clauses can leave them absent);
  every other command simply doesn't propagate → downstream uses the VM,
  zero regression, reason under -explain.
- **Unknown fields are a refusal in record mode, not loud** — rows may
  have been reshaped mid-pipeline and the VM validates against the real
  first record. (Typed mode stays loud; it has schema truth.)
- **matches (hoisted regexp) stays on the VM in record mode** — the
  record assembler has no package-level decl slot. TODO if telemetry
  shows demand.

Fallout: TestNegatedConditionGeneration's record pins asserted the VM
filter vars; record -if-expr now emits native negation
(`return !((ssql.GetOr(…) > 25))`) — pins updated, semantics unchanged.

Numbers: record-native predicate 47ns/op, 0 allocs vs 1.52µs VM (~32x);
typed native remains 4ns (GetOr pays its schema lookups).

Gates: TestExprToGoRecord, TestRecordNativeExprGeneration (native
where/update, VM-without-advisory + note, propagation, retype safety),
full equivalence (record lanes now natively generated end-to-end) +
permutations + corpus + vet + doc-check green.

That completes plan phases 1–4 in two days against an estimated 5-8.
Remaining: Phase 5 (breadth — time.Time lowering, string→int casts,
split/join/replace via exprfn, record `matches`, JSONL advisory types,
wider advisory propagation), to be driven by -explain fallback telemetry
rather than speculation.

## 2026-08-10 (Mon) — benchmark campaign + experience-report paper

Ran a real measurement campaign on the transpiler (5M-row / 115 MB CSV,
Ultra 9 275HX 24T) comparing interpreted exec, generated code from the
ACTUAL pre-transpiler commit (b1adab9, built via a temp worktree), and
current main. Wrote it up as doc/research/expr-transpiler-paper.md
(indexed in doc/research/README.md).

Headline medians (3 runs, /usr/bin/time -v, outputs verified equal
before timing):
- Micro: predicate 3.0ns/0B typed, 28ns/0B record-native, vs 1,261ns +
  1,088B/9 allocs VM (Tier V ~same as VM: 1,245ns/12 allocs).
- E1 filter+count: pre-gen 8.4s/1.18GB (and "parallel" mode pre-Phase-1
  ran at the SAME speed — the cliff, measured) → parallel-native
  0.44s/329MB = 19× CPU, 3.6× memory. Record-native 3.16s = 2.7×.
- E2 -expr agg: pre 6.9s/2.45GB (typed mode: hard error) → 0.43s/328MB
  = 16× CPU, 7.5× memory + capability unlock.
- E3 -stream-expr fold: pre 6.95s/1.80GB → typed serial 1.68s/29MB =
  4.1× CPU, 62× MEMORY (streaming accumulator vs materialized groups).
- Honest footnote: E2 parallel agrees with serial only to ~12
  significant digits (float summation order across shards).

Paper's judgement: worth it decisively — the CLIFF removal (one
expression no longer downgrades the whole pipeline) and the memory
capability boundary matter more than the constant factors; and the
technique (curated-subset transpilation + tier ladder + differential
oracle + sabotage-tested gates) generalizes to any system embedding a
dynamic expression language in generated code. Costs stated: ~2.3k impl
/ ~1.5k test LOC, 2 days, 1.4s compile amortization, well-typed-column
contract in record mode.

Benchmark hygiene: pre-binary worktree removed after the campaign; all
bench programs/data live in the session scratchpad only.

## 2026-08-10 (Mon) — flag-vs-expression convergence proposal

Discussion after the paper: does the transpiler's success obsolete the
flag forms (-if/-set)? Answer (agreed): no — their value shifted from
performance (now matched) to (1) the interactive surface (field/op/VALUE
completion, zero shell quoting, SSH/pushdown robustness), (2) being the
optimizer's IR (every generate-ssql rewrite and total SQL translation
operate on {Field,Op,Value} and bail on expressions), (3) predictability
(no tier ladder, plus record codegen's runtime-parameterized flags).

What SHOULD change: -if is lowered independently in five places (exec
applyOperator, record generateCondition, update generateConditionCode,
typed typedWhereCondition — no regex — and SQL translateWhere) — the
exact duplication class behind the six-site +if negation bug. Wrote
doc/research/flag-expr-convergence.md: keep both surfaces, converge the
lowerings onto the transpiler (condToExprGo + a parameter-reference leaf
to preserve CodeParam flags), Phase A FIRST = metamorphic flag≡expr
equivalence gates per operator (standalone value; likely to expose
latent divergences), exec's applyOperator deliberately left as the
untouched differential oracle. Unlocks regex-in-typed and optional
normalization of trivial -if-expr into optimizer-visible conditions.
