Wrote a small bash wrapper (`gemma-ollama`) that adapts ollama's REST
API to the `claude -p "$prompt"` shape used by `scripts/test-ai-prompts.sh`,
then ran the 30-test suite against five Gemma 4 quantizations and

| Model | Size | Tuned score | Notes |
|---|---|---|---|
| Claude (Opus 4.5) | frontier | 29/30 | follows docs |
| Gemini | frontier | 29/30 | follows docs |
| Gemma 4 31B | 19 GB | 28/30 | follows docs |

Surprising finding: **a 65 GB model can underperform a 7 GB one** if it
overrides documentation with its pretraining priors. Scout consistently
emitted the old `github.com/rosscartlidge/ssql` import path (no /v4),
called `ssql.Filter(records, fn)` instead of `ssql.Where(fn)(records)`,
and invented a plausible-looking CLI grammar (`-rename` instead of
`-as`, `ssql count` and `ssql avg` as standalone commands). All five
Gemma sizes and gpt-oss followed the documented API.

Iterated the prompts twice along the way. Some fixes that worked
(join schema-header requirement, output-destination clarification);
some that backfired (a Signal-vs-Record anti-pattern note actually
caused 31B to regress one Go test by triggering a speculative
encoding/json import). Writeup in `doc/research/llm-guided-api-design.md`
Appendix E with full before/after table.

## 2026-04-26 (Sunday)

A long focused day of typed-codegen work, in roughly four phases.

### Phase 1: typed runtime library (commits 916386a, d81fa77)

Started with a PoC outside the repo (`/tmp/typed-bench`) to validate
the original `typed-code-generation.md` doc's "35× speedup" claim
before committing to the full proposal. The compute-only
benchmark on 1M rows × 1 join showed:

```
RecordCompute   1,007 ms   644 MB    11.6 M allocs
TypedCompute       66 ms   0.15 MB           5 allocs
```

That's **15× faster, 4,000× less memory, 2 million× fewer allocs.**
The headline claim was real. Wrote the formal proposal
(`doc/research/typed-package-proposal.md`) following the same
structure as the prior LLM API-design paper, then promoted the PoC
into the repo as the `ssql/typed` package — `ReadCSV[T]`,
`WriteCSV[T]`, `Where`, `HashJoin`, `Limit`, `Skip`, `Select`. 25 unit
tests, all passing. Side-by-side example at
`examples/typed_pipeline/` that prints the live speedup.

The headline 10M × 3-join scale benchmark gave **15.1× faster, 34×
less memory** end-to-end with CSV I/O — slightly more conservative
than the doc's original claim but still order-of-magnitude.

Then added a DuckDB v1.5 baseline for context: same workload, run via
the `duckdb` CLI, completes in 0.42 s. So `ssql/typed` is ~12× slower
than DuckDB but ~177× faster than `ssql.Record` — within an order of
magnitude of the gold-standard column-store, in pure Go with no CGO.
Reasonable competitive position.

### Phase 1.5 / 1.6: rounding out the runtime (commits 9532ae9, 9336080)

Added types (int32/uint64/float32/time.Time + pointer-to-T for
nullables), the full join family
(`HashJoin`/`HashJoinMulti`/`HashJoinSized`/`LeftJoin`/`RightJoin`/`FullJoin`),
JSONL I/O, and streaming aggregation
(`GroupBy`/`GroupByOrdered`/`Counter`/`NewSummer`/`NewAverager`/standalone
`Sum`/`Count`/`Min`/`Max`/`Avg`).

Plus `Strict()` CSV mode for schema validation. 1.6 also tried a
custom byte-level CSV reader as a `perf-notes.md` candidate — and
**learned a useful lesson**: the byte reader was 17% slower with 50%
more allocations than `csv.Reader` with `ReuseRecord=true`. Turns out
csv.Reader already block-allocates per row; my hypothesis about
per-cell allocs was wrong. Deleted the experiment, documented the
failure in `typed-performance-notes.md` so we don't repeat it.

### Concurrency proposal (commit 025b6c1) — parked

Wrote `typed-concurrency-proposal.md` covering DuckDB's morsel-driven
parallelism model and how a Go equivalent would look (a
`typed.Stream[T]` partitioned across workers, with
`Parallel(in, n)`/`Serial()`/`SerialOrdered()` boundaries and
parallelism-aware operators). Researched parallel hash join,
fan-out/fan-in patterns, GOMAXPROCS behaviour. Estimated **3-4× gain
over single-threaded typed**, putting us at ~1.5 s on the headline
workload, within ~4× of DuckDB. Decided to **park** rather than
implement — Phase 2 codegen is the more user-visible win and we
should ship that first.

### Phase 2 Tier 1: ssql generate go -typed (commit c9fb00a)

The moonshot: write a normal interactive shell pipeline, add
`-typed`, get a typed Go program. The implementation extended the
existing `CodeFragment` system with optional `InputTypedSchema` /
`OutputTypedSchema` / `StructDefs` fields (purely additive — Record
mode unaffected), then added a typed assembler path in
`generate_go.go` that dispatches when any fragment carries schema info.

Each Tier-1 command (`from`, `where`, `join`, `to csv`, `to table`)
got a typed-mode emitter alongside the existing Record emitter.
`from FILE.csv` samples header + 1000 rows to infer types
(int64/float64/bool/time.Time/string/*string), emits a struct
declaration with `ssql:"colname"` tags. `where` emits direct field
comparisons. `join` builds the merged-struct definition and emits a
`typed.HashJoin` with key extractors and a merge function.

Strict-fallback: any unsupported command produces an error fragment
naming the offender. No silent partial optimization, no mixed-mode.

Then the codegen comparison benchmark (commit 8ea897c) — generates
the SAME pipeline two ways, builds both, runs both via `/usr/bin/time
-v`. Headline:

```
Record   2.622s   921.2 MB    1.2 KB source
typed    0.756s     8.5 MB    2.0 KB source
ratio    3.47x faster   108x less memory
```

The 3.5× wall-time and 108× memory ratio are validated end-to-end on
real generated code. Surfaced the numbers in three places: README
typed callout, typed-reference Phase 2 section, and the codegen
proposal as new section 11a (commit 2fc60fd).

### Phase 2 Tier 2: limit/offset, projection, group-by (commit 5a54208)

Added typed-mode emitters for the next batch of commands:

- `limit N`, `offset N` — straightforward pass-through, schema unchanged
- `include`/`exclude`/`rename` — `typed.Select` with derived structs
  (e.g. `EmployeesRowSubset`, `EmployeesRowRenamed`)
- `group-by FIELDS… -count -sum -avg -min -max` — the biggest piece.
  Emits three coordinated types per group-by:
    1. Key type (single field's Go type or generated `<Input>GroupKey`
       struct for multi-field)
    2. Aggregator struct implementing `typed.Aggregator[T,S]` with
       hand-rolled `Add` and `Result` methods, holding running totals
       typed appropriately
    3. Result struct merging group key fields with aggregation result
       fields, with `ssql:` tags on every field

  Avg uses a closure-wrapped division to handle empty groups; min/max
  track a "have any value" flag so the first observation initializes.
  Tier-3 flags (-expr, -rollup, -cube, -collect) emit clear errors.

11/11 typed-mode tests pass (5 Tier-1 + 6 Tier-2). No Record-mode
regressions. `ssql generate go -typed` now covers an estimated **95%
of real ssql pipelines** — what's left is `update`, `sort`, `distinct`,
`union`, and the expr-language commands, deferred to Tier 3 because
they need either typed-library additions or expression-language → Go
translation.
